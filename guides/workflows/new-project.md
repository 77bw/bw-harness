# 从空项目到第一个可交付功能

假设你已按[快速上手](../quick-start.md)生成 `frame_demo`，导入测试通过。现在想让它把一条文本编码成消息帧。以下输入都发在**业务目录的 Pi 对话**里，一步的结果就是下一步的输入。

1. **确定行为。** `/skill:grill-with-docs 我想给文本加一个长度字节。空串怎么处理、长度数什么，请逐个和我确认。` 试着回答“你”算 1 个字符还是 3 个 UTF-8 字节。确认术语进 `GLOSSARY.md`，若这个选择影响以后读旧消息，就用 ADR（架构决策记录）留下原因。已有明确回答不必再访谈。
2. **把决定变成可测试的计划。** `/skill:ce-plan 根据刚才的决定写进 docs/plans 的一个实施计划，保留非目标：不联网、不开 API。列出空串、中文和超长输入的预期行为。` 打开返回的文件核对；只有聊天中的摘要而没有要求的计划文件，就还没完成这步。
3. **实施但不交付 Git。** `/skill:ce-work mode:return-to-caller 实施 docs/plans 中刚确认的计划，运行测试，不写 Git 历史；若原生流程必须提交，停止该路径并说明。` 此模式跳过交付尾部，不等于替你做了最终代码审查。必要时明确授权本地实施，再请独立审查者核对变更。
4. **收尾。** `/skill:project-governance close 核对本次变更和验收命令，更新 docs/status.md。` 至少能指向正式实现、独立预期值和真实测试结果。一次顺利实现不需要专门写经验文章；若推翻了原有认识，再看[知识沉淀](knowledge-compounding.md)。
