# 文档放哪：按读者下次要找的答案分

例如“消息长度按字节算”：**术语是什么意思、为什么这么选、如何证明实现正确**是三个问题，不需要把同一段话抄到三个文件里。下面的路径都相对于业务项目；目录按需创建，不要求每次任务都写文档。

| 下次有人会问什么？ | 去哪里找或改 | 消息项目中的例子 |
|---|---|---|
| 这个项目怎么运行？Agent 工作有什么限制？ | `README.md` 写用法；`AGENTS.md` 写规则，`CLAUDE.md` 引用规则 | 如何测试 / 未经授权不提交，两者分开。 |
| 什么是“载荷”？ | `GLOSSARY.md`；`docs/agents/domain.md` 只指路 | 给出载荷定义，不把调试进度塞进词条。 |
| 代码现在怎么组织？为什么选这种格式？ | `docs/architecture.md` 记现状；`docs/adr/` 记重要取舍 | 编码器在哪里 / 为什么长度字段不用字符数。 |
| 这次要做到什么？今天做到哪？ | `docs/plans/` 下的当前计划；`docs/status.md` 是接续入口 | 计划写 255/256 边界，status 指向已跑测试和下一个缺项。 |
| 观察到了什么？以后遇到类似问题怎么查？ | `docs/research/` 按主题更新；`docs/solutions/` 放可复用经验 | 一组向量的结果 / 为什么只测往返会漏掉两端相同的错误。 |

**写入之前先找已有位置。** 能用断言固化的行为先加测试；知识文件引用测试即可。研究结论用 `VERIFIED`（在注明条件下已验证）、`HYPOTHESIS`（待验证）、`REFUTED`（条件下已证伪）或 `STALE`（环境改变需复验）。不要把“上次说过”当作验证。

遇到旧 `CONTEXT.md` 或 CE 的 `CONCEPTS.md` 时，先比较内容：术语归词表，进度归 status，决策可能归 ADR。报告分歧，确认后再合并，不覆盖旧内容，也不创建第二本权威词典。下一次开工按[会话接续](workflows/session-recovery.md)读，而不是通读全部文档。
