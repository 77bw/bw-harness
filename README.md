# BW Harness

BW Harness 帮助开发者在多个 AI 会话之间继续同一项工作：用 Matt 的访谈厘清领域语言，用 Compound Engineering（CE）规划、实施、验证、审查和交付，用项目自己的文档保存决定、证据与下一步。**接入改变工作约定，不替你选语言、创建代码目录或安装项目技术栈。**

## 从已有项目开始

在已配置模型的 Pi 安装本包（[安装方式与版本说明](guides/installation.md)），进入业务项目目录，在 Pi 对话中输入：

```text
/skill:setup-bw-harness check 请先检查现有指令、文档根、Git 和实际验证入口，不写文件。
/skill:setup-bw-harness 接入当前项目，保留现有规则和代码。只对实际冲突向我确认。
/skill:bw-help 我已有一个实施计划，接下来从哪继续？
```

第一次接入空目录也用同一个 setup。它读随 Skill 分发的模板，合并项目指令、工作流和真实状态；没有术语、重大决策或经验时不创建空文档。`check` 不写文件，升级工作约定用 `update`。普通开发无需反复初始化。

## 新项目接入与文档架构

按[安装指南](guides/installation.md)注册后，在自己的业务项目根目录启动 Pi，而不是在 BW Harness 分发包目录执行接入。可以是只有一个源码文件的项目，也可以是空目录。下面的 `/skill:` 输入发给 Pi；只有标为 `sh` 的代码块在终端执行。其他宿主的调用方式见安装指南。

### 先分清：接入工作流，不等于完成项目设计

`setup-bw-harness` 先探索项目，展示发现与拟变更，再按实际情况合并工作约定和基础文档。它会对齐文档根、指令入口、计划方式和实质冲突，但不生成应用代码，也不逐块采访并填满所有业务文档。

**setup 搭好“资料放哪里、如何协作、怎样接续”的入口；需求、术语、方案和验收在后续真实任务中对齐并沉淀。** 空项目的状态可以如实写“尚未开始、目标待明确”，不把模板当成已确认的项目事实。

### 完整文档架构：哪些现在有，哪些以后长出来

下面展示的是**按需发展后的文档全景，不是 setup 一次生成的目录清单**。路径相对于业务项目，默认文档根为 `docs/`：

- **[接入]**：setup 创建或合并；已有等价入口时沿用实际位置。
- **[条件]**：接入时确有需要才创建或合并，不保证每个项目都有。
- **[后续]**：后续有真实内容时再创建，不预建空文件或空目录。

```text
<项目根>/
├── AGENTS.md                         # [接入] Agent 规则与资料入口
├── .gitignore                        # [接入] 合并适用的忽略规则
├── README.md                         # [后续] 项目用途、运行和使用方式
├── GLOSSARY.md                       # [后续] 已确认的业务术语
├── CODING_STANDARDS.md               # [后续] 项目编码标准，按需
├── REVIEW.md                         # [后续] 项目审查标准，按需
├── .compound-engineering/
│   └── config.yaml                   # [条件] CE 共享配置
└── docs/
    ├── agents/
    │   ├── domain.md                 # [接入] 领域资料的位置与使用规则
    │   ├── workflow.md               # [接入] 工作流与文档职责
    │   └── issue-tracker.md          # [条件] 独立的任务跟踪说明
    ├── status.md                     # [接入] 当前状态、证据与下一步
    ├── architecture.md               # [后续] 当前已实现的系统架构
    ├── adr/
    │   └── 0001-决策主题.md            # [后续] 重要取舍及其原因
    ├── plans/
    │   └── 日期时间-类型-主题-plan.md    # [后续] 同一主题的统一计划
    ├── research/
    │   └── 研究主题.md                 # [后续] 假设、实验、结果与适用条件
    └── solutions/
        └── 问题类别/
            └── 已验证经验.md           # [后续] 值得复用的诊断与解决经验
```

这是默认单上下文示例，不规定源码目录。只保留一个主要项目指令入口；已有 `CLAUDE.md` 或 include 约定时沿用，不再平行维护另一套规则。CE 文档根只从共享 `.compound-engineering/config.yaml` 的 `docs_root` 读取，未设置时用 `docs`。领域资料可以沿用独立位置；出现真实的多上下文边界时，再用 `GLOSSARY-MAP.md` 指向各领域的词表和 ADR。

#### 每类文档负责什么？

| 要回答的问题 | 文档职责与创建时机 |
|---|---|
| Agent 怎么工作、去哪里读资料？ | `AGENTS.md` 链接 `agents/domain.md`、`agents/workflow.md` 和状态入口。`domain.md` 是使用规则，不是业务领域模型。setup 完成这层接入，后续按项目变化维护。 |
| 当前做到哪里、接下来做什么？ | `status.md` 保存当前目标、活动计划、已验证进展、最近检查、开放工作与下一步。setup 写真实快照，任务完成、暂停或中断时原位更新；它是索引，不是聊天日志或第二套任务清单。 |
| 项目如何运行、系统现在怎么组织？ | `README.md` 写真实用法，`architecture.md` 描述已实现的架构。后续随实际代码更新，不把设想写成现状。编码和审查标准按需由项目原有约定或 CE 原生流程维护；setup 不启动标准访谈。 |
| 业务名词是什么意思？为什么接受重要取舍？ | 术语确认后写 `GLOSSARY.md`；重要、难逆转且有真实权衡的决定才写 ADR。例行实现细节留在计划，不为每次讨论生成 ADR。 |
| 本次做什么、如何做、如何验收？ | 需要持久计划时在 `plans/` 维护同一主题的统一计划，容纳需求、方案、实施单元与验收。外部跟踪器只关联和协调，不再复制一套实施正文。 |
| 实验说明了什么？以后怎样避免同类问题？ | `research/` 按主题记录结果、假设、反例和条件；`solutions/` 由 CE Compound 判断是否沉淀可复用经验。测试或规则已足够时，可以不新增经验文件。 |

一项事实保留一处权威正文，其他位置引用。词表、ADR、计划、研究和经验都在有内容时创建；**没有这些可选文件，不代表接入失败。** CE 的运行收据、原型和交接产物仍按原生约定保存，不为凑齐这棵树而搬动；原始私人材料和临时工作放在合适的受保护、已忽略位置。详细边界见[文档职责](guides/document-structure.md)。

### 新项目具体怎么走

#### 1. 只读检查，了解将修改哪里

```text
/skill:setup-bw-harness check 检查生效指令、Git 根、文档位置和已有验证入口
```

结果应指出实际位置、缺口和冲突，不新增文件、不初始化 Git。空项目还没有词表或测试是正常的；位于更大父仓库下时，先明确项目边界。

#### 2. 接入基础规则和真实状态

```text
/skill:setup-bw-harness 接入当前目录，使用 CE 本地计划；保留已有配置、入口及工作中修改
```

它先展示已有、缺少、冲突和未知，再读取自身模板并合并。影响结果的选择或冲突会找你确认，已明确的非冲突步骤直接继续，不逐段重复确认。

完成时查看 **已创建／已更新／已保留／阻塞／检查／下一步**，打开返回的实际状态路径。空项目通常得到指令入口、领域与工作流规则、状态文件和适用的忽略规则；共享配置及独立任务跟踪说明按需处理。独立项目尚无仓库时才初始化 Git，已有仓库保留历史和远端；接入不代表已提交、推送或发布。

#### 3. 核对实际差异

在项目根运行：

```sh
git status --short --branch
git diff
git check-ignore .local/probe
```

变更应只覆盖约定文件；`git diff` 不显示未跟踪文件正文，需按 `git status` 列表打开新文件检查。`.local/probe` 应被忽略。再次接入应更新同一块，而不是追加第二个同义指令块。已有项目继续使用原有检查命令；没有业务测试时如实记录缺口，不声称测试已通过。

#### 4. 开始需求对齐，而不是逐个填模板

先准备项目想法、使用者、场景、已知约束和“怎样算有用”；未知项可以直接说未知。不确定该走哪条路时，用导航并明确执行意图：

```text
/skill:bw-help 这是一个新项目，我想做【项目想法】，给【使用者】在【场景】下使用，已知约束是【约束】。请判断当前缺的是产品范围还是领域语义，执行推荐的需求对齐步骤；先明确首版目标、非目标和验收标准，暂不实施代码。
```

也可以直接选与当前缺口匹配的入口，**不要求两个访谈都走一遍**：

- **尚未确定产品要做什么**：用 [ce-brainstorm](guides/skills/ce-brainstorm.md) 明确用户、问题、首版范围、流程和验收。例如：

  ```text
  /skill:ce-brainstorm 我想做一个离线消息编码工具。请先和我确认使用者、核心场景、首版非目标和验收例子，一次问一个影响结果的问题；将确认结果保存在同一份需求级计划中，暂不实施代码。
  ```

- **方向已定，但业务术语或边界有歧义**：用 [grill-with-docs](guides/skills/grill-with-docs.md) 通过具体场景澄清。例如：

  ```text
  /skill:grill-with-docs 我要做一字节长度前缀的文本帧。请用空串和「你」帮我确认载荷、长度单位、上限和超长输入行为，一次问一个会改变实现的问题；记录已确认术语，暂不实施代码。
  ```

方向和语义都已明确则跳过访谈。对齐完成的标志是：目标和非目标明确、关键术语一致、范围和约束清楚、有具体可验收的例子，剩余问题已区分阻塞或可延后。确认的术语进入词表，重大取舍才进入 ADR；不要求每块文档都产生新文件。

#### 5. 把已确认需求变成同一份实施计划

继续同一会话。若上一步已产生需求级计划，把**返回的实际路径**传给规划：

```text
/skill:ce-plan 请将【上一步返回的实际计划路径】原位补全为可实施计划，沿用已确认需求，补齐技术方案、实施单元、实际验证命令和完成标准；不另建同主题计划，暂不实施代码。
```

若上一步只有聊天简报，则把已确认的目标、非目标、要求、约束和验收例子交给 `ce-plan`，明确要求保存实施计划，并检查它返回的实际文件。当前约定不是先写一份独立需求文档，再复制成技术方案和任务清单；**同一计划从需求级逐步补全为实施级**：

| 计划中的精确标题 | 内容 |
|---|---|
| `Goal Capsule` | 目标、手段、权限与停止条件 |
| `Product Contract` | 用户、需求、流程、验收示例和范围 |
| `Planning Contract` | 技术方案、关键决定、假设与顺序 |
| `Implementation Units` | 可执行的实施单元及对应要求和测试 |
| `Verification Contract` | 项目实际验证命令和质量要求 |
| `Definition of Done` | 整体及各单元的完成标准 |

需求级计划主要包含前两部分；规划补齐实施部分。标题保留执行契约原拼写，正文使用简体中文。计划可保存为 Markdown 或 HTML，以实际返回为准。明确的小改仍可直接实施和验证，不为套流程强制创建计划。

#### 6. 确认计划后实施，暂停时留下接续入口

检查计划是否足以让别人独立验收，再显式选择实施，或把实际计划路径交给 `ce-work`：

```text
/skill:ce-work 【实际实施计划路径】
```

实施、测试、审查与 Git 交付沿 CE 原生流程和项目约定，见[从计划走到交付](guides/workflows/git-delivery.md)。重要任务完成或暂停时，用 `project-governance close` 核对证据、维护相关知识，并让状态文件指向当前计划和下一步，不另建每会话报告。

下一会话从原状态继续，不必重新 setup 或重新访谈：

```text
/skill:bw-help 请从当前状态和活动计划核对真实进度，告诉我下一步；先只读，不重新规划。
```

需要移交执行时明确说“执行这一步”；只有咨询时，导航不会自动实施。完整示例见[新项目首个功能](guides/workflows/new-project.md)与[会话接续](guides/workflows/session-recovery.md)。
