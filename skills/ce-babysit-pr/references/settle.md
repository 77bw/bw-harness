# 停止条件、结算和合并就绪判断

**“看起来准备好了”是一种判断，而不仅仅是一个已用的计时器。** CI 呈绿色并且 PR 已经安静了一段时间是远远不够的 - 请参阅下面的审核仍在进行中的检查。

**正在进行的信号仅控制*合并就绪声明*，而不是工作。**即使在审核正在进行时，也要继续解决收到的开放反馈：**不要等待 👀 清除后再对已发布的评论进行操作。**在处理已经留下的反馈之前等待审核*完成*会序列化工作，就像在处理评论之前等待完整的 CI 运行一样 - 核心原则的错误禁止。持续对每个未解决的项目采取行动；进行中信号所保留的“唯一”事情是“看起来准备好”调用。 （引擎仅报告 PR 安静了多久；审核是否仍在进行由您根据下面第 3 步中的审核仍在进行检查来判断。）

## 步骤 3：停止条件

在交互式运行中（管道模式在`references/pipeline.md`有自己的停止点），将每个条件分类为两种之一。 **真正停止**结束手表并返回指针。 **站立残差**会报告给用户并阻止*合并就绪声明*，但自维持手表**继续围绕**它运行 - 它**不会**结束循环。 **Terminal**、**looks-merge-ready**、**budget** 和 **`blocked-external-drained`** 是活动 PR 的真正停止点（在 `stack-ready`/`stack-land` 下，静态层是其中任何一个 — `references/stack.md` 之前的过渡）。第一个 **`blocked-external`** 观察会开始下面描述的限时等待审核，而不是停止。 **`needs-human`**、**`blocked-failing`**、`stack-sync-needed` 或链式查找的不确定结果，以及未解决的**语义冲突**是常设残差。本身当前的目标之上的陈旧依赖项是堆栈健康残留，而不是调用目标就绪*作为下一个PR*的阻碍。在**检查点模式**中，无论类别如何，单次刻度都会结束；区别仅改变您报告的内容以及是否打印恢复命令。

**真正的停止——手表结束：**

- **终端** — PR `MERGED` 或 `CLOSED`，除非此运行刚刚完成PR上的授权`stack-land`合并：该合并结果是层转换（请参阅`references/stack.md`中的堆栈着陆步骤），而不是运行级别的终端停止。
- **看起来合并就绪（已解决）** - 以下每一项均成立。 GitHub本身报告它可合并：`mergeability_certain`、`mergeable == "MERGEABLE"`和`merge_state_status == "CLEAN"`（在合并计算绑定到独立证明的当前基点和当前头之后，这将必需检查和必需审查策略推迟到GitHub），或者`update_branch_at_merge`为真（唯一的差距是为合并者留下的`BEHIND`分支，每个`references/branch-currency.md`）。 `base_ref_blocker == null`。 `checks_terminal` 为真（没有任何东西仍在运行）。 **零可操作的积压** - `counts.threads == 0` **和** `counts.comments == 0`（没有未解决的内联线程，没有未执行的top-level/review-body反馈） - **和`open_needs_human == 0`**（您因人工决定而推迟的线程或评论意味着它*未*准备好 - 报告它，不要将其称为合并就绪），**和`branch_currency_blocker == null`**（没有开放，声明，或停放的基础运动项目）。 `quiet_seconds` 已达到解决阈值 ** 并且下面的审核仍在进行中的检查很明确 ** - 要么看起来没有审核正在进行，要么它允许的有界等待已经用完并且您这么说。 “可针对当前基础合并”并不意味着 PR 头包含最新的基础提交；需要维护的状态属于`references/branch-currency.md`所有，而GitHub报告`CLEAN`的普通基地移动则没有。 链状态进一步限定了该结果。 托管目标需要`stack_blocker == null`（快照遵循GitHub的特定`MERGEABLE`/`CLEAN`读取普通主干漂移）；称之为**“准备好堆栈中的下一个PR”**，从不独立准备好，并单独列出过时的上栈条目。 在手动依赖链中，将其称为**“相对于其父级准备就绪”**，并命名必须首先登陆的任何开放父级。 基本身份`race`、`mergeability-pending`或`probe-error`、链`probe-error`或未清除的未知管理新鲜度（`stack_blocker`存在）只会阻止准备就绪，直到新的观察证明结果为止。 GitHub可以在主要动作之后无限期地将其测试合并保留在旧基地上；当只有测试合并的基础父级滞后时，引擎会发出 `base.identity == "stale-computation"` 和 `merge_computation_stale: true`，这算作是确定的 — 如果其余条件成立，则声明就绪，并在报告中披露 GitHub 的缓存合并计算已过时（在合并时发生新的重新计算）。 稳定阈值是脚本的 **300 秒默认值**； *唯一*会扩大它的事情是在 `merge-ready` 唤醒后重新启动，您判断尚未准备好（下面的审查仍在进行中） - 永远不要提前扩大第一个臂，无论是否审查机器人。 稳定窗口是一个“冷静”信号——证据PR停止移动，**不**保证不会有进一步的审查。 **在报告准备就绪之前，检查 PR 描述新鲜度（最终检查点）。** 充满增量提交的监视 - 修复、新行为、已解决的反馈、从基础到头部的合并 - 通常会留下*原始* PR 描述，描述不再存在的 PR。 如果PR现在所做的与它的描述有重大偏差（new/removed行为，改变的方法，解决了警告），**自主刷新它：在描述更新模式下非交互地调用`ce-commit-push-pr`（`mode:pipeline` - 它直接通过`gh pr edit`重写和应用，没有预览提示）。 不要问 - 当前描述是保持 PR 合并就绪**的一部分，更新它是 `ce-commit-push-pr` 自己的功能之一。 如果描述仍然反映了更改，则保持不变。 将独立的 PR 报告为“看起来已准备好 - 您需要合并”，而不是“安全合并”。对于已确认的托管堆栈，请在将此层停止视为整个运行的停止之前应用`references/stack.md`中的层转换规则。 在**检查点模式**中，您无法强制执行手动重新运行之间的经过时间，因此，如果它在其他方面是干净的，但`quiet_seconds`低于阈值，请说“现在绿色，在〜5分钟内重新运行以确认它在合并之前保持安静”。
- **在排出审查后，在外部CI批准时被阻止** - `checks_awaiting_approval > 0`没有可操作的积压意味着工作流程正在**等待基础存储库维护者的批准运行**（GitHub的分叉-PR安全门）。你和循环都无法触发它； **从不自动批准**运行。 CI被阻止，但审查仍然可能独立移动，因此第一个`blocked_external`观察不是交互式停止：
  - **交互式自维持手表：**无需询问，应用相同的审查仍在进行的判断，并在正常轮询间隔 (`--interval 150`) 重新启动，当没有审查时，使用 `--blocked-external-drain-seconds 300`，或者当有审查时，使用 `--blocked-external-drain-seconds 900`。助手将一个时钟绑在当前的头上。新的或编辑过的外部反馈、已提交的审阅或审查者信号已移动，或者新的负责人将其重置；未更改的批准门、循环自身的回复、check/base/stack 移动以及项目处理方式的记录均未更改。传入的反馈仍然在批准门之前唤醒——立即解决它，然后重新等待新证据。如果批准通过，则返回普通CI手表。
  - **排水到期：** `blocked-external-drained` 是您决定的唤醒时间。在 900 安静秒时，来自同一审查者的具体先前当前头部计时可能会证明使用 `--blocked-external-drain-seconds 1800` 重新装备是合理的；它可能永远不会因为仅仅缺少完成信号而缩短 900 秒的楼层或延伸到 1800 秒以上。当看起来没有审核即将到来时，300 秒就结束了——但在交还之前再次应用审核仍在进行的判断。审核者可以在选择等待长度后宣布自己，并且在等待期间没有任何东西可以自行观察到这一点，因此到期唤醒是仍然可以捕获运动的唯一位置。只有明确的用户请求在更长的规定时间内继续监视批准门会覆盖这些默认值，并且它仍然受到此调用的原始预算的限制。
  - **交回：**一旦选定的引流到期且审批门仍然存在，请停止而不询问其他问题。报告所有观察到的反馈均已处理、当前负责人审核安静的时间、CI从未运行，因为仍需要维护者批准，并给予主机渲染的简历调用。稍后的通知或显式重新调用将启动下一个有界监视。
  - **管道/无人值守：**不要**排空、询问或旋转 — 返回带有运行 URL 的 `blocked-external` 残差并终止。其有界协调器合约明确不等待人工审查或批准。
  - **检查点：**处理当前tick，报告审批门，声明监控暂停，并给出恢复调用；它本身不能强制执行消耗时间。
- **预算耗尽** — 活动`invocation_elapsed_seconds`达到固定调用预算（默认 8 小时的活动观察时间，或用户在输入时选择的持续时间），**或**原始挂钟达到 3 个日历日的逆止器，用户设置的轮数上限，或者用户中止。 `max-runtime` 尾流通过 `max_runtime_ceiling`（`active-budget` 或 `backstop`）命名哪个天花板被击中。监视重新准备和确认的托管堆栈层转换必须与原始 ID、开始和预算相匹配；他们既不能重置也不能延长上限并保留累积的死区时间。截止日期的最终刷新可能仍会报告`terminal`或已经解决的`merge-ready`；两者都立即停止并且不再开始新的工作。否则，`max-runtime` 的排名超过 actionable/residual 的工作，因此不会开始额外的代理轮次。在`max-runtime`，报告发出的`invocation_elapsed_seconds`和预算，从不报告`persisted_state_age_seconds`，并且不会自动启动另一个调用。这是 `references/tick.md` 停止点下方的钝性成本底线，当 PR 的轨迹显示其未收敛时触发 - 它捕获永远不会触发触发器的失控，而不是卡住的 PR 结束的正常方式。有界调用交回控制权；只有稍后的显式 user/orchestrator 调用才会启动另一个预算。

**只剩下定时等待，并且在结束时没有任何东西可以唤醒该代理。** 结算窗口、扩大的审核等待和批准消耗都需要在时间用完时唤醒。探测器通过上面的臂标志提供了一个。主机的机制可能不会，因此将其作为唤醒源，跳过这些手臂标志并从 `quiet_seconds` 和 `blocked_external_review_quiet_seconds` 判断每个滴答的相同限制。快照中的非空`timed_wait`表示仅剩下稳定窗口，其`seconds_remaining`假设为300秒。当勾号发现只剩下未过期的等待时，寻找主机指令允许的计时器，包括您尚未加载的工具。返回到该线程的一次性计划任务计数。将其设置为等待结束后，然后结束回合。一旦计时器触发或运行停止，请将其删除，这样主机的日程安排中就不会保留任何过时的内容。如果没有，则报告该状态并在唤醒源仍处于开启状态的情况下结束回合。使用 `⏳ Waiting on a timed window — <evidence>.` 打开，说明此唤醒源可能会错过什么，并给予主机渲染的恢复调用，因为如果没有事件到达，运行将保持等待并且预算不会检查。这是一种等待，而不是真正的停止。后来的事件带来了一个新的滴答声，它会根据经过的时间重新判断，直到那时它才算作 `stack-land` 陆地步骤的解决。

**`stack-land` 层的窗口较短。** `stack-land` 下的目标是迅速落地堆栈，而不会在即将到来的审核之前落地。因此，一旦至少一名审查者对当前头部做出最终裁决并且仍将进行的审阅检查明确，则解决阈值是 60 秒，而不是 300 秒。着陆一层会重新设置下一层的基准并重新启动其 CI 和审查，因此每层的完整窗口会增加等待时间，而不会比已完成的审查所提供的保护更多。将探测器作为唤醒源，为其配备 `--settle-seconds 60`。其他所有案例均保留 300 个，其中包括尚未审查者完成的图层。

**常设残差 - 报告它们，然后继续观察（这些不会结束自我维持的循环）：**

- **`needs-human`** — 来自 `ce-resolve-pr-feedback` 或 `ce-debug` 的累积类型决策，或语义合并冲突第 2 步（勾选）无法机械解决。托管上栈冲突遵循步骤 7（托管上栈维护）的较窄规则：中止管理器事务并报告它，而不是决定另一个 PR 层的语义。通过共享原子标记保留每个完整的残差，显示其完整的决策负载，并使每个覆盖的审查线程保持打开状态。暂停的决策会阻止合并就绪，但在交互式连续模式下，它不会结束监视：继续处理独立审查和 CI 流。当任何覆盖的源发生变化或消失时，快照会使分组的残差失效，并使每个幸存的源再次可操作；切勿维护单独的特定于路线的决策或重新打开路径。
- **`blocked-failing`** — 已发送的支票 `ce-debug` 呈红色（`has_failing_checks` 与 `counts.ci == 0`，没有任何新内容可供发送）。相同形状：报告红色残差，它会阻止合并就绪，但稍后提交或头 SHA 可能会清除它 - **继续观察**，并且探测器不会在相同的红色残差上重新唤醒（它与手表武装时记录的状态进行比较）。只有上面的 **真正停止** 或用户才能结束循环。
- **`stack-blocked`** - 目标是管理器过时的或未知的管理新鲜度，而GitHub未报告某些`MERGEABLE`/`CLEAN`（CLEAN读取下的普通主干漂移不是阻塞器），管理器发现失败，或步骤7无法完成其清理堆栈事务。报告`stack_blocker`和相关`pr_chain`条目；继续review/CI工作，但不执行普通的基础更新或声明目标准备就绪。稍后的管理器同步、成功的探测或成功的步骤 7 维护会清除残留。即使目标可以报告为下一个准备就绪，剩余的陈旧堆栈条目也是堆栈运行状况残留。

**审核还会来吗？ （外观就绪检查的一部分）。** 稳定窗口告诉您 PR 停止移动。它不会告诉您审阅尚未进行——在后台审查者开始之前，窗口可能已经过去。在做出决定时，从一个简单的`gh`查看当前头部，涵盖公告可以到达的每个位置：PR主体上的反应，顶级评论，对该头部进行的检查，以及针对它的评论。恢复的运行不会记忆已分类的临时注释，并且快照中不存在分派的注释，因此查找是唯一仍可以看到它的位置。

这种外观告诉你，只有当每个地方都被完整阅读时，才会有任何评论。您无法阅读的地方（失败的请求或在页面限制处停止的结果）并不是缺席信号，因为您还没有查看它。再读一遍，逐页阅读。如果仍然无法读取，请说出哪个位置，然后像等待审查者一样等待，该审查者宣布自己尚未显示任何内容：直到读取成功并且没有显示任何待处理的内容，或者直到有限的等待时间结束。

一个自我宣布的审稿人——一个👀反应，一个“审阅……”的注释——已经告诉你它**开始了**。没有任何义务要求它在完成后收回该声明，因此长期公告并不能证明工作仍在继续。相反，请查看同一位评论家对此头的评论，并询问它是否解释了其宣布的评论。带有审查者裁决的东西 - 它的审阅，它的评论，或者*是*它的审阅的检查运行 - 达到最终结论意味着它停止了：说出哪个，并且永远不要将超时或跳过视为批准。任何仍在运行的内容都意味着它仍在工作。不考虑已宣布的评论的输出会使评论悬而未决，因此将该评论者视为没有产生任何内容的评论者：来自同一应用程序的不相关检查在其评论尚未出现时完成，这不是评论完成。一个审稿人宣布了自己的观点，但无论如何都没有什么可证明的，这才是真正无法判定的情况。当您在不同位置匹配审查者时，请注意应用程序审查者会出现在两个登录名下：REST 结果（包括反应端点）添加尾随 `[bot]` (`cursor[bot]`)，而 `gh pr view` 使用的 GraphQL 则将其保留 (`cursor`)。比较没有该后缀的登录。检查运行通过 slug 命名其应用程序，这是没有后缀的相同登录名。

公告并不是即将进行审查的唯一证据。一位审阅过 **早期** 头部而不是这个头部的审查者通过其自己的历史在这个 PR 上告诉了你同样的事情，并且许多审查者以这种方式工作而从未宣布任何内容 - 在某些仓库中根本没有审查者宣布。将该审查者视为尚未发布任何内容的审查者，并且以相同的方式清除：当它审阅此头时，或者当有界等待耗尽时。

请记住这种不对称性：**存在**的信号提供了丰富的信息，而**不存在**的信号则无法告诉您任何信息，因为许多审查者什么也没宣布，只是简单地发布。因此，永远不要最终等待完成信号，也不要让丢失的信号自行阻塞。

当您可以看到正在进行的工作时，请等待一段时间，当审查者宣布自己没有任何结果时，请等待一段时间。 通过使用更长的`--settle-seconds`重新运行arm命令来重新武装——传递它使得重新武装真正生效，因为安静已经超过了300秒的默认值，并且普通手臂将在下一次轮询时重新启动。 使用：大约 900，当审查者的具体事先时间证明合理时，延长一次至不超过 1800。 这些只是上限，而不是目标——在这里观察到的宣布审稿人在四到六分钟内完成，而一个从不宣布的慢审稿人在 157 篇评论中的 21.6 分钟 p90 和更长的尾巴超出了它。 一旦 1800 秒的安静时间传递出未改变的证据，停下来并清楚地说出你无法证实的事情；永远不要根据相同的未改变的证据重新武装过去。 加宽的窗口是您对所查看的证据的判断，因此当该证据移动时，手表会在 `review-evidence-moved` 唤醒您，而不是在已发生变化的状态下休眠窗口。 与做出任何决定时一样，从当前头部重新判断：如果移动的内容影响了您正在等待的审查，则普通窗口将再次决定，如果没有，则像以前一样重新准备。 引擎仅报告有物体移动；是否解决任何问题都是你的。 准备就绪是对用户的建议，绝不授权合并，除非在`posture:stack-land`下，其中选择该姿势是用户的提前是，并且确定的前缀确实落地。 因此，提早调用通常只需要披露，而在 `stack-land` 下，它的代价是比审查者完成的时间更早，而永远保留在每种姿势中都会花费 PR。
