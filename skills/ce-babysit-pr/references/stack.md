# 托管堆栈：状态、发现、转换、堆栈上维护、着陆

## 姿势（全文）

跑步时只保持一种姿势。它被写为 `posture:target|stack-ready|stack-land` — 与 `watch` / `checkpoint` / `mode:pipeline` / 持续时间不同。在每个托管堆栈层`--continue-invocation`过渡以及现有预算标志上重新声明相同的姿势。

| 姿势 | 行为 |
| --- | --- |
| `target` | 仅命名为PR。停在看起来准备好的地方。当确认的多层托管堆栈需要工作时，可以提供堆栈范围的一次；下跌保持目标本地止损。永远不会合并。 |
| `stack-ready` | 一旦活动层处于**静态** — 可操作的积压为零 (`counts.threads/comments/ci == 0`)、** 无常设剩余**（无开放 `needs-human`、无 `blocked-failing` — `has_failing_checks`，没有任何剩余可分派 — 无 `stack-blocked`、无开放或已认领的货币项目），并且没有正在进行的委托工作 — 自动继续到下一个需要工作的开放非草稿上栈层，即使在静态层处于CI 仍在运行或其稳定窗口尚未到期。较低层位于观察者的下层探测器下方；重新开放的最低层会将步行拉回。永远不会合并。坚持跑步；不要重新询问每一层。 |
| `stack-land` | 就像 `stack-ready` 一样用于遍历。选择或移交`posture:stack-land` **是**运行级土地授权。着陆仍然需要**稳定**，而不仅仅是静止：一旦最底部的开放层看起来准备就绪（完整的第3步门），通过`gh stack merge`+`gh stack sync`合并它，然后继续。 |

**选择：**用户命名一个PR，没有堆栈语言→默认`target`，但如果是确认的多层托管堆栈，询问一次（只有这个PR vs 整个堆栈准备就绪）。意图own/finish堆栈→`stack-ready`。绿色时意图land/merge → `stack-land`。优先考虑意图而不是关键字匹配。显式的“托管托管堆栈”请求选择`stack-ready`（或当土地意图也明确时选择`stack-land`）。在 `mode:pipeline` 中，仅使用调用中已提供的 posture/scope — 不要询问。

当已确认的托管堆栈正在运行并且您需要CLI配方时，请阅读`references/stack-commands.md`。

## 发现与延续

**自动对目标的PR链进行分类；永远不要依赖用户宣布堆栈。** 第一个快照和以后的每个轮询都会使用 `gh stack view --json` 探测只读本地管理器，仅当其分支列表包含目标 PR 时才接受它。如果这无法证明成员资格，则帮助程序将使用只读 GraphQL 后备。成功的空栈意味着`pr_chain.manager_status == "absent"`。仅当单独的只读查找解析存储库的默认分支时，特定的堆栈字段模式不可用响应也意味着`"absent"`；身份验证、传输、速率限制、格式错误、其他 GraphQL 或失败的默认分支探测意味着 `"probe-error"`。当没有确认管理器时，普通的开放PRbase/head关系将独立的PR与手动依赖链区分开来。 Discovery 永远不会运行 `gh stack checkout`、导入堆栈、切换分支或更改远程状态。

**只有当新鲜快照有`manager_status == "confirmed"`时，堆栈范围的延续才会激活；没有其他分类授权它。** 手动依赖链永远不会激活堆栈范围的延续：即使其 base/head 拓扑类似于管理器的有序分支，也将其保持为目标本地。 `probe-error` 也保持目标局部性和变异保守性，直到后来的快照肯定地确认了管理者。 Discovery 仍然为每个PR 看护运行 — 状态不会禁用已确认的管理器检测或步骤 7 upstack 维护。

对于已确认的托管堆栈，在选择活动层之前检查管理器的有序条目一次；这是只读查看命令，不是多PR监控。在进行任何 review/CI 工作之前，请按照上表解决 **姿势**。如果姿势仍然是`target`并且所请求的中间PR有一个未解决的downstack层，则提供一次从最低的未解决的非草图层开始并向上进行（`stack-ready`），仅目标作为替代方案；不要默默地将 review/CI 工作重定向到另一个 PR。如果姿态已经是 `stack-ready` 或 `stack-land` 并且请求的 PR 有一个未解决的下栈层，则从最低的未解决的非草图层开始，而不询问（下栈到上栈）。如果所有下层都已解决，则从请求的 PR 开始。当请求的PR看起来已经准备好或稍后稳定在`target`以下时，如果需要工作，则提供一次继续立即打开的非草稿上层堆栈层（接受选择`stack-ready`以进行其余的运行）。这一一次性提议扩大了已确认的托管堆栈的PR 看护范围 - 它**不是**创建或采用 PR 堆栈的主动建议。托管托管堆栈的显式请求算作 `stack-ready` 接受，因此不要多余地请求。在无法请求的`mode:pipeline`中，仅当调用已提供`posture:stack-ready`、`posture:stack-land`或等效的堆栈范围范围时，才继续超出所请求的PR；否则返回下一个候选者作为残差。

一旦`stack-ready`或`stack-land`生效，该姿势授权依次照顾已确认的托管堆栈的每一层，而无需在每一层再次询问。保持 1 个活跃的 PR 目标和 1 个观察者。在每次转换时：重新验证管理器成员身份和有序状态，停止旧观察者，switch/check退出下一个直接层，然后使用`--continue-invocation`初始化其自己的快照状态以及第一个快照使用的标志上相同的三个记录值 - `--invocation-id "$RUN_INVOCATION_ID" --session-started-at "$RUN_STARTED_AT" --invocation-budget-seconds "$RUN_BUDGET_SECONDS"`（锚标志是`--session-started-at`，而不是`--invocation-started-at`） - 加上`--continue-dead-time-seconds <prior layer's `invocation_dead_time_seconds`>`，因此共享活动时间预算包含已在早期层中排除的挂起时间（每个层的状态目录会累积其自己的死区时间，因此如果没有此功能，新层会将先前的挂起视为活动状态） - **并在继续调用时重新声明相同的 `posture:` 值**。调用预算不会按层更新。除非用户明确包含该草稿，否则切勿跳过草稿或输入该草稿；切勿通过带有 `needs-human` 阻挡层的层。停在范围之外、人为阻挡层、堆栈末尾、预算或用户停止的初稿处。在每次跨PR转换之前重新确认`manager_status == "confirmed"`——失去肯定确认会结束堆栈范围的延续，而不是降级为手动链行为。

## 预推基线

**托管堆栈预推送基线。** 在调用可能将活动目标推送到已确认的托管堆栈中的委托之前，记录来自新`gh stack view --json`的可恢复基线：经理命令的位于目标或目标之上的打开分支（目标加上打开的依赖项）以及跟踪远程上每个分支的当前远程跟踪 OID。需要 target/current 分支有一个干净的工作树和仍然确认的经理成员资格。如果任一前提条件失败，则每种模式下的主动调用都会真正停止：不调用委托、运行另一个tick或arm/re-arm观察者；陈述残差并给出主机渲染的恢复调用。不要因为缺少原子多引用推送证明而停止——当前`gh stack push`可能会非原子地更新分支（`github/gh-stack#216`）；当安装的管理器稍后证明原子推送时，更喜欢全有或全无，但总是在推送后重新探测而不是假设它。

## 第7步：授权目标推送后的upstack维护

7. **在确认的托管堆栈中进行授权的目标头推送后，在恢复监视之前保留上堆栈。** 这是通过托管托管层隐式授权的经理拥有的维护，而不是任意历史编辑的权限。 保留委托报告的推送 SHA，重新运行只读 `gh stack view --json`，并要求它仍然标识当前本地分支上的目标 PR。 需要一个干净的工作树，从其跟踪远程获取目标分支，并验证目标的本地头和远程跟踪尖端仍然等于推送的 SHA；移动的目标将成为堆栈上的残差，这一步不会重新设置或覆盖任何内容。 从新的管理器订单中，选择紧邻目标上方的第一个打开的依赖分支。 如果没有，则不需要级联。 如果任何前提条件失败，则留下堆栈残差，而不导入、检出或猜测堆栈。 否则运行 `gh stack rebase "<first-dependent-branch>" --upstack --no-trunk --remote <tracking-remote>`，验证目标本地头在推送的 SHA 上仍保持不变，然后仅运行 `gh stack push --remote <tracking-remote>` — 绝不运行原始 `git push --force`。 从第一个依赖项开始，将目标从级联变基中排除； `--no-trunk` 将操作限制在分支间传播，并避免本地主干失效。 推送成功或拒绝后，获取并重新探测：验证目标仍然等于委托报告的推送 SHA（上面已检查）；对于基线中的每个**开放依赖**，将本地和远程跟踪头与记录的推前 OID 和预期的变基后提示进行比较 - 不要**将目标有意的推后 OID 更改视为分歧。 不要假设全有或全无。 将已经更新的依赖远端视为观察到的进度；命名第一个被拒绝或发散的依赖层，并返回精确的可恢复的上堆栈残差（修复原因后从该层重试）。 在每个当前头上重新验证经理命令、祖先、审查和 CI 之前，切勿声称堆栈已准备就绪。 如果变基冲突，立即运行`gh stack rebase --abort`并报告`needs-human`/stack-sync残差——不要在另一个PR层中决定冲突语义。 如果目标移动或租约拒绝意外的远程状态，请不要用原始力量重试；报告残差。 此步骤永远不会应用于手动依赖链，并且委派的目标修复程序永远不会执行它。

在接受的托管堆栈延续期间，有一个观察程序和一个变异目标，但观察程序会进行以下探测：为管理器顺序中的每个打开的较低层使用 `--downstack-pr <N>` 进行武装（每个 PR 重复该标志）。当较低层获得新线程、注释、失败检查或超出ARM时的状态时，它会唤醒`downstack-actionable`（与`downstack_prs`）。在该唤醒过程中，停止观察者并使用`--continue-invocation`返回到**最低**重新打开的非草稿层，处理它，级联，然后向上走。还要重新检查管理器的有序条目和每个层转换时的下堆栈静态、紧接在活动目标突变之前以及在看起来就绪的决策时。切勿同时改变两个层：下栈返回会等待当前层上任何正在进行的委托完成。如果经理确认消失，则结束延续并报告分类残差。

## 层转换和 stack-land land 步骤

**确认的托管堆栈层停止可能是运行转换。** 在 `stack-ready` 下，转换条件是静止（上表；携带任何站立残差的层不是静止的，因此行走永远不会留下红色或人为阻挡的层），而不是稳定。当活动层没有可操作的内容时，在一行中报告其状态（“静止，CI正在运行”/“准备好下一步”），重新验证管理器和下堆栈，然后前进到下一个需要工作的开放非草稿层，而无需再次询问；仅在重新确认每一层后才通过已经静止的非草案层。它的稳定窗口在下叠探针下保持运行；最终报告说明了来自新探测的每一层的 settled/quiescent 状态。在 `stack-land` 下，一旦最底部的开放层被解决，就在任何普通前进之前**运行下面的着陆步骤（当已解决的前缀仍然打开时，不要跳过合并并向上走）；仅仅静止的底层可以被走过但不能着陆。在草稿之前停止，除非用户明确将该草稿包含在范围内。在`target`下，如果没有做出继续决定，并且这是最初请求的PR，则使用步骤1的一次性报价。下降使得目标本地看起来准备好的结果成为最后一站。 `needs-human` 层仍然是活动层 - 继续观察其独立流，但不要向上推进。这些转换规则仅在新的探测器仍报告 `manager_status == "confirmed"` 时适用；独立PRs、手动链和探测错误始终使用目标本地停止。

**`stack-land` 着陆步骤（在结算/管道绿色门之后，在任何普通前进之前）。** 当姿态为 `stack-land` 并且活动层看起来已准备好（交互式结算） **或** 满足 `references/pipeline.md` 中的管道成功条件时，在管理器顺序中识别 **最底部打开的已结算** PR（CLI `gh stack merge <PR>` 通过该规则合并完整前缀） PR 原子地 — 当打算单前缀着陆时，永远不要合并上栈活动 PR，而下栈 PRs 保持打开状态）。如果需要，请读取`references/stack-commands.md`，然后运行`gh stack merge <that-PR> --yes --squash`，然后运行`gh stack sync --remote <tracking-remote>`。在将土地视为完成之前，重新探测已着陆的PR的`pr_state`/队列状态：在合并队列基础上，`gh stack merge`可能会在**入队**之后成功，而PR保持打开状态 - 继续观察PR（或返回`mode:pipeline`中的排队残差），直到它实际上为止`MERGED`；不要在仍然打开的排队前缀上推进或声明管道成功。仅当重新探测显示 `MERGED` 时，将刚刚登陆的 MERGED 视为 **托管堆栈层转换**：停止观察程序，重新探测堆栈，然后将 `--continue-invocation` 转移到下一个需要以相同姿势重述的打开的非草稿 — **不是**此PR 看护调用的运行级别终端真正停止。从外部观察到的层上的`MERGED`/`CLOSED` 可以看出，这次运行不仅仅是着陆（那些仍然是真正的终点站）。在merge/sync失败时，报告需求-人力/堆栈残差；不要回落到`gh pr merge`。在 `mode:pipeline` 和 `posture:stack-land` 中，不要**在绿色已定前缀上返回成功，直到此陆地+同步完成到实际 `MERGED`（或失败到残差）；土地过渡成功后，继续下一层的管线。
