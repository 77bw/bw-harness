# 第四步：报告/总结

通过`ce-noslop`技能写下每一个总结。以下规则是该技能添加的规则。

每一个停靠点以及每个检查点都以总结结束。在第一行下面写下它，但读起来很干净；格式是你的。重要的是它满足了这些目标，因为每个目标都针对这些摘要失败的具体方式：

- **结果第一，不可错过 - 以一个状态行打开。** 表情符号，状态，然后是从最终快照中获取的一个证据条款（安静时间，CI，剩余积压，停放残差 - 您的措辞，真实值），因此状态是可扫描的，而不是埋藏在散文中。只有状态短语是固定的：
  - `✅ 看起来已满足合并条件——<evidence>。是否合并由你决定。` — 对于已确认的托管堆栈`✅ 已可作为提交栈中的下一个 PR——<evidence>。`，对于手动依赖链`✅ 相对于其父 PR 已准备就绪——<evidence>。`
  - 当最终快照报告`update_branch_at_merge`时：`✅ Looks merge-ready — <evidence>. Update the branch when you merge; your call to merge.`
  - `🟡 Cautiously looks ready — <stalled-reviewer evidence>. Your call to merge.`

  其他停靠站也遵循相同的形状，并带有说明情况的表情符号 - `🎉 Merged`、`🚫 Closed`、`⛔ Blocked`、`⏱️ Budget exhausted`、`⏸️ Paused` 是常见的。停止运行的旧PR摄入判决以`🔧 Rework recommended — <reason>.`或`🛑 Close recommended — <reason>.`开头，然后遵循`references/intake.md`的报告顺序。除了 ✅ 或 🟡 之外，就绪声明永远不会以任何其他内容打开，并且任何其他状态都不能以这两个打开。
- **PR 在实时更新中首先声明。** 说明 PR 发生了什么变化以及剩下什么。将唤醒、快照、重新启动或磁头等检测器机制视为内部实现细节；仅当它们解释故障或所需的用户操作时才提及它们。
- **操作收据是历史性的。** 当主机要求提供所采取操作的列表（包括 `ACTIONS` 预告片）时，仅列出此刻度实际执行或观察到的突变。计划的、下一步的或待定的过渡保留在叙述中，永远不会算作行动。
- **每次真正停止时的跑步回顾。** 长达一小时的观看可以解决反馈并修复用户从未见过的CI发生的情况。 停止摘要是唯一可见工作的地方，忽略它是该技能最常见的报告失败 — 合并就绪停止仅表明当前 PR 状态（CI 绿色，无线程）已跳过此目标。 在状态行之后，用几行简短的内容回顾一下运行：反馈的内容以及它是如何解决的（按主题分组，带有计数），CI破坏了什么以及每个修复的性质（每个子句），仍然在会话上下文中的任何`prevention_signal`和`ce-debug`返回建议，推送了什么以及这些推送改变了多少差异（`git diff --shortstat`从运行的第一个推送提交的父级到最后一个头），手表运行了多长时间，以及剩余的停放位置。 测试：读者无需向后滚动即可决定是否合并并解释PR的旅程。 单纯的计数失败了——“解决了 11 个线程”，而没有告诉用户任何相关信息——相反的极端情况，每个线程或每个检查的记录也是如此。 从会话上下文中幸存的内容构建回顾，从 PR 自己的远程记录验证和填补空白 - 已解决的审查线程、PR 的提交列表、检查运行、通过 `gh` - 加上状态目录的停放项目和快照的运行时间；绝不能仅凭对话记忆。 长时间的监视通常比看到其早期轮次的上下文寿命更长，并且状态目录故意忘记已处理的工作（已解析的线程离开提取，新的头清除已分派的检查），因此 PR 的远程记录是运行实际执行的操作的持久源。 如果手表没有任何变化，有一行文字会这么说。
- **升级是突出且完整的。** 当规范 `needs_human_residuals` 集非空时，立即在结果行之后添加 `## Needs your decision`。将每个未更改的负载与其快照的 `human_decisions` 视图中的 `decision_id` 配对，然后渲染 `quoted_feedback`、`investigation`、`decision_reason`、每个 `options` 条目和权衡、`recommendation`（非空时）以及每个 `thread_urls` 链接。返回剩余对象不变。切勿从特定于路由的计数器或摘要派生此部分，也切勿解析所覆盖的线程。
- **链范围是明确的。** 对于托管堆栈，请说明活动层的位置、运行姿势 (`target` / `stack-ready` / `stack-land`)、是否准备好作为下一个、是否接受或拒绝堆栈范围的延续（在 `target` 下）、下一个 transition/draft/human 边界以及任何 `upstack_needs_rebase` 残差。在 `target`/`stack-ready` 下，当准备下一步且不自动合并时，打印确切的 `gh stack merge <N> --yes --squash` 命令。对于手动依赖链，命名 parent/dependent PRs 并限定相对于父级的准备情况。永远不要暗示目标本地的成功使整个链条健康。
- **浮出判断调用，而不是例行修复。** 如果循环（通过其代表）执行了除字面要求之外的其他操作 - 与审查者建议的修复方式不同，反馈被拒绝或反驳为错误，或者调用人工引导的中循环 - 将其命名为带有*为什么*的一行。一个有理智的人会想知道这些电话是代表他们打的。跳过常规的“审稿人询问，我们修复了它”的项目；这些保留在总数中。如果人为决定或明确的偏好决定了某个项目的运行方式，请说出来，以便记录显示呼叫到达的原因。如果没有做出任何非常规的决定，就不要说什么——不要制造电话来彻底检查。
- **诚实地谈论安定性。**如果看起来已经准备好了，请说明它已经安静了多久，并且您可以决定合并。切勿暗示“可以安全合并”。
- **简洁地披露停滞的审查者。** 在可识别的情况下命名审查者，否则命名观察到的信号；说明多久没有观察到额外的审阅进度，并说明审查者从未产生其正常的完成标记。将主机渲染的恢复调用作为恢复路径，并仅在存储库公开触发器时才提及已知的手动审核触发器。
- **检查点模式以恢复路径结束。**明确说明监控已暂停，并给出运行下一个滴答的确切命令。
