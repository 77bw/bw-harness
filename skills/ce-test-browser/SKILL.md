# 浏览器测试技巧

使用活动宿主中可用的最佳认可的浏览器驱动程序，在受 PR 或分支影响的页面上运行端到端浏览器测试。

**完成：** 运行以报告其发现的内容结束 - 要么是摘要，其中每条受影响的路线都标记为“通过”、“失败”或“跳过”，并且每个“跳过”都带有其原因，或者，当飞行前拦截器在任何路线可以执行之前停止测试时，拦截器以及将清除它的内容。无法到达任何一个，或者因为没有人能够到达而从摘要中删除一条路由，是此完成条件要防止的失败。

## 模式

- **手动（默认）：**用户控制开发服务器。当后备驱动程序为`agent-browser`时，询问是有头运行还是无头运行。
- **管道 (`mode:pipeline`)：** 由 LFG 或其他自动运行程序调用。跑步是无人值守的——永远不会阻止某个问题。从该技能的目录中读取`references/pipeline-orchestration.md`并遵循它；它会覆盖端口选择（步骤 4，确定开发服务器端口）、开发服务器启动（步骤 5，验证开发服务器是否正在运行）和可见性提示（步骤 6，设置可见性），在启动服务器的块内使用 `--free` 运行相同的端口脚本。

## 浏览器驱动程序政策

在第一个浏览器操作之前选择驱动程序：

1. **首选主机本机集成浏览器。** 当活动宿主可以导航本地 URL、检查渲染和交互状态、click/fill/press、捕获屏幕截图以及检查控制台错误时，请使用嵌入到活动宿主中或直接由活动宿主拥有的浏览器控制界面。单独配置的浏览器扩展或集成不是主机本机的。在浏览器工作之前加载并遵循所选功能自身的说明。
2. **否则回退到 `agent-browser`。** 在运行任何命令之前阅读 `references/agent-browser-driver.md`。
3. **不要引入第三个浏览器堆栈。** 切勿安装或替换独立的 Playwright、Puppeteer、单独配置的浏览器扩展或 MCP，或其他临时浏览器自动化。暴露在所选主机本机浏览器内的 Playwright API 仍保持主机本机；它不是独立的剧作家。

整个运行过程中使用一名驾驶员。仅当在测试第一个路由之前初始化失败时，选定的主机本机驱动程序才可能回退到`agent-browser`。测试开始后，请勿混合驱动程序会话、元素引用、屏幕截图或身份验证状态。

## 工作流程

在步骤 3 之前从该技能的目录中读取 `references/route-and-report.md`（将更改的文件映射到路由）。它携带路由映射模式、端口和服务器命令、每页检查、两个人性化的提示以及摘要格式。

1. **根据上述策略选择驱动程序**并记录下来。这还需要一个包含要测试的更改的 git 存储库。
2. **根据参数确定测试范围**：PR数字→`gh pr view [number] --json files -q '.files[].path'`； `current` 或空 → `git diff --name-only main...HEAD`；分支名称 → `git diff --name-only main...[branch]`。
3. **将更改的文件映射到路由**并构建要测试的 URL 列表。
4. **确定开发服务器端口。** `scripts/resolve-port.sh` 解析它并在 stdout 上单独打印端口：显式端口参数；否则 `package.json` dev/start 脚本中的 `--port` 标志；否则 `PORT=` 位于 `.env`、`.env.local` 或 `.env.development` 中；否则`3000`。当用户给出 `--port N` 时，或者当您的活动项目指令已在上下文中声明开发服务器端口时，传递显式端口。不要 grep 指令文件：文档、示例和故障排除中提到的散文不可靠且容易出现误报，而配置文件和 `.env` 是值得信赖的。每种模式都在需要端口的 shell 调用中运行脚本，因此端口值不必在 shell 调用之间保留或从散文中转录出来；参考给出了命令。手动模式按原样使用该端口：用户控制自己的服务器，因此不会扫描替代端口。
5. **在询问 headed/headless 问题之前验证开发服务器是否正在运行** — 没有服务器的手动运行会在此处停止，因此首先询问会浪费问题。
6. **设置可见性，然后验证根。**可见性独立于无人值守执行：
   - **主机本机集成浏览器：**保持其正常集成表面可见且无阻塞，以便用户可以在有用时查看进度。不要随着路线的变化而反复抢走焦点。这适用于手动和管道模式。
   - **`agent-browser`后备，管道模式：**无需询问即可无头运行。
   - **`agent-browser`后备，手动模式：**询问用户是否使用当前工具列表中已有的主机阻塞问题工具来运行有头或无头（按功能匹配，而不是按主机特定名称匹配）。当前工具列表中的存在证明该工具存在；永远不要调用面向用户的提问工具来发现它是否存在。如果列出了匹配的工具但已卸载，请使用主机的工具发现原语来加载该功能 - 不要搜索另一个主机的工具名称。仅当列表中没有此类工具或真正的问题调用错误时，才回退到在主持人的用户可见聊天界面上显示选项。永远不要默默地跳过这个问题。

   然后导航到`http://localhost:<port>`，捕获其渲染或交互状态，并在迭代之前确认根已服务。
7. **测试每个受影响的页面** - 导航、检查新状态、执行关键交互、捕获证据。
8. **人工验证** 当流程需要外部交互（OAuth、电子邮件、支付、短信、第三方 API）时：暂停并询问。 **管道模式不会暂停** - 将每个此类流程记录为“跳过”并注明原因并继续。
9. **通过捕获错误状态和准确的重现来处理故障**，然后询问是立即修复还是跳过。 **管道模式不询问** - 记录失败并继续。
10. **以引用文档给出的格式报告摘要**。
