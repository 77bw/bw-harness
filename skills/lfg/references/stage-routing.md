# 每阶段路由载体

载体是将阶段分配（哪个模型或宿主应执行该阶段的工作）传递给子技能的前缀字符串。填埋气有两个可路由的阶段，每个阶段都有自己的载体。该文件定义如何检测分配、如何解析其范围和强度、载体语法、有序回退情况、如何从功能请求中剥离路由，以及当 LFG 调用子技能时如何传递每个载体。

LFG 则不干涉，并且从不停止询问。它可能会问的一个问题是下面范围规则 3 中的问题，并且仅在交互式主机上。

## 什么是可路由的

解释调用对话是否表达了将管道阶段（规划或实施）分配给特定模型或工具的**语义意图。这是判断，而不是关键字或提示标记匹配：诸如“用寓言进行计划”或“使用Codex进行实施”之类的明确指令会创建一个作业，而在专题内容、引用材料、比较文本或文件名中简单提及Codex、作曲家、寓言或另一个model/harness则不会。两个管道阶段是可路由的，每个阶段都有自己的载体：

- **规划** 作为 `plan_model:<alias>` 承运人飞往 `ce-plan` 的航线。这命名了创作平面图（模型立面）的**模型**，仅此而已。别名示例：`fable`、`opus`。 LFG 无法将宿主分配传递给计划：**不支持将*宿主*范围限定为计划的分配（“使用代码进行计划”、“在光标上进行计划”）。停止并将其报告为路由载体阻塞项（阶段分配 LFG 无法传递），而不是将宿主名称编码为 `plan_model:<harness>`，`ce-plan` 无法提供服务，并且会默默地回退到会话模型。只有实施阶段才会路由到不同的宿主。
- **实现** 将 `ce-work` 作为 `implementation_engine` 对象路由（语法如下）。这命名了编写代码的宿主和模型。

## 按范围解析每个指令

1. **作用域指令** — 指令命名阶段（“计划寓言”、“实施法典”、“计划寓言、法典工作”）。将其路由到该阶段的载体。多个作用域指令可以同时解析，每个指令都有自己的阶段。
2. **无作用域指令** — 一个裸的 model/harness 分配，没有命名的阶段（“use fable”，“with codex”）。仅将其绑定到**实现阶段**；切勿将范围外的指令扩大到规划或每个阶段。在步骤 1 之前披露 LFG 开头行中已解决的绑定（例如“将实施路由到 Codex；规划保留在会话模型上。”）。
3. **无范围且真正模糊的人类存在** - 在步骤 1 之前准确提出 **一个** 预先问题以绑定阶段，然后继续进行。仅当这三个条件都成立时才询问：无作用域指令可以可信地属于多个阶段，错误绑定将付出高昂的代价，并且主机是交互式的（它公开了一个阻塞问题工具，并且不是`disable-model-invocation`/无头运行）。在`disable-model-invocation`/无头奔跑中，永远不要问；应用实施默认值并披露它。默认路径是强制性的：LFG 从调度程序、循环和嵌套协调器运行，没有用户应答，因此未解析的指令必须始终落入公开的默认路径而不是阻塞。

需求强度是从整个指令中推断出来的，不是一个字：“使用Codex来实现”是偏好强度（`prefer`）； “仅使用 Composer 进行实现”是需求强度 (`require`)，因为它的含义拒绝本机回退。

## 实现载体语法

当实现解析为一个候选者时，保留一个具有以下四个字段的瞬态 `implementation_engine` 对象：

- `mode`: `prefer` 或 `require`
- `target`：恰好是 `codex`、`claude`、`grok`、`cursor`、`composer`、`opencode`、`antigravity` 或 `pi` 之一 — **宿主**名称，绝不是型号名称
- `model`：显式模型引脚，否则`null`
- `source`：调用者可见的字符串，说明绑定来自何处，标识当前的 LFG 指令

命名没有宿主的裸 **模型** 的指令（例如“use fable”、“with opus”）是一个模型 *pin*，而不是目标：将其编码为为该模型系列提供服务的宿主，别名为 `model`。克劳德家族模型（`fable`、`opus`、`sonnet`、`haiku`）为`{"target":"claude","model":"<alias>"}`。切勿将型号名称放入`target`。如果您无法将命名模型映射到上述宿主之一，则这是路由载体阻塞项，而不是默默删除用户指令的 `null` 绑定。

当实现指令改为命名有序回退列表时，不要将其截断为标量载体（上面的单候选对象）。相反，保留整个有序分配作为当前任务实现意图，并且不传递 `implementation_engine:` 对象。当 LFG 调用 `ce-work` 时，仍然活动的当前任务分配优先于配置，并且 `ce-work` 按顺序标准化和预检候选者。这是实施阶段的背景，而不是计划内容。如果主机无法在其技能调用中保留该上下文，请使用路由载体阻塞项停止，而不是默默地丢弃后来的候选者。

## 净化产品输入

从进入规划的功能请求中删除每个路由指令，保持请求在其他方面不变。切勿将 `implementation_engine` 对象或任何已删除的指令传递给 `ce-plan`、`ce-doc-review`、`ce-code-review`、已解决的决策概要或任何计划或审查 **产品** 输入。载体是一个阶段的路由指令，而不是产品内容或已确定的产品决策。 `plan_model:<alias>` 运营商是一个例外：它是结构化路由数据，与经过净化的请求一起传递给 `ce-plan`，但从未编织到其中。不要在此处从常设配置构建载体：当阶段不存在显式绑定时，`ce-work`和`ce-plan`各自决定如何应用仍然适用的session/project意图和常设每次结帐配置。

## 通过步骤1的规划载体

当规划阶段指令得到解决时，在 `ce-plan` 调用前加上其 `plan_model:<alias>` 载体。它是请求旁边的结构化路由数据，从未融入其中，因此即使在管道模式下，`ce-plan` 的模型提升也会在所选模型上制定计划。

## 在步骤2中传递实施载体

当不存在标量瞬态载波时，包括当保留的有序当前任务分配在上下文中仍然处于活动状态时，请使用`mode:return-to-caller <plan-path-from-step-1>`。当标量载体存在时，使用精确的字符串主机形式`mode:return-to-caller implementation_engine:<compact-json> <plan-path-from-step-1>`。

将其精确的 `implementation_engine.{mode,target,model,source}` 数据序列化为紧凑的 JSON 紧跟在 `implementation_engine:` 前缀之后（例如 `implementation_engine:{"mode":"prefer","target":"codex","model":null,"source":"lfg-current-turn"}`）。这是任何主机都可以通过的可移植字符串中的结构化调用者数据，而不是计划路径或实现提示的一部分。当空载体不存在时，不传递该空载体。然后，`ce-work`解析保留的有序当前任务分配（如果存在），否则适用session/project意图和常备每次结账配置。 LFG 是一个自动的无头调用程序：它从不提示削弱需求强度路由。

可选的 `implementation_run:<safe-id>` 载体仅用于恢复。切勿将其包含在最初的第 2 步调用中。在一个证据协调恢复中，将其放置在同一发动机载体（如果存在）之后和未更改的计划路径之前：`mode:return-to-caller implementation_run:<safe-id> <plan-path-from-step-1>` 或 `mode:return-to-caller implementation_engine:<compact-json> implementation_run:<safe-id> <plan-path-from-step-1>`。安全 ID 匹配 `^[A-Za-z0-9._-]{1,128}$` 并包含至少一个非句点字符。拒绝格式错误或重复的 run/engine 载体，而不是启动工作。
