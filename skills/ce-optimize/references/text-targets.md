# 作为指令文本的目标

当 `scope.mutable` 中的文件是模型运行的指令时，请阅读此内容：技能、代理指令文件、角色或系统提示、工具描述。循环与代码相同。不同之处在于评估集的构建方式、哪些假设是移动而不是猜测、哪个模型运行什么以及如何读取满分。 `references/example-text-target-spec.yaml` 是该形状的完整规格。

## 评估集

指令文本运行的好坏取决于其评分的案例，而案例是运行保留的产物；每次实验都会重新生成文本。

- **根据发生的失败构建集合。** 每个案例记录四个字段：输入、您想要什么、出了什么问题以及产生的输出。五到十次记录的事件是文本值得优化之前的基础；在此之下，修复是收集更多失败，而不是运行循环。
- **覆盖规则：您想要保留的每条规则都需要一个没有它就会失败的案例。**优化器保留移动分数的文本并删除不移动分数的文本。没有失败案例的规则没有合理的理由存在，因此预计运行会消除或削弱它；如果这是一个缺陷，请在第 1 阶段之前添加该案例，而不是在规则消失之后添加。
- **多次覆盖每种故障模式。**见过一次的模式可以落在选择样本或保留样本中，但不能同时落在两者中，因此永远无法同时学习和确认。真实故障的综合变体对此是可以接受的；没有人观察到的合成模式不是。
- **修复跑步所需的装备。** 这些箱子位于宿主旁边的 `scope.immutable` 中。增长或编辑该集是范围更改：它结束本次运行并使用新基线开始另一次运行。

## 宿主

测量命令针对任务模型下的候选文本运行每个案例，并打印一个 JSON 对象：主要的通过率或判断分数、`cases` 映射（案例 ID 到 pass/fail），以便 `measurement.per_case` 可以报告回归，以及 `prompt_tokens` 或等效长度的诊断。一个二元PASS/FAIL法官给出案件的“出了什么问题”，因为告诉通常就足够了；只有当部分学分发生变化而候选人获胜时，评分标准才会产生成本。保留文件是选择命令从不读取的第二种情况文件。

## 模特角色

涉及两种型号，规格固定其中之一。 **任务模型**是文本在生产中运行的模型；宿主运行其下的每个箱子，并且在运行过程中不会发生变化。 **提议者**是编写每个候选者的任何内容：实验工作者或外部优化器。提议者可能比任务模型更强；由强大的模型编写并在廉价的模型下进行测量的候选者是正常的形状，并且通过这种方式发现的改进比相反更经常地带来更强的任务模型。永远不要让harness默默地使用proposer的模型来评分；这测量了错误的东西。

## 假设是优化器的移动

每个假设都是应用于当前文本的少量移动之一。将假设中的移动命名为`category`，以便摘要可以看到哪些移动已用尽。

| 移动 | 实验做什么 | 当下一步最便宜的时候 |
|---|---|---|
| `add-examples` | 插入从当前文本失败的情况中提取的标记为 input/output 对 | 失败主题命名了散文已经描述的模式，但该模型并未遵循 |
| `bootstrap-examples` | 在通过的案例上运行任务模型并保留其自己的良好输出作为示例 | 手写示例的读法与模型生成的内容不同 |
| `rewrite-from-feedback` | 重写摘要失败主题中的失败部分，作为条件而不是案例列表 | 多起案件因同一个原因而失败 |
| `shorten` | 当 `prompt_tokens` 是必需或次要目标时剪切文本 | 初级扁平，文字较长 |
| `restructure` | 移动、合并或拆分部分；更改顺序规则触发 | 一条规则在错误的位置触发，或者两条规则发生冲突 |
| `decompose` | 将一条指令拆分为调用者和在使用时加载的引用 | 始终加载的文本包含大多数运行从未达到的步骤 |
| `vote` | 让任务模型产生多个输出并按照规定的规则进行选择 | 模型可以解决的情况下，单个输出不一致 |
| `external-optimizer` | 见下文 | 优化器库可用，并且度量调用预算比一批手写候选者更便宜 |

为一个失败案例添加的规则并不是一项举措。这是失败主题存在的目的是为了防止出现这种情况：当同一部分在每个实验中不断吸收一个案例时，下一个假设是该部分的`rewrite-from-feedback`，重申案例共享的条件。

### 外部优化器作为实验

当项目安装了提示优化器库并且可以调用工具作为其指标时，一种假设可能是：针对种子文本运行优化器进行规定数量的指标调用，并将其返回的候选者作为实验的差异。然后，与任何其他差异一样，通过不可变的工具来测量候选者；优化器自己报告的分数不是测量值。仅使用宿主的选择案例运行它；坚持不懈的人保持不可见。当现在可以从项目中导入或调用该库时，该库就被视为可用；丢失的配置条目或环境变量无论如何都证明不了什么。在假设中命名库及其度量调用预算，以便摘要可以将其成本与手写的移动进行比较。当没有可用的优化器时，积压工作中不存在此移动。

## 读取分数

- **天花板是一种气味，而不是终点。** 当当前最好的分数位于选择集的最高分数时，对于现在的文本来说，评估太容易了。在`target_reached`停止，报告该集合不再区分候选人，并建议为下一次运行添加更困难或对抗性的案例。不要收紧规则或在运行中增加集合。
- **小案例集上的实际收益因噪声而损失**是提高样本或重复计数的原因，而不是降低阈值的原因。
- **长度是一个既定目标，或者没有测量。** 如果较短的文本很重要，请将 `prompt_tokens` 放入 `metric.objectives`（最小化，`role: secondary` 进行记录，`required` 使其成为保留条件）。否则不要用手惩罚长度。

## 事物居住的地方

案例文件、校准标签和宿主是`scope.immutable`中的存储库文件；它们在运行中重复使用。判断缓存、每项反馈、失败主题和利用验证记录是实验日志及其暂存目录中的运行状态。获胜的文本是 `optimize/<spec-name>` 上的差异，由一个人在总结时进行审查，就像任何其他保留的更改一样。
