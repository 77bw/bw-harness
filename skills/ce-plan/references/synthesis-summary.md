# 范围综合

**范围综合 ≠ 计划文档。** 范围综合是计划写入（阶段 5.2）作为输入使用的 scope/decisions 检查点。它显示了代理在综合时可以做出的决策：范围级别（该计划是否涵盖了完整的头脑风暴或缩小到一个子集？）、方法（扩展现有模式与引入新的抽象）、测试方法。它不会显示计划写入生成的决策：PR计数、commit/branch排序、工作量或时间估计、实施单元列表、确切的文件路径、测试命令配方。如果综合声明其中任何一个，那么它就泄露了计划编写思维，必须重新削减为范围决策。即使代理在会议早些时候形成了计划编写意见，综合仍停留在范围级别 - 用户被要求确认范围，而不是橡皮图章实施。

**两阶段形状：内部草稿，然后聊天时合成。** 合成分两个阶段组成。第一阶段是内部三桶草案（陈述/推断/超出范围），代理用于全面考虑范围。第二阶段是聊天时的输出：您对问题（单独）或头脑风暴锚点（头脑风暴来源）的理解、范围以及用户可能重定向的“呼叫”。用户只能看到第 2 阶段。内部草案仍然通过下面的文档形状路由通知计划主体；它只是没有逐字到达用户。这种分裂的存在是因为全面的审计形状产生了太多的细节，用户无法权衡。

**三桶结构是内部草案，而不是面向用户的产物。** 它在第 1 阶段进行范围思考工作，并在第 5.2 阶段编写计划时消失：规定的内容告知产品合同的要求和问题框架，成功信号告知其成功标准 - 来自已确认的交互式运行中的任一桶，仅在未确认的路径上陈述，会话解决的产品决策告知其关键决策，推断的内容告知关键技术决策/实施单位（正常交互模式）或计划合同的 `### Assumptions`（非交互模式，或交互式 `SKIP_SCOPING_CONFIRM` 跳过运行），超出范围的内容告知产品合同的范围边界。该计划没有并行的 `## Synthesis` 部分 - 只有阶段 2 摘要嵌入在产品合同的 `### Summary` 下。有关确切的布线和节嵌套，请参阅下面的“确认后的文档形状”。

当综合摘要阶段在 ce-plan 运行时加载此内容。有两种变体——它们具有相同的结构，但时间安排和内容重点不同：

- **单独变体**（阶段 0.7，单独模式范围综合）：在阶段 0.4 引导和阶段 0.6 深度分类之后运行，在阶段 1 研究开始之前。在使用子代理调度之前捕获范围误解。全宽度——问题框架、预期行为、成功标准、in/out范围。
- **源自头脑风暴的变体**（第 5.1.5 阶段，源自头脑风暴的范围综合）：在第 1 阶段研究之后、第 5.2 阶段计划编写之前运行。重点关注计划时决策（接触哪些files/modules、扩展哪些模式与引入新模式、测试范围、重构范围）。集思广益验证假设的内容，而不是重新陈述。

两种变体共享两阶段形状、标注规则、软剪切行为和文档形状路由。在非交互（无头）模式下，两者都构成内部草稿并跳过第 2 阶段——当没有同步用户时，面向用户的压缩是没有意义的。内部草案以同样的方式融入计划主体，推断投注路由至 `## Assumptions` 部分。有关完整路由，请参阅下面的“无头模式（共享）”。

---

## 第一阶段：内部三斗吃水（共享）

内部草稿由三个带标签的桶构成。当有意义时，项目可能会出现在两个存储桶中 - 将包含然后排除标记为推断，以便捕获推理。

- **陈述** - 用户直接所说的内容（在原始提示、先前对话、对话答案或上游头脑风暴文档（如果存在）中）。这里的项目有明确的用户语言锚点。
- **推断** — 代理假设可以填补空白。用户从未明确命名的范围边界，成功标准是从意图和技术假设中推断出来的，因为简短的采访没有探究它们。推断列表是最具可操作性的存储桶 - 这里的项目是用户可以纠正的代理的赌注。
- **超出范围** — 故意排除的项目。代理考虑过但决定不包括的相邻工作、重构、必备品、未来工作项目。

会话解决的决策是**有出处的**，从不推断——用户的对话行为根据定义来锚定它们。将每个项目与其类别和被拒绝的替代方案一起放入指定的桶中。

该草案是内部草案。不要将其逐字粘贴到聊天中。将其作为一个思考步骤，然后从中导出阶段 2。

---

## 第 2 阶段：聊天时间范围综合

第二阶段是用户实际看到的。它的工作是让用户一读就检查你是否理解他们，以及他们在研究或计划编写之前可能想要更改哪些调用。根据你的理解，用你自己的话写出来。展示你的理解和假设，而不是用户所说的；对提示、头脑风暴或用户答案的重述显示的是回忆而不是理解。

### 独奏形状（阶段 0.7）

没有上游文档，因此综合是对您认为用户想要的内容的唯一检查。单人跑步通常很少有对话，因此你对球门的想象是跑步中测试最少的部分。

1. **问题** — 1-2 句话，作为散文：什么是错的或想要的，它影响谁，为什么它现在很重要，以及完成后会发生什么。陈述请求背后的目标，而不是改写请求。当用户从未说出原因时，请说出您的推断，以便他们可以纠正。
2. **范围声明**——在用户可以确认或重定向的级别上阐述计划的目标和不目标。描述计划的整体目标，而不是后面列出的要求的功能；用户在摄入期间给出的答案将作为描述的一部分显示在此处。
3. **继续进行**和**标注**，如下。

### 头脑风暴得出的形状（阶段 5.1.5）

头脑风暴已经确认了问题和内容；不要重述它们。展示头脑风暴中未做出的决定。

1. **锚** - 用自己的词汇命名头脑风暴范围的一句话，这样读者几天后就知道该计划针对的是哪个产物。
2. **特定于计划的范围** - 计划是否涵盖完整的头脑风暴或子集，哪些相邻的重构在其中或不在，以及场景级别的测试范围。当计划涵盖所有内容且没有添加任何内容时，请用一句话说出来。
3. **继续进行**和**标注**，如下。

### 共享规则

- **结转：** 从该技能开始之前（调用对话或通过的简报）开始，每个会话解决的决策一行：决策、类别以及选择的内容。这些只是陈述，而非呼吁；用户已经关闭的分叉不是分叉。该技能本身的问题中给出的答案没有线路，并且用户在上游头脑风暴中已记录的决策也没有线路。
- **调用**是另一个合理的代理可能做出不同的调用，并且用户现在可以便宜地纠正：真正的分叉方法，改变计划内容的不明显的默认值，不明显的排除，或者现在修复成本低廉但在研究或制定计划后成本昂贵的赌注。如果没有标题，则省略标题。
- 忽略用户在不阅读代码的情况下无法判断的任何内容，以及计划编写产生的任何内容：实施单元列表、PR计数或排序、估计、行号、方法签名、数据形状、确切名称、错误措辞和测试命令。单独的合成停留在产品级别。仅当决定选择某个模块或模式时，来自头脑风暴的综合可能会命名该模块或模式。根据每个决策对用户获得的效果的影响来命名，而不是根据其机制（“重新运行不能对发票收取两次费用”，而不是“幂等性密钥”）。名称要求和示例应使用简单的文字，切勿使用裸露的 ID（`R3`、`AE2`）。忽略没有真正替代方案的机械选择，仅证明完整性（“涵盖所有九个要求”）以及摘要中已经说明的任何内容。
- 将每个项目符号保留为合作者会大声说出的一个句子，没有嵌套的项目符号。仅包括用户需要了解的内容来判断计划的目标是否正确：您对问题和范围（单独）或计划特定范围（集思广益）的理解，以及如果错误则可能改变计划的决策或假设。其他一切都属于计划。更大的范围意味着在更高的级别上命名这些决策，而不是添加行。没有任何内容超出综合：没有流程叙述、回购调查结果、方法推介、文件列表或基本原理块。
- 当会议已经掌握了详细材料（研究、代码、早期计划）时，预计内部草案会在第二阶段之前过度共享和压缩。更多上下文意味着要压缩更多内容，而不是要展示更多内容。
- 如果某个问题确实不能被默认，请在提出综合之前解决它。切勿在综合报告旁边附带开放性问题。
- 通过`ce-noslop`技能写综合。要求确认是开放式的，没有 `AskUserQuestion` 菜单（交互规则 5(a)）。

### 确认行

独奏，以“根据您的要求”开头（仅当第 0.4 阶段实际提出澄清问题时才添加“以及我们的简短讨论”）：

```
根据您的要求，我建议规划的范围如下：

**The problem:** ...
**Scope:** ...
**Carrying forward:** ...
**Call outs:**
- ...

确认后，我将利用这个范围继续研究。 （如果这比你最初想象的要大，你也可以重定向到 `ce-brainstorm` — 我会在这里停下来为你加载它。）
```

头脑风暴来源：

```
头脑风暴范围[一句话锚]。本计划[计划特定范围]。

**Carrying forward:** ...
**Call outs:**
- ...

确认后，我将根据头脑风暴、研究和综合来编写接下来的计划。
```

例如，单独请求添加一项对逾期发票收费的夜间作业：

```
根据您的要求，我建议规划的范围如下：

**问题：**有人每天早上都要手工收取逾期发票。我们的目标是在不向客户收取错误费用的情况下收回时间。

**范围：** 无人值守的夜间运行，对每张逾期发票的保存卡进行收费，并仅在成功时将其标记为已付款。此计划中没有重试、客户电子邮件或管理 UI。

**Call outs:**
- 失败的指控将留给团队跟进，我将列出一份早晨清单，列出失败的内容及其原因
- 我将“一张发票绝不收取两次费用”视为一项硬性要求，包括重试运行时

确认后，我将利用这个范围继续研究。
```

## 何时跳过阻塞确认

自动继续路径（无需等待用户确认即可宣布）仅在**计划深度为轻量级且没有标注**时适用。对于标准或深度计划，即使没有呼叫，也始终要求确认 - 计划的实质内容是需要检查点的内容，而不是之前有多少对话。一个包含丰富的无声决策和 1-3 行摘要的深度计划正是最有可能橡皮图章的情况；明确的确认请求为用户提供了在研究或计划编写继续进行之前进行推迟的真正机会。

当应用自动继续时（轻量级+零呼叫），将此公告作为聊天消息发送给用户，然后继续。在你的推理中做出决定并不是发送它；而是在发送它。不允许静默进行，并且原因（没有值得标记的分叉）必须可见：

```
规划：【1-3行总结】

没有公开的决定可供权衡——继续[研究/制定计划]。如果我的范围错误请打断。
```

对于没有标注的Standard/Deep，确认线仍然适用； “Callouts:”标题被简单地省略。用户获得摘要以及明确的确认请求。

还有第三个跳过条件：**选择加入 `SKIP_SCOPING_CONFIRM` 设置**（阶段 0.0 — `confirm:auto` 令牌或 `plan_skip_scoping_confirm` 配置密钥）。当它决定跳过时，将自动进行*任何*层或呼出计数的确认 - 用户已对其进行预授权。该公告仍然是强制性的（它指出确认已关闭并且推断范围落在`## Assumptions`），并且跳过的范围仅限于此确认：真正的阻塞问题和阶段 5.4 菜单仍然运行。这与无头模式的不同之处仅在于该公告 - 无头模式没有同步用户可以公告。

当选择加入跳过适用时，以相同的方式发送此公告 - **不是**上面的自动继续模板。选择加入跳过适用于*任何*层和呼出计数，因此只要呼出幸存，声称“没有公开的决定可以权衡”将是错误的；相反，该公告指出确认已关闭，并且推断范围记录在`## Assumptions`下：

```
规划：[1-3行范围索赔]

范围确认已关闭，因此我无需等待即可继续[研究/计划编写]。推断的范围记录在计划中的假设下——如果我错了就中断。
```

## 修订循环（共享）

**修订不是确认。** 在任何用户修订（即使是简单理解的交换）之后，整合更改，重新呈现修订后的第 2 阶段以及反映的更改，并在编写计划之前等待明确的确认。循环是：

1. 当前阶段 2 → 用户响应
2. 用户确认→编写计划
3. 用户修改→整合，重新呈现修改后的阶段2，返回步骤1

计划写入（阶段 5.2）仅在明确确认后或软切阻止问题的“继续”选项后运行。切勿在修订后立即编写，即使修订足够小，以至于代理认为已理解 - 确认步骤才是使综合得到**确认**的原因，而不是“代理的最后提案”。

## Solo 变体（阶段 0.7）

仅在以下情况下运行：
- 0.2 阶段发现没有上游头脑风暴文档
- 并且阶段 0.4 留在ce-plan（未路由至ce-debug、ce-work或通用规划）
- AND 阶段 0.5 已清除（没有未解决的阻碍）
- 并且不在阶段 0.1 快速路径上（恢复正常，深化意图）

每个守卫都是 `references/intake.md` 中的显式条件，而不是隐式的。单独变体不会在 resume/deepen 路径、将任务交给其他技能的路径或头脑风暴来源的路径上运行。

**内容重点**：全幅内部草案。阶段 0.4 引导程序在设计上很简短（“提出一两个澄清问题”），因此代理在阶段 0.7 运行之前已经做出了实质性推论。内部草案中的推断桶在这里最重要——代理人的赌注是最广泛的。大多数推论不应传达给用户；仅显示他们可以有意义地重定向的分叉。

**针对丰富上下文调用的反警告。**当推理源*不*只是阶段 0.4 引导程序时（例如，先前的对话中验证代理、同一会话中较早完成的同级工作单元或对话中已有的规划产物），人们会倾向于将该材料逐字转储到标注中。已在上游验证的赌注是**规定**（内部），而不是推断（内部）；无论上游上下文提供了多少细节，其细节属于计划主体的赌注都会在调用中的决策级别命名。如果最近的轮次产生了详细的代码、文件路径或研究产物，则预计内部草案会在第 2 阶段之前过度共享和主动压缩。会话解决的决策是已验证内容的最强形式 - 将其作为 `Carrying forward:` 行继续前进，永远不要重新询问它。

**为什么要预研究，而不是预写**：如果范围错误，研究工作就会被浪费。在子代理调度之前捕获范围错误（第 1.1 阶段的 repo-research-analyst、learnings-researcher 等）可以节省令牌和时间成本。

## 头脑风暴衍生的变体（阶段 5.1.5）

仅在以下情况下运行：
- 阶段 0.2 找到上游头脑风暴文档（头脑风暴来源的调用）
- 并且不在阶段 0.1 快速路径上

**内容重点**：仅限计划时决策。头脑风暴及其综合已经验证了要构建什么；内部草案和第二阶段显示了计划将如何执行这项工作——头脑风暴没有做出的决定。

内部草案中应包含的项目：
- **Files/modules 触摸（而不是触摸）** — 实现的内容
- **扩展模式与引入新模式** - 代理在确认的范围内做出的架构决策（报告代理的走向；都不赞成）
- **测试范围** — 哪些现有但未经测试的代码是本工作测试范围的 in/out
- **重构范围** - 相邻的清理（如果有的话），将延迟项目与活动差异进行比较
- **跨领域影响** - 涉及到的身份验证、迁移、共享类型

其中大部分不应成为单独的标注。仅显示另一个合理的代理可能会做出不同选择的分叉，并且用户现在可以廉价地进行纠正。

**从产品合同中读取，而不是综合部分**：上游产物是仅需求的统一计划（`product_contract_source: ce-brainstorm`），而不是单独的头脑风暴文档，并且它没有`## Synthesis`部分（综合是ce-brainstorm中的聊天时间产物；只有散文摘要嵌入在产品合同下）。第 5.1.5 阶段从产品合同的各部分（摘要、问题框架、要求、关键流程、范围边界）以及第 1 阶段的研究中得出计划时决策。旧版独立需求文档 (`origin: docs/brainstorms/...`) 和可能带有旧版 `## Synthesis` 部分的旧版头脑风暴仍然有效；该内容被视为补充性内容，而不是权威性内容，其中产品合同/正文部分优先。

**为什么要预写，而不是预研究**：头脑风暴文档及其综合已经验证了内容，因此研究具有明确的针对性。计划时决策是在研究和构建（阶段 1-4）期间出现的，因此预写会在最近的便宜时刻捕获它们 - 在阶段 5.2 将计划提交到磁盘之前。

## 圆度软切削（共享）

跟踪用户每轮触摸的标注。 **仅当相同的标注被修改两次**时才会询问软剪切阻止问题（或者第三轮修订针对已在第二轮中修改的标注）。各轮的新召集修订不受限制地进行。

**各轮之间的同一性取决于决策维度，而不是表面措辞。**修订可能会导致第 2 阶段重新推导 - 相同的底层分叉可能会重新措辞、与另一个标注合并或分成两个。 “相同的标注”意味着做出相同的决定（例如，“扫描在哪里运行”仍然是一个决定，无论其措辞是“促进扫描工作目录快照”还是“扫描目标：预复制工作目录”）。当重新剪切将多个先前的标注折叠成一个时，新的组合标注将继承其任何组成部分的“触及”状态 - 软剪切问题被问到是否有任何这些基本决策之前已经修改过一次。

当软切问题到期时，使用当前工具列表中已有的主机阻止问题工具（按功能匹配，而不是按主机特定名称匹配），有两个选项：

- `Proceed and continue to [research / plan-write]`
- `暂缓下一步，继续讨论`

出现在列表中就是证据；永远不要调用面向用户的提问工具来发现它是否存在。仅当列表中没有此类工具或真正的问题调用错误时，才回退到主持人的用户可见聊天界面上的编号列表。永远不要默默地跳过。

## 无头模式（共享）

当从自动化工作流程（例如 LFG 或任何 `disable-model-invocation` 上下文）调用技能时，技能以非交互模式运行（无同步用户）。该产物由下游技能（ce-doc-review、ce-work）和人工审查者（PR 审阅）读取。

**第 2 阶段在无头模式下没有实际意义。** 像往常一样编写内部草稿（第 1 阶段），但跳过聊天时间压缩 - 没有同步用户需要确认，没有呼出要派生，没有自动进行公告。通过下面的文档形状表将内部草案直接路由到计划正文中。

**每个变体的行为**（时间对于接下来的阶段很重要）：

- **单独变体（阶段 0.7）**：*在*研究之前运行。撰写内部草案并继续正常进行第一阶段研究。推断的内容一直保留到计划写入（阶段 5.2），在此路由到 `## Assumptions`。
- **源自头脑风暴的变体（阶段 5.1.5）**：在研究*之后、编写计划之前运行。撰写内部草案并进入阶段 5.2 计划编写。推断的内容路由至`## Assumptions`。

**两个变体的共同行为：**

- **无用户提示；无第 2 阶段；没有自动继续公告。** 这三个都没有实际意义。
- **使用模式感知形状路由内部草稿内容**（嵌套在 `ce-unified-plan/v1` 产物中的产品合同/规划合同下；旧版独立计划中的顶级 `##` 标题）：
  - **规定的**内容→产品合同`### Requirements`（用户规定的约束，在存在时追溯到来源的R-ID），以及相关的叙述上下文`### Problem Frame`
  - **成功信号 — 仅在这些路径上说明** → 产品合同 `### Success Criteria`（当其目录条目适用时）。 *推断的*成功信号不会出现在这里：这些路径从未确认过它，因此它与其他未经验证的赌注一起保持在 `### Assumptions` 以下。
  - **超出范围**内容 → 产品合同 `### Scope Boundaries`
  - **推断**内容 → 规划合同 `### Assumptions` — 明确标记为未经验证的代理赌注。不要将推断的项目纳入关键技术决策或实施单元；这将使未经验证的投注与用户确认的决定无法区分。
  - **会议解决的决策**（包括来自通过的简报的决策）→ 解决的产品决策路由至其标记的产品合同关键决策，并具有确切的 `Governs R…` 链接；已解决的planning/how决策将路由至标记的关键技术决策。两者都不属于`### Assumptions`——它们是用户确认的； `### Assumptions` 规则仅适用于代理推断的投注。未能通过结算测试的简短条目（无法说明其被拒绝的替代方案）将降级为指令或开放区域。

`### Assumptions` 部分出现在非交互式计划和用户选择 `SKIP_SCOPING_CONFIRM` 的交互式计划中 — 两种情况都会在不确认推断赌注的情况下进行，因此这些赌注必须保持明显的标签。正常的交互式计划不需要它（推断的赌注要么通过标注得到用户纠正，并成为关键技术决策，被修改掉，要么被判断不值得标注并默默地分解到实施单元中）。

**在正常的交互计划中，两个推断项目不受静默溶解**的影响，由上面存储桶自己的词汇命名：*从意图推断的成功标准*，以及*用户从未明确命名的范围边界*。两者都会路由到其产品合同部分 - `### Success Criteria` 和 `### Scope Boundaries` - 无论它们是否成为标注。呼出规则决定用户被询问的内容；它不决定产品范围是否达到该文件。所有其他推断项目都保留上述溶解行为。

豁免范围仅限于已确认的交互路径，并且**不适用于**无头或`SKIP_SCOPING_CONFIRM`运行。这些在不确认任何推断赌注的情况下进行，因此 `### Assumptions` 规则管辖其中的每一个 - 未经验证的猜测必须保留在那里标记，而不是显示为未标记的产品声明。

这恢复了原始设计预期的审计可见性（未经验证的投注不得作为权威内容传播），但将它们显示在自己的标签下，而不是隐藏它们。下游审核（ce-doc-review、ce-work、人工PR审核）可以专门审查假设。

## 自重定向（共享）

如果用户响应表明他们的技能错误或想要不同的工作流程：

- **单独变体**：常见的重定向包括“这比我想象的要大——让我先集思广益”（建议`ce-brainstorm`），“这只是一个修复，不需要计划”（建议`ce-work`），或“我需要先调查”（建议`ce-debug`）。
- **源自头脑风暴的变体**：不太常见，但有可能 - “实际上这个范围是错误的，将其带回头脑风暴”（建议 `ce-brainstorm` 修改上游文档）。

无论哪种情况：停止ce-plan，建议替代技能，提供在会话中加载它。不要反驳或争论——用户的重定向信号是经过深思熟虑的选择。

## 确认后的文档形状

用户确认后（或软切割决策进行后），阶段 5.2 编写计划文档。内部草案不作为`## Synthesis`部分纳入计划。仅嵌入第 2 阶段范围摘要，位于产品合同的`### Summary`下；已确认的单独问题陈述锚定`### Problem Frame`。内部草案内容融入到统一计划的各个部分中。在 `ce-unified-plan/v1` 产物中，这些目标是嵌套的 — 摘要、问题框架、需求和范围边界位于 `## Product Contract` 下；关键技术决策和假设位于 `## Planning Contract` 下；实施单位是它自己的顶级部分。 （没有 `artifact_contract` 的旧版独立计划将它们保留为顶级 `##` 标题。）

| 内拔模元件 | 它在统一计划中的位置 |
|---|---|
| 总结（第二阶段） | 产品合同`### Summary`（1-3行散文，前瞻性）——如果聊天时间摘要使用项目符号，则重写计划约定。单独变体：目标范围。集思广益：实施方法 |
| 问题（单独，已确认） | 产品合同 `### Problem Frame` — 已确认的问题锚定了该部分的叙述，是扩展而不是复制 |
| 指定项目符号 | 产品合同 `### Requirements` (R-ID) 以及与叙述上下文相关的`### Problem Frame` |
| 推断子弹 | 当赌注驱动结构性选择时，规划合同`### Key Technical Decisions`（带有理由）和实施单位。在非交互模式**或交互`SKIP_SCOPING_CONFIRM`跳过运行**，转至规划合同`### Assumptions` — 两者都在不确认投注的情况下继续进行，因此它们必须保持标记；请参阅上面的无头模式。 |
| 超出范围的子弹 | 产品合同 `### Scope Boundaries` — 包括相关的 `#### Deferred to Follow-Up Work` 小节 |
| 成功信号 | 产品合同 `### Success Criteria` 当其目录条目适用时 - 质量、指标或交接信号要求尚未包含。此行**覆盖**这些项目的通用规定行和推断行：成功信号在此处路由*而不是*，从不另外。始终发出信号。仅在已确认的交互式运行中出现**推断**信号；在 `SKIP_SCOPING_CONFIRM` 跳过运行中，它会与其他未确认的投注一起进入 `### Assumptions`，与上面的推断行路由它们完全相同。 |
| 会议确定的产品决策 | 产品合同`### Key Decisions`，带有`session-settled:`注释和确切的`Governs R…`链接。已解决的planning/how决策将转至`### Key Technical Decisions` |

没有斜体捕获上下文注释（例如，“在第 0.7 阶段捕获...”）。它将工程过程泄漏到读者不需要该信号的产物中。

产品合同的`### Summary`和`### Problem Frame`必须服务于不同的目的：摘要回答“这个计划提出了什么？” （前瞻性，1-3行）；问题框架回答“为什么这个提案存在？” （向后看，段落）。不要在问题框架中重述提案；不要用情境背景来填充摘要。
