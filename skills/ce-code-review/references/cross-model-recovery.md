# 跨模型对抗通行证：恢复分支

仅从发送到此处的分支中阅读此内容：阶段 3d 的无作业 id 启动失败 (`references/select-and-route.md`)，或当运行程序的退出代码或作业的最终状态表明对等方没有生成可用产物时，在`references/cross-model-review.md`步骤 5 中折叠读取。其对等方启动并折叠的运行永远不会打开此文件。下面的每个分支都决定一件事：对手的镜头是否仍然被覆盖，以及被什么覆盖。

## 需要做出决定的结果

- **调度基础设施故障** — 运行程序或工作线程本身崩溃：任何作业开始之前的非零退出、preflight/detach 失败或未解析的 `$SKILL_DIR`/脚本路径。 这与上面的条件未满足跳过不同，上面没有尝试调度，因此不要在第一个错误时将其折叠到干净的未运行存储桶中。 两种故障形状在不同点恢复。 在本地花名册最终确定之前，**无作业 ID** 预检失败（在任何作业 ID 之前退出，未解析 `$SKILL_DIR`）在 **阶段 3d 的无作业分支** 完全恢复。 这是重新运行启动仍然可以恢复跨模型验证的唯一点，如果失败，则干净地回退到进程内审核器，然后由该审核器覆盖镜头；只丢失了佐证。 **不要**在折叠时重新尝试这种情况：第 4 阶段可能已经调度了进程内 `adversarial-reviewer`，因此折叠对等重新运行会将两者放在同一个简报上，并且只有其中一个可以运行它。 此步骤仅处理 **job-id-returned-then-failed** 崩溃；它的失败工作在这里得到了收获，而正在进行的审查者已经走了。 为此，手动重新运行**相同的已解析固定路线**，保持目标和模型、`git diff <base-ref>`读取范围以及固定的对抗角色简介。 当每一次故障都是新的、似乎可以恢复的故障并且共享对等截止日期有效时，继续重试。 这是同路由重试，故意与下面的配额规则区分开来，后者需要新公开的路由。 一旦失败重复发生或超过最后期限，就停止。 手部恢复是对手镜头的唯一覆盖，因此覆盖线必须将对手镜头报告为**降级**，而不仅仅是跨模型验证丢失。 手动恢复不得替代不同的目标或提供者、扩大读取范围或放宽只读信任边界；这些使得恢复的对等体不值得信任，而不仅仅是无法获得。
- **出门前交通不可用** — `out.log` 载有 `transport unavailable (pre-egress, <scope>): <reason>`。对等点没有运行，并且没有审阅的内容到达提供者，因此这绝不是“对等点运行，没有可用的输出”；由于这个原因，覆盖率报告跨模型对等点未运行。范围 `shared`（Node、`npx` 或 acpx 的 npm 获取）以相同的方式在每条路线上失败，因此没有替代节点可以覆盖镜头：采取未运行回退的步骤 2。范围 `route`（该路由的 CLI 丢失，acpx 配置文件替换了其启动命令，或者适配器拒绝了模型，并列出了可用模型）仅影响该路由。被拒绝的模型遵循下面的拒绝模型规则；任何其他路线原因都会运行未运行的回退，这允许其进行一次替换。
- **未由工作人员证明的主机系列** — `out.log` 带有 `host serving family unattested`：工作人员在任何出口之前跳过，因为它无法证明主机的服务系列（在 omp 下，名为 no 第一方模型的会话文件，或另一个宿主的标记显示该文件属于父会话）。没有其他收件人更改这一点，因此直接执行未运行后备的步骤 2，原因在覆盖范围中。
- **运行但没有产生可用的输出** — 作业达到 `done`（或任何最终状态），但不存在 `adversarial-<provider>.json`。对等方运行并接收了内容，但在模式形状中没有返回任何内容：无法解析的输出，或脚本删除的空结果。这与未运行不同：请注意面向人类的Markdown覆盖率中的“跨模型传递：同行运行，没有可用的输出”。决不让审核失败。当下面的诊断分类证明这是未经审查的结果时，请在将镜头视为已覆盖之前运行未运行的回退。
- **开始但不是`done`** - 最终状态读取报告`failed`、`timeout`或`died-without-result`（在共享截止日期记录`timeout`收获的作业，在其原因中注明收获）→仍然非阻塞，但从不沉默：在覆盖范围中命名对等点及其最终状态（例如“跨模型对抗对等点：超时”）。从未开始的传递不会获得最终状态线；据报告未运行。当下面的诊断分类证明这是一个未经审查的结果时，请运行未运行的后备，而不是让镜头未被覆盖。
- **删除前对跳过原因进行分类。**清理前读取`out.log`，包括前缀为`peer skip evidence:`的有界行。判断全面诊断；不要 grep 查找封闭短语列表。仅在启动上下文或提供者响应明确建立了提供者支持的调度后，才归因于帐户身份验证失败；然后报告观察到的故障和登录或凭据刷新修复。如果没有该证据，登录形状的对等文本仅描述对等点的执行上下文：沙箱主机会产生与真正注销相同的信号，因此切勿将其报告为用户帐户正在注销或提示登录命令。
  - 任何身份验证形式的失败：对等方没有审查，无论解释是凭证归因的还是仅执行上下文的。归因改变了解释，而不是覆盖范围；运行未运行的后备。
  - 暂时的提供程序容量或速率限制故障：在步骤 1 的过载条件下，工作线程独占一次相同路由重试（在其适配器报告提供程序过载后，HTTP 529，工作线程单独重试一次）。一旦提供商未审核结果到达主机，则调度进程内`adversarial-reviewer`；主机永远不会重新启动该对等点。不要运行未运行的后备或切换收件人。
  - 最大周转耗尽：调度进程内`adversarial-reviewer`。不要重试对等方或切换收件人。
  - 请求的模型本身被拒绝：适配器没有提供它，或者提供者为此帐户拒绝了它（`peer skip evidence (reply):`携带提供者作为回复文本发送的拒绝）。只是模型失败了；该路线仍然可用。如果工作人员运行自己的默认模型，因为用户没有配置或命名任何模型，则使用镜头的一个替代品来替代同一路线上的新工作。为其提供最接近的同族模型，当该行存在时从 `peer skip evidence (advertised models):` 中选取，并将其绑定为 `references/cross-model-review.md` 中描述的同族替换段落。如果该作业也以未审核结果结束，请执行未运行后备的步骤 2。覆盖率表明哪种模型被拒绝，用户可以将 `cross_model_model` 设置为有效的模型。配置的或用户命名的模型永远不会被交换；运行未运行的后备。
  - 显示对等方从未审查过差异的任何其他诊断：它达到了会话或使用配额，或者在审查之前其 CLI 失败，例如拒绝其安装版本不支持的选项。不要重试该路线；运行未运行的后备。
  - 其他任何内容，包括无法显示同行是否审查的诊断：列出观察到的故障；不运行未运行的后备。
- **未运行后备**（第一个未经审查的结果，包括第一个）：开始的工作没有涵盖对抗性镜头。不要重试同一条路线。然后：
  1. 如果这是第一次替换尝试，则失败的收件人**不是**明确的用户声明的首选项（步骤 1 第 1 项），并且另一个已证明的不同已安装 + 允许列表目标仍然存在：宣布新收件人并使用新的 `CROSS_MODEL_FIXED_ROUTE` 启动新作业。等待剩余的共享截止日期，并以与第一项工作相同的方式折叠其产物。这项工作现在涵盖了镜头。切勿在工作人员内部切换接收者。如果此替换也以无审核结果告终，则不要启动第三个对等点；执行步骤 2。
  2. 否则（明确的接收者，或没有其他符合条件的对等方）：立即调度进程内`adversarial-reviewer`。 Coverage 将对等点记录为未运行，并带有观察到的原因，并以这种形式命名覆盖：`adversarial lens: in-process fallback (cross-model peer not run: <reason>)`，匹配`peer.outcome: in-process-fallback`。永远不要在这里写`harness-native fallback`：该短语是`ce-work`的船门信号，用于根本没有`ce-code-review`运行的评论，并且重复使用它会使完整的评论读作被跳过的评论。配置或默认选择不是用户明确声明的首选项。仅更换一件；永远不要默默地继续向另一个收件人发送信息。

## 信任边界（维护者）

同行根据`git diff <base-ref>`审查**当前工作树**。已审核的 code/diff 内容将发送到外部模型提供商（OpenAI、Anthropic、xAI、Google 或 Cursor，具体取决于已解析的对等方）。 `CROSS_MODEL_PEERS` 限制哪些提供商可以接收内容。

**隔离在设计上与 ce-doc-review 不同。** Doc-review 嵌入一个独立的文档并拒绝来自空工作区的所有权限。代码审查需要周围的代码上下文，因此对等点在树中运行：每条路由都从存储库根通过 acpx（代理客户端协议客户端，需要带有 `npx` 的节点 22.13 或更高版本）运行，并且 acpx 不向其传递任何 MCP 服务器。 acpx 批准对等方的读取和搜索请求，并拒绝所有其他权限请求，并且每个适配器都以其只读模式运行。仅当代理在使用前请求许可时才会删除该工具，因此路由在对等方仍然可以执行的操作方面有所不同：

| 路线 | 读取存储库外部，包括分阶段的大差异 | 未经许可仍可使用工具 |
|---|---|---|
| `claude` | 允许（读取权限，acpx 批准） | 阅读和搜索；只读 shell 命令，例如 `git diff`。 Web 工具被拒绝 |
| `codex` | 允许 | 读取任何地方和 shell 命令，包括写入：其适配器不强制执行只读模式 |
| `grok-cursor`, `cursor`, `composer` | 允许 | 随时随地阅读和搜索 |
| `grok-cli` | 小差异：拒绝（它通过 acpx 读取，它拒绝存储库外部的路径）。 Large diff：允许，通过自带的读取工具 | 读取存储库内部； Web 获取和 Web 搜索，其 ACP 服务器无法禁用。在大的差异上，它自己的工具也无需询问即可编写 |
| `opencode` | 允许（其配置允许外部目录读取） | 随时随地阅读；编辑、网络和子代理在其配置中被拒绝 |
| `antigravity` | 允许（读取权限，acpx 批准） | 阅读和搜索。 Shell 命令和编辑需要许可，但会被拒绝。它仅从其私有的每次运行主目录以及存储库的 `.agents/skills` 和 `.gemini/skills` 加载技能 |
| `pi` | 允许（自带读取工具，无需权限） | 随时随地读取、搜索和列出文件。 Pi 不请求许可，因此其启动器仅启用这些工具并关闭 MCP；存储库的 Pi 设置、扩展和技能不会加载 |

对于太大而无法内联的 diff，每个路由都会获取暂存 diff 的私有路径，而不是 diff。 `grok-cli` 然后使用它自己的文件工具运行，因为 acpx 的文件访问拒绝该路径。 Claude 以安全模式启动，OpenCode 使用 `OPENCODE_DISABLE_PROJECT_CONFIG=1`，因此所审查的存储库的 Claude 设置和挂钩及其 `.opencode/{plugin,agent}` 不会加载。最糟糕的情况是泄露已审查的内容，除了在 Codex 路线上，以及在具有较大差异的 `grok-cli` 上，同行也可以更改文件。脚本的 stderr 审核日志记录每次发送，因此即使在 `mode:agent` 中，每次传输也是可审核的。
