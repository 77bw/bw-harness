该参考是审查完成的合并叶部分（`references/finish-input.md`）。合并叶运行阶段 5 和阶段 5b 步骤 1 到 3，并写入 `synthesized-findings.json` 和 `validator-input.json`。然后，调度上下文按照 `references/finish-input.md` 的状态运行阶段 5b 第 4 步，并写入 `validator-verdicts.json` 加 `validator-outcome.json`。然后，报表叶从 `references/finish-report.md` 运行阶段 5b 步骤 5、阶段 5c 和阶段 6。首先阅读`<run-dir>/finish-input.json`。无论何时此引用引用早期阶段的结果、意图摘要、花名册、计划、范围或对话上下文，该值都是该文件的匹配字段，并且`<root>`是其`docs_root`。当合并叶启动时，跨模型对等点已经是终端并进行分类：它在设置时折叠`peer.artifact`并复制`peer.coverage`，并且从不读取作业状态或启动路由。叶子不启动任何子代理；它的回归正是`finish-input.md`的名字。

为您读取的每个文件提供自己的工具调用，以便其输出自行返回，而不是在一个命令或一个脚本中返回多个文件。仅当整个文件返回时，读取才算数。某些主机会从长工具输出中切掉中间部分，并在其位置留下截断标记，因此当读取返回时缩短，请在对该文件进行操作之前读取较小范围内的缺失行。

### 第五阶段：合并结果

在路由任何发现之前阅读`references/action-class-rubric.md`：它定义了严重程度和应用的操作路由规则综合，并且它指出综合做出最终的路由决策。

将多个审查者紧凑 JSON 返回结果转换为一个经过重复数据删除、置信度过滤的结果集。使用此技能目录中的 `scripts/findings-mechanics.py` 进行 schema/value 验证、精确指纹重复数据删除、保守路由合并、引用和置信度检查、确定性排序和稳定编号。这些是机制，而不是模型判断。

将紧凑的审查者返回写入 JSON 数组，然后准确运行以下命令。不要检查助手源或运行其 `--help`；它的契约是这个引用和它的 JSON 输出。

输入是一个 JSON 审查者返回对象数组。输出是一个具有`findings`、`pre_existing_findings`、`suppressed_findings`、`suppressed_by_confidence`、`malformed_findings`、`malformed_returns`、`first_evidence_backfilled`的对象；直接使用这些字段，不检查实现来推断其他行为。

```bash
SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>";
PY="$(for c in python3 python py; do command -v "$c" >/dev/null 2>&1 && "$c" -c '' >/dev/null 2>&1 && { echo "$c"; break; }; done)"; [ -n "$PY" ] || { echo "no working Python 3 interpreter on PATH" >&2; exit 1; };
"$PY" "$SKILL_DIR/scripts/findings-mechanics.py" < "$RUN_DIR/raw-returns.json" > "$RUN_DIR/mechanical-findings.json"
```

在第一个帮助程序运行之前，加载每个可用的每个审查者产物并构建由审查者加上帮助程序指纹键入的源详细信息映射：规范化 `file`、字符串 `line` 和空白规范化小写字母 `title`。该地图包含每个源发现的 `why_it_matters` 和 `evidence`；紧凑返回是合并输入，而不是最终报告对象。

在编写辅助输入之前，使用相同的键将每个匹配产物的 `evidence` 数组附加到其紧凑查找中。保留紧凑结果的其他字段。对于锚点 75 或 100 处的结果，助手会在验证之前从 `evidence[0]` 处的非空字符串填充缺失或空的 `first_evidence`。其他主播保留现有的报价和推广行为；没有任何可用报价的调查结果仍受报价门的约束。

`first_evidence_backfilled` 计算重复数据删除之前以这种方式恢复的有效输入结果。在合成重新运行中保留初始计数并添加任何进一步的回收率，因此使用已经标准化的结果重新运行不会删除它。

Compound Pack规则`learnings-researcher`报告差异**矛盾**是一个发现候选者，并且在第一个帮助程序运行之前，每个通过普通检查（引用行，验证，误报检查）的候选者被序列化为形状`references/dispatch-reviewers.md`定义的完整紧凑审查者返回，因此它接收稳定的`#`和普通路由。审稿人是`learnings`； `file`、`line`、`first_evidence`来自研究者引用的违规行；严重性遵循每 `references/action-class-rubric.md` 规则的后果；当研究人员同时引用规则文本和行时，锚点为 100，否则为 75。源详细信息映射条目保存其 `evidence`：规则的引用文本和 `(pack: <id>, <包内的路径>)` 引用。仅由研究人员引用的未更改行违反的规则与 `pre_existing: true` 相同。步骤 1 中的合并测试保持不变：仅当结构化审查者的发现都描述相同的缺陷和修复路径时，才会与其合并，并且合并后的发现保留引用。规则差异荣誉和相关过去的解决方案是第 6 阶段（综合和呈现）第 7 节的注释。

检查助手的 `findings`、`pre_existing_findings` 和 `suppressed_findings` 是否存在使用不同措辞或附近锚点的语义重复、直接依赖异常以及下面的解决冲突。仅当候选人描述相同的缺陷和修复路径时才合并。如果语义协调、直接依赖性重新分类、结算协调或审核策略更改了集合，则将所有三个分区中的每个协调候选序列序列化为一个有效的综合审核者返回，并再次运行帮助程序以恢复确定性检查、分区、排序顺序和编号。切勿要求帮助者决定语义对等或解决冲突。协调语义重复项时，将其原始源映射键与工作记忆中的候选项一起携带，以便细节水合作用不依赖于重写的标题。助手的确定性 `suppressed_findings` 分区不是主要审核输出；结算对账后，检查下面的软桶路线，然后丢弃其余部分，同时保留 `suppressed_by_confidence` 计数。

然后仅应用帮助者无法做出的判断。将每个审查者的输出视为一个声明：根据预期结果和当前来源验证其结果。具体的维护收益可以证明没有运行时错误的发现是合理的，但偏好、对完整性的要求而没有问题的证据以及审查者协议却不能。在要求用户做出决定之前，先从证据中解决争议。

**范围标准权威。** 本地`project-standards`审查和综合是范围规则覆盖范围的唯一所有者（他们单独决定适用哪些范围规则）；外部对手同行是佐证的。仅当与本地建立的每条适用的范围规则兼容时，同行候选人才会进入最终报告；否则拒绝它。替代候选人需要独立的当地证据。

1. **按语义协调。** 只有不同措辞指向同一个缺陷和同一种修复方式时才合并；保留分歧。合并各候选由机械处理产生的 `reviewers` 与 `independent_reviewers` 列表，不能仅因身份出现在前者就加入后者。旧缺口只有在本次变更的正确性直接依赖它时才列为主要发现；此时在最后一轮辅助处理前标为 `pre_existing: false`。旁支清理仍属既有问题。
2. **决定已定。** 检查幸存的`findings`和`suppressed_findings`。放弃仅仅倾向于替代 `session-settled:` KTD（已发现计划中的关键技术决策）的发现，包括已经标记为 `settled_conflict` 的候选者。保留真实缺陷的证据，或者已解决的方法无法达到正常严重程度的商定结果的证据。保留的调查结果并不授权撤销已解决的决定。仅当比赛明确时才遵守推断计划和解。

   **审核策略。** 当 `finish-input.json` 命名审核策略时，立即通过 `references/action-class-rubric.md` 的存储库审核策略部分将其应用于尚存的 `findings` 和 `suppressed_findings`，并编写该部分所需的覆盖率句子。发现策略删除或重新降级已更改集合，因此运行步骤 3。
3. **恢复机制。** 在语义协调、直接依赖关系重新分类、解决协调或审查策略更改之后，使用每个协调的候选者重新运行帮助程序，包括未更改的主要候选者和预先存在的候选者以及剩余的被抑制的候选者。忽略在和解调节过程中被丢弃或被审核政策删除的候选者。它强制执行引用行检查、离散置信锚、精确重复数据删除、独立协议升级、保守路由、预先存在的分区、置信阈值、确定性排序和稳定的`#`编号。仅当合并组中包含返回记录为`independence_verified: true`的`adversarial-<provider>`对等体时，协议才将锚定提升一级；正在进行的审核者共享一种服务模型，因此他们的同意记录在 `reviewers` 中，但永远不会提高信心，而 `fast-pass` 根本不重要。同行的发现从来不具有适用的权威。
4. **验证前软桶降级。**最终帮助程序通过后，检查幸存的 `findings` 和剩余的 `suppressed_findings`。即使自动化助手提高了他们的信心，也拒绝没有明确的重大后果或有价值的好处的索赔。在内部记录决定；不要将被拒绝的索赔重新纳入剩余风险或缺失的测试中。仅当项目证据证明其相关性时才保留不确定风险。
   - 当前的 P0/P1 仍然是主要的，除非它是语义重复、仅偏好解决的冲突或真正预先存在的。此步骤不存在验证器判决，因此基于判决的保留和删除属于阶段 5b。切勿仅仅因为只有一位审查者找到它而将其移动到`residual_risks`或`testing_gaps`。具有不同故障模式或修复路径的结果不会重复，即使它们触及相同的行（例如，等待分类账追加不能解决稍后追加两次的发布失败重试）。
   - 对于仅测试缺乏覆盖的发现，当缺乏测试本身很重要时，每个更改的子系统最多保留一个伞形主要发现；仅当它们在该保护伞之外添加相应的未覆盖场景时，才将较窄的情况保留在`testing_gaps`中。
   - 来自 `testing` 的保留单一审查者 P2/P3 咨询属于 `testing_gaps`，来自 `maintainability`、`reliability` 的咨询或敌对审查者属于 `residual_risks`，除非它引用了明确违反的合同或证明当前面向用户的缺陷。审稿人的身份和严重性不需要担心录取失败。
   - 不要用假定的部署拓扑或流程生命周期来扩大存储库合同。仅当存储库证据确定了操作条件和重大后果时，才保留此类风险；想象的配置并不是未解决的项目风险。
   - 被压制的候选人仍缺席初选`findings`；在此步骤之后丢弃所有其他`suppressed_findings`。记录模式感知降级计数。只有剩余的主要组进入阶段 5b（验证通过）。

**详细水合检查（在验证和渲染之前）。**从其源详细信息地图条目中水合每个保留的主要和预先存在的发现。为了精确合并，联合并删除贡献的 `evidence` 数组并保留最具体的源 `why_it_matters`；对于语义合并，使用携带的原始源映射键。 `actionable_findings`稍后重用这些水合对象，而不是重建紧凑的子集。每个保留的结果必须具有非空 `why_it_matters` 字符串和非空 `evidence` 数组。如果产物不可用或格式错误，请重新读取引用的更改行并在存在时使用`first_evidence`仅重建直接验证的细节。切勿仅凭标题来创造影响力。如果仍无法建立必填字段，则在阶段 5b 之前将候选字段视为格式错误而删除，并将其记录在 Coverage 中；永远不要在 markdown、`mode:agent` 或 `review.json` 中发出部分结果。

5. **分区工作。** 可操作队列是`gated_auto`或`manual`加上所有者`downstream-resolver`；咨询调查结果和`human`或`release`拥有的调查结果仅供报告。到处重复使用助手的马厩`#`。即使子系统在财务或运营上敏感，具有特定代码或测试响应的具体当前P0/P1也属于`downstream-resolver`；下游调用者仍会对其进行审核、应用和验证。仅当下一步真正需要 product/design 决策、不可用的权限、外部协调或释放操作时，才使用所有者 `human`。审查者谨慎和`requires_verification:true`本身并不能从调用者的可操作队列中删除可修复的缺陷。
   在渲染之前，将每个具体的P0/P1规范化为`downstream-resolver`，除非其报告条目指定了特定的product/design选择、不可用的权限、外部依赖项或阻止实现的发布决策。广泛的重新设计、一些相关的编辑或敏感代码都不是这样的障碍。路由为 `validation_status: "unresolved"` 的发现阶段 5b 不受此规范化的影响：它与 `owner: "human"` 和 `autofix_class: "advisory"` 保持仅报告状态，并且后面的综合通道不会将其拉回到可操作队列中。可操作的发现部分仅包含生成的 `downstream-resolver` 队列； `human`或`release`拥有的项目出现在它之外，作为一个人必须做出的决定。
6. **建立主题分类组。**对相关发现进行分组，以便读者可以对主题而不是项目进行分类。这与重复数据删除不同：组永远不会合并发现结果或更改严重性、置信度、路线、所有者或稳定`#`。组跨越整个主要组。团体可以将未解决的第 5b 阶段的发现命名为验证门，但绝不能指示修复者应用未解决的索赔。
   - **`grouping:off`:**跳过这一步。
   - **`grouping:auto`（默认）：**当发现的问题涉及不同的问题时建立小组；触发因素是不同的关注点，而不是项目计数（反映了计划需求如何按功能分组）。仅当所有发现确实是关于同一件事时才跳过；比起装饰性的单项组，更喜欢没有组。
   - **`grouping:always`:** 总是建立团体；仅当不存在有意义的多查找分组时才使用单查找组。
   - **分组信号：**共享根本原因、受影响的子系统、面向用户的故障模式、重叠修复路径、依赖顺序或一种设计选择的重复症状。
   - **组形状：** 短标题，包含稳定的发现 `#`s、单行上下文、首选解决方案以及原因。当一个修复路径解决了多个问题时，请将其命名并说明首先处理哪个问题。
   - **排序：** 按组中包含的最高严重性发现对组进行排序，然后按最低稳定 `#` 进行排序。一项发现最多出现在一组中；将真正不相关的发现不分组。
7. **收集报道和咨询资产。** 让帮助者 drop/suppression 发挥作用。根据与主要发现相同的关于重要性和相关性的规则，承认角色提供的残余风险和测试差距；不要通过这些字段保留被拒绝的索赔。对遗留问题进行重复删除并保留任何选定的学习内容和部署验证输出。 `data-migration` 的架构漂移已存在于合并的结果集中。

### 第 5b 阶段：验证通过（可选质量门）

此阶段是对结果的可选第二次检查。对于缺乏跨模型佐证的调查结果仍需要独立验证。不要再花另一个模型来重新验证已经在服务家庭中独立建立的证据。

1. 仅当发现结果具有 `first_evidence` 且既有普通审查者，又有产物记录 `independence_verified:true` 的 `adversarial-<provider>` 审查者时，才跳过验证者。相同模型的证实永远不会许可这种捷径。在覆盖率中记录跳过计数。
2. 选择每个剩余的 P0/P1 以及每个剩余的可操作发现。始终选择单源 P0。 P2/P3 咨询项目应该已经移至软桶中；不要仅仅为了保持主要性而验证它们。
3. 将选定的集合放入 **一个** 确定性验证器批次中，按严重性和稳定 `#` 排序，使用 `references/validator-batch-template.md`。八个结果是正常上限。当超过 8 个 P0/P1 幸存时，将同一批次扩展到正常上限以包含每个幸存的 P0/P1，而不是默默地忽略阻塞项；切勿将工作分成另一批。验证器针对每个发现返回一个独立的判决。成本、经过的时间、信心或机械上显而易见的发现永远不会允许额外的跳过；当所需的验证器无法运行时，将P0/P1保留为验证降级并如此说。
4. 启动并收集验证器批次：调度上下文按照“验证器（调度上下文）”下的`references/finish-input.md`所述运行此步骤，包括有界等待、失败分类和代理生命周期规则；没有叶子运行它。
