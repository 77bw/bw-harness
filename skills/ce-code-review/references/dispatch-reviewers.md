### 第四阶段：产生子代理

#### 内联快速传递（在审查者队列之前发出）

为了在几秒钟内显示结果，编排器会在第一个前台审查者调度之前**对其已经保存的差异进行快速的第一原理扫描。将快速通过块作为文本发出，然后开始确定性审查者队列，无需中间等待。

仅扫描**高信号、明显**问题，仔细的第一次读取捕获：data/SQL安全性、注入（shell/SQL/LLM-output信任边界）、损坏的控制流、丢失`await`/未处理的承诺、交换的参数或逐一关闭、添加enum/status但未更新其同级开关、diff 使其可达的值上的 null deref。不要**进行深入分析、阅读差异以外的内容（除了快速的 Grep 以获得枚举完整性）或追逐微妙的问题。逐字引用每个相同的条形作为角色发现的激励语句。

快速传递会分配严重性，因此在标记任何内容之前，请先阅读 `references/action-class-rubric.md` 中的 P0-P3 等级；第 5 阶段重用同一文件中的相同比例。仅当发现紧急的P0/P1候选者时才显示初步快速通行证。将这些内容放在明确的初步标题（例如 `### Fast pass (preliminary — deep review in progress)`）下，作为 `severity — file:line — what` 的简短列表，其中一行表明它们未经验证，并将在最终报告中进行重复数据删除。将 P2/P3 候选者保留在内部，直到最终报告，其中验证和重复数据删除提供所需的上下文。如果没有P0/P1候选者，则仅发出简短的“没有紧急快速通过结果；继续深入审查”进度线。不要在这里分配稳定的 `#` 数字。

快速通行证作为名为 `fast-pass` 的伪审查者进入第 5 阶段，有两个硬约束，因为它是协调器自己的阅读，**不是**独立审查者（它与协调器和会话模型角色共享会话模型及其盲点）：

- **限制锚点 50 处的每个 `fast-pass` 发现。** 在锚点 50，仅当其为 P0（P0+50 通过第 5 阶段置信度阈值）时，它才会自行到达报告。否则，只有通过对带有自己 ≥75 锚点的独立角色发现进行重复数据删除，它才能成为可操作的发现。
- **`fast-pass` 永远不会计入跨审稿人晋升**（第 5 阶段第 3 步，恢复机制）。审核者列中会注明`fast-pass`+角色指纹匹配，但**不会**碰撞锚点。进程中的角色之间也没有达成一致；只有经过验证的跨模型同行才能证实。

不要将 `fast-pass` 候选人输入角色或验证器提示中。这些代理独立审查原始差异，并播种它们将创建此上限所要防止的错误协议。如果快速通行证没有发现任何明显的情况，则发出一行这样的话并继续；永远不要阻止对其进行调度。

**在最终报告中协调初步区块。** 必须考虑未保留下来的初步快速传递项目（已删除重复数据、受第 5 阶段置信阈值限制或通过验证丢弃），而不是悬而未决。添加一行“初步快速通行项目已撤回：<n> (<reason>)”注释，以便用户看到可怕的初步结果后知道该结果已被清除。标记仅从`fast-pass`幸存下来的任何最终发现（没有人物佐证），以便读者可以看到它依赖于较弱的证据。

**`mode:agent`：**不**发出初始块，因为该模式的响应必须是单个原始 JSON 对象，前面没有任何内容。仍然在内部运行扫描并将其结果作为 `fast-pass` 输入到第 5 阶段重复数据删除中。

#### 模型分层

以下等级是每个审查者的默认等级。在第一次生成之前阅读 `references/subagent-model.md`：它决定每次生成通过的模型和工作量，并在 Codex 中替换这些层。

三个审查者继承会话模型而不进行覆盖：`correctness-reviewer`、`security-reviewer` 和`adversarial-reviewer`。这些执行最高风险的分析（逻辑错误、安全漏洞、对抗性故障场景），并且应该在用户配置的任何功能级别上运行。如果用户使用 Opus，这些将获得 Opus。

所有其他角色子代理和 CE 本地提示资产都使用该平台的中间层模型来降低成本和延迟。有关确切的调度时间覆盖，请参阅下面的“生成”小节。

Orchestrator（这个技能）也继承了会话模型；它处理意图发现、审查者选择、查找 merge/dedup 和综合。

#### 运行ID

使用已在阶段 1b 中创建的运行 ID 和绝对运行目录。将`{run_id}`和`{run_dir}`传递给每个角色子代理，以便他们可以将完整的分析写入`{run_dir}/{reviewer_name}.json`。

**大型共享上下文：传递路径，而不是内容。** diff 和文件列表发送给每个审查者和验证者。当将它们内联到每个子代理提示中会很浪费（许多文件或大差异）时，将它们写入运行目录一次（例如`full.diff`，`files.txt`）并在差异和更改文件槽中传递这些**路径**而不是内联内容。子代理和验证器模板指示子代理读取暂存路径。直接内联一个小的差异。

#### 产卵

**代理生命周期。** 在清理之前收集每个审查者的最终结果，包括失败。当宿主允许呼叫者关闭或释放座席时，请在开始更多、继续或返回之前为此审核的座席执行此操作。不要向已完成且没有剩余工作的客服人员发送消息。不要因为代理完成或被中断而假设槽是空闲的，并且不要发明宿主缺乏的清理操作。此规则管理此技能启动的每个子代理，包括阶段 5b 验证器。

调度子代理时省略 `mode` 参数，以便应用用户配置的权限设置。不要通过`mode: "auto"`。

**在离开此阶段之前解析任何提示资产中的 `<root>`。** 子代理从不运行产物根块，因此仍在其读取的文本中的 `<root>` 占位符是它将搜索但找不到任何内容的文字路径。当您内联提示资源时，请将本次运行解析的产物根替换为它包含的每个`<root>`。当子代理按路径读取资产时，在提示中告诉它这些文件中的 `<root>` 表示已解析的根，并给出该路径。

**在调度时覆盖模型。** 当您在第 3 阶段选择审查者（选择审查者）时，**在内部工作列表中记录您将为每个审查者传递的模型**。该列表是您的外部存储器（旧打印的 `[session model]`/`[mid-tier]` 标签所扮演的角色），它必须存在并受到尊重，即使它不再在面向用户的公告中呈现：

- **会话模型**（无覆盖；继承会话模型）：仅限 `correctness-reviewer`、`security-reviewer` 和 `adversarial-reviewer`。
- **中层**：所有其他角色和 CE 特工。通过平台的平衡中层模型。在Claude Code中，那就是Sonnet类。在调度原语未公开显式模型或自定义代理选择器的主机上，省略覆盖并继承父模型，因为单独的任务措辞不会选择不同的模型：对父模型的工作审查胜过对无法识别的名称的损坏的调度。

如果用户或项目的活动指令或实时提示为此子代理命名了模型，请使用该模型而不是上面的默认层。他们可以按子代理的层、提示资产名称或正在分派的子代理来命名。如果没有此类指令，为此子代理角色配置的模型将优先于默认层。遵循命名模型并不是错过覆盖，也不是为此子代理角色配置的模型。

将此应用于**每个**代理/`spawn_agent`/子代理调用。当默认层获胜时，在顶级父会话（例如 Opus）上忽略它会在昂贵的层上静默运行该审查者，因此请根据需要对待内部列表。将其移出面向用户的输出删除了*显示*，而不是保留和遵循它的要求。

**有界依次调度。** 在批次启动时在阶段日志 (`references/scope.md`) 中记录 `--end select --start dispatch --reviewers <count>`，然后将选定的审查者作为一个**本轮收集的并发批次**而不是串行调度。启动以便在第一个审查者开始之前存在有界收集器：仅当前台调用返回您可以绑定的收集器时才要求关闭后台执行；如果前台调用阻塞，直到子进程退出并且无法被限制，则通过后台执行启动并通过主机的有界依次等待进行收集。产生与主机的活跃代理上限接受的数量一样多的审查者，并将每个批次的大小调整为主机实际接受的上限；永远不要对数字进行硬编码。审查者在结构上是独立的（没有人提供其他人的输出；请参阅上面的独立规则），因此批次组成和完成顺序不能改变任何发现，并且在合并后排序后向下游分配稳定的数字。如果宿主不同时运行相同消息调用，则此相同的调度**会自动降级为串行**。这是正确的楼层，而不是失败的楼层。

通过原语观察到的返回而不是其主机名或请求的后台设置进行收集，并等待结束。 每个审稿人的产物，`{run_dir}/{reviewer_name}.json`，就是事实；调度调用自身的返回、启动时阻塞等待的返回、或者主机传递的命名启动并携带其最终有效负载的终端消息都是它的一种呈现。 当在本回合内，您持有该特定发射的其中一个发射或其产物位于磁盘上时，就会收集发射。 吃掉先落地的那个，一次。 当神器在发射仍在进行时着陆时，请在离开此阶段之前停止发射；下面的代理生命周期规则然后在其他任何事情开始之前释放它，因此完成的审核者永远不会持有验证者需要的插槽。 启动收据（主持人对审查者启动的确认）未收集，而不是审查者返回，状态或进度更新或在启动终止之前返回的等待也是如此。 当调度返回异步 id 或收据时，继续使用主机的阻塞收集功能依次等待，连续重复主机的等待，两次等待之间没有任何内容，直到每次成功启动都达到最终结果或其产物落地，或者自审查者自己的成功启动以来已超过聚合挂钟限制`references/subagent-template.md`状态（在串行降级下，后来的审查者时钟在其启动时启动，而不是在批处理启动时启动）。 单次等待时间较短的主机通过重复等待来达到该限制，而不是通过将一次短暂返回视为最后期限。 要求每个人等待主机允许的时间，直到该限制之前剩余的时间，而不是主机的默认或最短时间。 例如，如果等待工具需要长达一个小时的超时，则启动后立即开始的等待会要求完整的 20 分钟，而不是 10 或 60 秒。 一旦审查者完成，等待仍然会返回，因此长时间的超时不会延迟收集。 每次等待返回都需要完全重新读取此上下文，因此十次 10 秒的等待成本大约是收集相同审查者的一次长时间等待的十倍。 验证每个结果：使用有效的紧凑JSON，无论是带内返回还是异步收集，并根据下面的降级覆盖率规则将终端工具错误或格式错误的输出分类为失败的审查者。 当限制通过时既没有最终结果也没有产物的审查者将被停止并以相同的方式记录为失败的审查者；这是一次集体失败，而不是部分名单。 这些由宿主管理的阻塞收集等待收集批次；它们不是禁止的分离委托轮询循环。 当发射尚未收集时，绝不能运行第 5 阶段。

判断一个收藏家的标准是它的实际用途，而不是它的名字。仅当工具阻塞直至启动终止时，该工具才是阻塞等待。仅当消息标识启动并携带最终有效负载时，消息才是结果，因此报告进度或状态更改的通知不是最终结果。当主机没有提供轮流方式来为已启动的审查者提供最终结果，或者没有可以通过任何方式限制的等待（有界等待或后台执行加上主机的有界等待）时，就没有可靠的阻塞收集路径：停止已启动的工作并采取模式的失败路径，而不是结束轮流等待、发出进度或合成部分花名册。在采用该故障路径之前，将每个持久化对等点交给其所属的清理（清理步骤`references/cross-model-review.md`定义）；不归，不得放弃超然工作。在`mode:agent`中，仅发射`{"status":"failed","reason":"<one sentence>"}`。

此轮流批次**不是**禁止的模式。被禁止的是将本地审查变成编排器必须轮询的“独立”委托：后台 bash/CLI 调用加上前台 `sleep`/状态文件循环，或计划的唤醒和“仍在等待”轮流（已退休的 ce-work-beta 故障模式）。该规则管理分离的委托，例如跨模型对等点，它保持分离，并且是唯一允许与该批次重叠的工作；它并不禁止宿主的本机等待和结果传递。切勿插入 shell 无操作（`echo waiting`、`noop`、`yield turn`、`end turn`、`true` 或睡眠）、分离状态轮询、计划唤醒或面向用户的“仍在等待”轮流等待审查者。

如果平台根本没有并行子代理原语，则按顺序运行审核器；阶段、输出格式和合并管道保持不变。将 active-agent/thread/concurrency-limit 生成错误视为背压（主机要求您等待容量），而不是审查者失败：主机拒绝容量的插槽将保持排队状态，并在稍后的批次中作为活动审查者空闲容量重试。大于主机上限的请求批次会限制在主机接受的范围内，不会丢弃任何审查者。如果排队的审查者无法调度，并且活动工作和支持的发布都无法恢复容量，则继续用户可见的 degraded/no-subagent 审阅路径。不要缩小名册、询问用户或将审查者记录为因容量背压而失败。仅在成功调度失败后，或者在调度由于非容量原因而在更正调用后仍然存在时失败时，才将审查者记录为失败。在父上下文中执行的审查者通过可能会提供属性证据，但它不是独立的：将其从 `independent_reviewers` 中排除，切勿使用其协议进行升级，并命名丢失的独立覆盖范围。

在组装任何生成提示之前，请从该技能的目录中读取`references/subagent-template.md`：它定义了每个审查者需要的插槽以及收集等待使用的挂钟预算。 每个审查者需要四个完整文件：其角色资产、模板、`references/diff-scope.md` 和 `references/findings-schema.json`。 默认情况下，传递从该技能目录解析的绝对路径，并让审查者读取它们。 告诉它在检查之前读取所有四个文件，遵循模板的 Template 块内的所有内容，并将其他三个文件的内容视为其槽的值 (`{persona_file}`、`{diff_scope_rules}`、`{schema}`)。 在每个审查者的提示中完全按照所写的内容包含这句话：“为您读取的每个文件提供自己的工具调用，以便其输出自行返回，而不是在一个命令或一个脚本中包含多个文件。 仅当整个文件返回时，读取才算数。 某些主机会从长工具输出中切掉中间部分，并在其位置留下截断标记，因此当读取返回时缩短，请在对该文件进行操作之前读取较小范围内的缺失行。”将每个其他槽的值放入提示中，或将提示名称放入暂存的 run-dir 文件中。 在任何审查者开始之前，将四个文件复制到每个提示中会花费每个审查者数千个输出令牌，因此仅当主机的子代理无法读取文件时才内联它们。 在该内联路径上，还读取角色资产、`references/diff-scope.md`和`references/findings-schema.json`，并将其内容粘贴到匹配的插槽中。 为您在此处读取的每个文件提供自己的文件读取调用。 当主机支持并行调用时，将它们一起发出在一条消息中。 切勿将文件连接到一个 shell 输出中。 在串行主机上，每轮读取一个文件。

通用子代理的整个简介就是您发送的提示。当主机的子代理工具要求您命名代理时，请仅使用您在主机列表中看到的名称，如果没有，请在第一次调度之前列出其代理。选择不添加自己的角色的普通子代理，它仍然算作通用子代理。切勿选择专家，例如审查者或工作代理，他们自己的角色提示、输出格式或工具限制会取代或缩小您的提示。

对于每个选定的审查者，并且仅针对这些审查者，使用子代理模板和相应的本地提示资产 `references/personas/<reviewer-name>.md` 生成通用子代理，按上述方式交付。请勿通过 `subagent_type`、键入 `Agent` 名称或平台级 CE 代理注册来命名角色或 CE 代理；当主机需要代理名称字段时，它携带普通的通用代理。每个角色子代理接收：

1. 他们的角色文件（身份、故障模式、校准、抑制条件）
2. 来自`references/diff-scope.md`的共享差异范围规则
3. 来自`references/findings-schema.json`的JSON输出合约
4. 子代理模板（校准、输出合同、规则、预算）
5. PR 元数据：查看 PR 时的标题、正文和 URL（否则为空字符串）。在 `<pr-context>` 块中传递，以便审查者可以根据既定意图验证代码
6. 查看上下文：设置时的意图摘要、文件列表、差异、范围模式 (`local-aligned` | `pr-remote` | `branch-remote`) 和远程头引用 (`PR_HEAD_REF` 或 `<branch-head-ref>`)
7. 产物文件路径的运行 ID 和审查者姓名
8. **仅适用于选定的 `project-standards`：** 非空 Stage 3b 标准映射 — 每个标准文件及其管辖的更改文件 — 包装在附加到审阅上下文的 `<standards-paths>` 块中
9. **第 1 阶段差异删除整份文件时，交给每个审查者：** 在上下文提供 `<deleted-files base="<ref>">`。`<ref>` 指读取旧文件正文的 Git 修订，通常是 `BASE:`，`pr-remote` 模式改用 `PR_BASE_REF`，未设置时省略属性。逐条列出删除文件的导出和导入时的副作用（注册、插件、顶层调用）。对该修订定点搜索，如 `git grep -n <pattern> <ref> -- <path>`；不用整份加载。
10. **当阶段 1d 上演 `review-policy.md` 时，对于每个审查者：** 该文件在附加到审阅上下文的 `<review-policy>` 块中的绝对路径
11. **仅适用于 `data-migration`：** 第 1 阶段中已解析的审阅基本引用（确定范围；`BASE:` 标记），包装在审阅上下文内的 `<review-base>` 中，因此架构漂移检查永远不会假设 `main`

角色子代理对于项目来说是**只读**：他们审查并返回结构化JSON。他们不编辑项目文件或提出重构建议。允许的写入是将其完整分析保存到输出协定中指定的已解析运行产物路径。

**例外：树变异审查者。** 其方法对树进行变异的角色（`testing`，当它运行变异测试时）仅对已审阅树的忠实快照进行操作，而不是共享结帐。禁止对共享树进行突变测试：并发审查者可以观察瞬态写入，就好像它是差异一样。当提交已审核的树`HEAD`时，使用`isolation: "worktree"`分派该角色并向其传递已审核的提交 SHA。宿主提供的工作树不会自动忠实：当会话本身在托管工作树内运行时，宿主可能会将其从主结帐或默认分支中删除（实时观察）。因此，在变异之前，角色会验证其副本的 HEAD 是否等于已审查的提交，并在任何不匹配时回退到临时副本。当审查的树包含暂存或未暂存的更改（`local-aligned`范围），或者主机无法隔离时，让角色创建一个保留这些更改的临时副本并仅更改该副本。只读兄弟姐妹保留在共享结账上。

此处的只读意味着**非变异**，而不是“无 shell 访问权限”。当需要收集证据或验证范围时，审核子代理可以使用非变异检查命令，包括面向读取的`git`/`gh`用法，例如`git diff`、`git show`、`git blame`、`git log`和`gh pr view`。当发现的声明取决于行历史（`pre_existing`、意图、引入此差异或依赖于authorship/age的P0/P1置信度）时，审查者应在引用的行上附加来自目标blame/log的简明出处证据行。该行是对引用行门（每个发现都引用其激励行的规则）的补充，而不是完整文件转储，并且当仅从差异证明发现是合理的时，该行被省略。在 **`pr-remote`** 或 **`branch-remote`** 范围内（请参阅第 1 阶段，确定范围），通过 `git show <remote-head-ref>:<path>` 或 diff 块检查更改的文件。不要为范围内的文件使用 Read/Grep 工作空间路径；针对已审查的首席裁判收集blame/log。他们不得编辑项目文件、更改分支、提交、推送、创建 PRs 或以其他方式改变签出或存储库状态。

每个角色子代理将完整的JSON（所有模式字段）写入`{run_dir}/{reviewer_name}.json`，并返回仅包含合并层字段的紧凑JSON：

```json
{
  "reviewer": "security",
  "findings": [
    {
      "title": "用户在帐户查找中提供的 ID，无需进行所有权检查",
      "severity": "P0",
      "file": "orders_controller.rb",
      "line": 42,
      "confidence": 100,
      "autofix_class": "gated_auto",
      "owner": "downstream-resolver",
      "requires_verification": true,
      "pre_existing": false,
      "suggested_fix": "在查找之前添加 current_user.owns?(account) 守卫",
      "first_evidence": "orders_controller.rb:42 -- account = Account.find(params[:account_id])"
    }
  ],
  "residual_risks": [...],
  "testing_gaps": [...]
}
```

`first_evidence` 是提升到紧凑返回中的 **一个** 详细层字段：引用行门所需的带有 `file:line` 的逐字激励行。 **对于锚点 75 或 100 处的每个发现都是强制性的**。仅对于anchor-50 结果省略它。第 5 阶段（合并发现）从匹配的产物证据（如果可用）中恢复被遗漏的引用，并删除或降级任何仍然丢失的 75/100 发现；第 5b 阶段（验证通过）将其用于验证器跳过检查。将其保留为单个触发线，而不是完整的 `evidence` 数组；该数组保留在产物中。

产物文件**必须**携带完整的详细信息层字段（`why_it_matters`、`evidence`）。紧凑的*返回*省略了所有细节层字段**除了`first_evidence`**，但是将紧凑的形状写入产物（常见的审查者纸条）会默默地剥离Coverage和键控细节行所依赖的细节。无论审阅上下文和资产是如何交付、内联或从磁盘读取的，每个审查者仍然会收到完整的子代理模板输出合同；路径运输不允许使用更薄的产品。 `suggested_fix` 在两层中都是可选的；如果存在，请将其包含在紧凑的回报中，以便调用者可以在审核后应用修复。如果文件写入失败，紧凑返回仍然提供合并所需的一切。

**CE 通用条件本地提示资源** `learnings-researcher` 仅在被第 3 阶段选择时才会通过与结构化角色相同的确定性前台批量调度进行调度。 `agent-native-reviewer` 是一个结构化角色，与其他角色一样被调度。阅读 `references/personas/` 中的学习提示文件，然后为其提供角色接收到的相同审阅上下文捆绑包：输入模式、在第 1 阶段收集的任何 PR 元数据、意图摘要、审阅已知的基本分支名称、`BASE:` 标记、文件列表、差异和 `UNTRACKED:` 范围注释。

在编写 `learnings-researcher` 调度之前，通过运行此技能的解析器作为一个命令来解析配置中声明的任何Compound Pack：

```bash
SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>";
PY="$(for c in python3 python py; do command -v "$c" >/dev/null 2>&1 && "$c" -c '' >/dev/null 2>&1 && { echo "$c"; break; }; done)"; [ -n "$PY" ] || { echo "no working Python 3 interpreter on PATH" >&2; exit 1; };
"$PY" "$SKILL_DIR/scripts/packs-resolve.py"
```

将JSON的`roots`（包`id` + 绝对`dir`）与`<root>/solutions/`一起添加到研究人员的搜索根列表中；在覆盖范围内报告其 `errors`/`warnings` 一次，而不是在其他地方报告。如果没有 `packs:` 键，结果为空并且没有任何变化。一项基于包装规则的发现将其引用为`(pack: <id>, <包内的路径>)`。 diff 矛盾的匹配规则成为第 5 阶段（合并结果）中的编号发现，而 diff 荣誉规则和相关的过去解决方案保留在第 6 阶段（综合和呈现）注释。跳过`pr-remote`/`branch-remote`范围内的解析，因为本地配置不是审核树的配置。不要使用通用的“查看此”提示来调用它们。它们的输出是非结构化的，并在第 5 阶段和第 6 阶段分别进行合成，在叶子中运行：收集到每个此类返回后，将其逐字保存到`{run_dir}/{reviewer_name}.md`，并将其列在`collection.unstructured_returns`（`references/finish-input.md`）下的`finish-input.json`中；以下的`deployment-verification-agent`也同样。

**CE 条件本地提示资产**（仅`deployment-verification-agent`）在迁移产物条件适用时通过相同的确定性前台批量调度作为通用子代理进行调度。从 `references/personas/` 读取提示文件，然后传递相同的审核上下文包以及适用性原因（例如，哪些迁移文件触发了提示资产）。它的输出是非结构化的，必须保留用于第 6 阶段合成，就像其他选定的本地提示资产一样。模式漂移由 `data-migration` 角色作为结构化结果处理，而不是在这里。

#### 跨模型对抗通行证

第 3d 阶段（绑定对抗路线和最终名单）已经做出了排他路线选择，并在适用时启动了分离对等点。不要在此处解析、启动或替换路由，除非拥有的折叠规则（恢复分支 `references/cross-model-recovery.md` 定义）要求在相同路由速率限制重试失败后执行未运行回退或进程内恢复。仅派遣第 3d 阶段的本地名单确定。

内联快速传递完成并且本地审查者批次开始后，在审查者运行时准备完成输入 (`references/finish-input.md`)。请勿在该轮次期间轮询对等方。本地审查者完成后，如果 Stage 3d 保留了对等作业 ID，请在调度上下文中执行引用的单个有界 status/wait/reap 序列，并在此处应用其折叠分类：未运行的回退、替换接收者、同路由崩溃恢复和进程内 `adversarial-reviewer` 调度都需要启动或只有此上下文具有的用户可见的披露。来自artifact的属性，通过runner进行清理，在stage log中记录`--end peer`，在`finish-input.json`（`references/finish-input.md`）中将结果记录为`peer.outcome`、`peer.artifact`、`peer.coverage`；当回退运行时，它的返回连接`raw-returns.json`。无论是否存在对等作业，一旦收集到每个本地返回，都会在阶段日志中记录`--end dispatch --candidates <raw-returns.json 中的发现数>`，因此没有对等作业的运行仍然会关闭调度阶段。合并叶折叠记录的产物并且不决定对等点的任何内容。失败或超时保持非阻塞状态并在覆盖范围中命名。它永远不会触发后期进程内对抗性重试，除非 `references/cross-model-recovery.md` 中的所属折叠规则要求在相同路由速率限制重试失败后执行未运行回退或进程内恢复。同行发现进入普通合成，但协议提升需要顶级`independence_verified: true`；虚假或缺乏独立性是有用的证据，而不是不同模型的佐证。报道必须说明对抗性镜头是跨模型运行还是使用了进程内后备。

与任何角色产物一样，同行回报作为审查者`adversarial-<provider>`进入第 5 阶段。从未启动的传递被记录为未运行（或选择时作为进程内回退）；失败、超时、死亡或收获的已启动对等点以其最终状态命名，而不是默默消失。
