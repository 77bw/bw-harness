# 承诺和推动

如果`references/stack-submit.md`在此步骤之前已经构建并提交了堆栈层，则跳过普通的单分支提交和推送，继续执行步骤4（组合PR标题和正文）；第5步（应用和报告）中的`gh stack submit`压入堆栈。

如果您位于默认分支上，则创建功能分支必须处理三件事：过时的本地 `<base>`、本地 `<base>` 上未推送的提交以及与新远程库冲突的未提交更改。在继续之前，请阅读`references/branch-creation.md`并遵循其决策流程。

扫描已更改的文件以找出明显不同的问题。如果它们明确分组为单独的逻辑更改，请创建单独的提交（最多 2-3 个）。仅在文件级别进行分组 — 无 `git add -p`。当模棱两可时，一次提交就可以了。

暂存并提交每个组。 **避免 `git add -A` 和 `git add .`** — 它们扫荡 `.env`，构建产物并生成文件。 **当调用携带它时，尊重 `exclude:<paths>`。** 调用者命名必须保持未提交的文件，通常是用户自己正在进行的编辑，它无法与其工作分开。切勿上演或实施它们，并在报告中说它们被排除在外。当此提交的计划实施单元 ID 已在手（对话、调用者或属于一个单元的文件）时，请在括号中附加该单元的 U-ID — `(U3)` 表示单元 3。不要寻找计划。当提交跨越多个单元、单元不清楚或手中没有计划时，请省略。

将您的提交添加到此分支上其他人的提交之上；永远不要以放弃作者或预告片的方式重写他们的内容，例如将它们压入你的。当您创建的提交包含其他人的作品，而这些作品不会以其他方式登陆他们的名字（从他们的分支或 PR 移植，或从他们的补丁应用）时，请以 `Co-authored-by: Name <email>` 预告片结束其消息，为每个工作人员鸣谢：其提交作者和任何人的 `Co-authored-by` 预告片名称。从这些提交或补丁中准确复制每个身份。切勿猜测电子邮件：如果没有记录任何电子邮件，请在邮件正文中命名它们。

```bash
git add file1 file2 file3 && git commit -m "$(cat <<'EOF'
commit message here
EOF
)" -- file1 file2 file3
```

`git commit` 上的尾随路径列表很重要。裸露的 `git commit` 占用整个索引，因此在此运行之前已经暂存的任何内容（调用者的 `exclude:` 路径，或用户暂存但未命名的工作）都将最终出现在提交中。命名路径会准确提交组，而不会影响其他索引条目。

然后应用**项目发布门**。在推送之前，使用 `git branch --show-current` 重新确认您位于预期的功能分支上。 Context 中聚集的分支是一个提示，步骤 1（解析分支和 PR 状态）可能已经创建或切换了分支。推送实时 `HEAD` 以便它反映当前结账，而不是过时的分支名称：

```bash
git push -u origin HEAD
```

如果工作树是干净的并且所有提交都已推送，则此步骤是无操作的。
