# 选择加入堆栈构建并提交食谱

仅当 commit-push-pr 堆栈模式处于活动状态时才加载此文件（用户要求 PR 堆栈，或者常设首选项需要一个）。当存在 `gh stack` CLI 时使用；永远不需要单独的 gh-stack 技能包。

该引用文档有两个阶段。在普通步骤 3（提交和推送）之前，运行 Probe、Topology，并在需要时仅运行 Retrospective 构建；不要运行提交。步骤 5（应用和报告）是运行“提交”并将标题和正文应用到在此运行中创建的 PRs 的唯一阶段。

下面的**剩余**表示您向用户或调用管道报告而不是猜测的未解决的项目。

## 探测

```bash
command -v gh
gh stack view --json
```

如果 `gh` 或 `gh stack` 丢失，或者 stack 命令报告堆栈对此存储库不可用（而不是仅仅报告当前分支不是堆栈的一部分），则停止并显示清晰的残差。当用户明确要求多PR堆栈或常设偏好强制堆栈→硬停止时，堆栈意图是**必需的**。否则意图是**软**→报告残差并回退到普通的单PR创建。

## 拓扑结构

**当用户指定要堆叠的父级 PR 或分支时，对其进行分类并将层建立为根。** 无论存在什么，都按 **PR 数字**进行分类 - 这就是从 GitHub 下拉堆栈的原因；裸分支名称仅解析本地堆栈。 `references/gh-stack-cli.md` 列出退出代码以及每个命令的作用。

分类移动`HEAD`，因此在分类之前**记录你的工作分支及其提示，并在构建之前返回它们。构建将签出的分支读取为原始分支；如果您就地分类，它会将父级作为原始层，并从层中删除您的提交。

- **在堆栈中**（退出 0 - 父级现已签出） - 从恢复的工作分支中规划层，然后再次签出父级并从那里运行 `gh stack add`，因此该层位于用户指定的父级之上。退出**5**表示parent不是top：residual。切勿使用 `gh stack top` 清除它，只有将新图层作为另一个图层的父级才能成功。
- **独立**（出口 2 - 未检出任何内容） - 首先解析 `<parent-branch>`：运行 `gh pr view "<n>" --json headRefName,headRefOid,author`，然后确保本地分支位于 **位于 `headRefOid`**。缺席时创建它。当该名称已经存在时，请验证它是否在该提交处，并以剩余值停止，否则：该名称可能属于不相关或过时的分支，并且重置它可能会删除未推送的提交。从没有PR的分支，直接获取并验证该ref；那里没有PR作者可以检查，所以分支只能充当主干。然后运行 `gh stack init --base "<parent-branch>" …` 将父级保留为未触及的主干，或者首先列出父级的分支以将其采用为底层 - 后者仅当 `author` 是当前用户时。
- **未经证实** - 残差，而不是猜测：错误的“独立”是创建第二个堆栈的原因，出口 6 和出口 9 也是如此。

使用此处选择的 `init` 形式代替构造中显示的通用形式，其 `--base` 将使收养父母不受管理。在构造中，`<base>`是父母的小费。 `references/branch-creation.md` 从存储库默认分支，在命名父级时不得遵循。要求从 PR 获取的分支名称在到达命令之前匹配 `[A-Za-z0-9._/-]+` — git 允许在分支名称中使用 `$(...)`，并且双引号不会停止扩展 — 并在失败的名称上留下残差。

当 `gh stack view --json` 确认当前分支属于托管堆栈时，保留该拓扑。如果不存在拓扑，请使用下面的追溯构造。当用户在此请求中没有要求堆栈时（单独的常设偏好并不要求）并且完整的工作是一个逻辑更改或只能进行人工切片，则拒绝堆栈并使用单PR路径。不得以这些理由拒绝明确的请求。 （探针的 soft/required 分割决定了当 CLI 丢失时要做什么，而不是决定堆栈是否会被拒绝。）

用户已经定向的任何显式新上栈分支必须在获取后基于**权威父提示**：当该远程提示对于已确认的堆栈层来说是当前的时，更喜欢`<tracking-remote>/<parent>`；如果父级的最新工作只是本地的（尚未在跟踪远程上 - 在第一个 `gh stack submit` 之前常见），则从本地父级分支开始。使用 `git checkout --no-overwrite-ignore -b "<branch-name>" "<parent-tip>"` 进行创作。如果由于未提交或忽略的文件将被覆盖而签出失败，请停止并要求用户处理冲突路径；在`mode:pipeline`中，无需询问即可举报拦截者。不要隐藏或删除冲突路径。对于 **upstack** 层，不要**遵循 `references/branch-creation.md` — 该引用的 `origin/<base>` 流会将层与其父层分离。当跟踪远程不同或远程提示滞后于本地父级时，请勿硬编码 `origin/<parent>`。

## 追溯建设

在普通步骤 3（提交和推送）之前，根据已解析的基础检查**完整的更改集**：现有提交以及已跟踪、暂存和未跟踪的工作更改。按照依赖顺序导出**最小有用的线性、可独立审查的层**，基础优先。每个层必须与其父层保持一致，并且不得依赖于上层层。使用整个文件组或现有的提交边界；切勿使用 `git add -p` 强制拆分。

当一种安全拓扑清晰时，无需询问即可继续：显式堆栈意图授权必要的本地分支和提交。当多个合理的拓扑会实质上改变审查边界时，请向用户询问简洁的自下而上的建议。在 `mode:pipeline` 中，停止将该提案作为残差而不是猜测。如果拆分需要块级分区或重写已发布的历史记录，请在以交互模式继续之前询问用户。在`mode:pipeline`中，不要拆分或重写；停止并显示残差，该残差描述了所需的分区或重写以及继续所需的明确确认。未经明确确认，切勿重写已发表的历史记录。

从回溯施工开始时检查的分支中选择底层路径。如果在解析的默认分支上开始构建并且没有命名父分支，请按照 `references/branch-creation.md` 获取并解析其安全基础，包括未推送的本地提交决策。如果在现有功能分支上开始构建，请不要遵循`references/branch-creation.md`：从拓扑（除非指定父级，否则为存储库默认分支）从其基础远程获取已解析的基础`<base>`，验证获取的远程跟踪提示，并使用该确切提示作为底部父级。当拓扑已经将父级解析为经过验证的本地分支时，请使用它：从 `refs/pull/<n>/head` 实现的分叉头没有要获取或验证的远程跟踪分支。记录原始分支和提示，在任何可以移动它的操作之前使用恢复引用或分支保留原始提示，并且不要将底部父级和原始提示之间的功能提交视为本地默认的未推送提交或将整个功能提示带入底层。每个上栈层都从其直接父层开始到`gh stack add`。

对于现有功能分支上未提交的整个文件组，请在切换分支之前保存所有跟踪和未跟踪的工作更改，然后仅在其父级包含其先决条件的计划层上恢复它们。保留保存的工作，直到验证顶部构造完成。在已解析的`<base>`提示或其计划的提交提示处初始化或采用底层，仅提交其文件，然后按顺序添加并提交每个下一层。调用时由 `exclude:<paths>` 标记命名的文件不属于任何层。切勿保存、移动或恢复它们——它们与发现时一样保留在工作树中。命名每个层提交上的路径，以便预先暂存的排除文件无法进入，并将“完整的原始更改集”视为更改集减去这些文件。如果构建过程中的分支切换会覆盖排除的文件，请停止并保留剩余文件，而不是继续。使用与步骤 3 相同的主题规则编写 `<bottom-message>` 和 `<next-message>`：当该层提交的计划实施单元 ID 已在手时，请在括号中附加该单元的 U-ID — `(U3)` 表示单元 3。不要寻找计划。当提交跨越多个单元、单元不清楚或手中没有计划时，请省略。

```bash
gh stack init --base "<base>" "<bottom-branch>"
git add <bottom-files> && git commit -m "<bottom-message>" -- <bottom-files>
gh stack add "<next-branch>"
git add <next-files> && git commit -m "<next-message>" -- <next-files>
```

对于现有提交边界已与计划匹配的已提交工作，请在每个计划的提交提示处创建或重用一个分支，并使用 `gh stack init --base "<base>" "<bottom-branch>" "<next-branch>" ...` 自下而上采用它们。仅当其未更改的提示是这些计划提示之一时，才重用原始功能分支。如果未发布的提交需要重新排列，请在重写之前在原始提示处保留一个恢复分支。构建完成后，运行`gh stack view --json`；在提交之前验证报告的订单是否与计划匹配，并且顶层包含完整的原始变更集。

## 提交（准备好/非草稿）

在提交堆栈之前应用**项目发布门**。

在提交之前，解析普通的`pr_teaching_archive`/`archive:on|off`门。如果归档开启，则在`gh stack submit`之前停止并有残差；提交后不要创建解释器提交或静默禁用请求的存档。用户可以使用 `archive:off` 重新运行以使用安全的提交后描述路径，直到堆栈存档具有管理者感知的路径。

在提交之前，检查堆栈的打开 PRs (`gh stack view --json` / `gh pr view`) 是否有任何 **现有草稿** 层。如果作者未明确要求打开此运行的任何草稿已存在，请不要**通过`--open`（GitHub文档`--open`也标记现有的PRs准备审查）。在这种情况下，仅提交`gh stack submit --auto`，然后在PR 看护开启时将剩余草稿视为PR 看护之前的硬残留。切勿将某人的正在进行的草稿标记为就绪。

当不存在现有草稿时（或用户明确授权打开每一层）：

```bash
gh stack submit --auto --open
```

`--auto` 单独创建草稿，babysit 默认跳过草稿。当PR 看护开启时，仅草稿结果是PR 看护切换之前的硬残留（或标记PRs准备就绪的步骤）。切勿将草稿视为已成功发送的堆栈。

提交后，将本次运行中创建的每个PR映射回其头分支和显式PR URL。对于每个新的 PR，将该 URL 传递给普通的 PR 描述组合，以便 PR 模式派生直接父级和精确头，然后将结果应用于 `gh pr edit "<pr-url>"`。切勿依赖恢复的当前分支来选择 PR。现有堆栈PRs保留其标题和主体，除非当前调用明确请求重写； `mode:pipeline` 保留记录的保守的无重写默认值。不要在此技能中发明特定于堆栈的标题改进。

## 受管理成员禁止

```bash
gh pr merge …
```

登陆仅使用`gh stack merge`，由`posture:stack-land`下的`ce-babysit-pr`或用户运行。

## 所有权

对于本次运行中创建的PRs，第 5 步独占堆栈提交和上述提交后描述步骤。没有更早的步骤提交。
