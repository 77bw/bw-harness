# 存储库上下文、分支和 PR 状态

在步骤 1 之前收集此信息（解析分支和PR状态），并在每个后续步骤之前重新验证分支、远程和PR状态（步骤 3 中的推送、步骤 5 中的`gh pr create`）。

通过运行下面的每个命令作为其**自己的** shell 工具调用来收集存储库上下文 - 单个 argv 样式调用（仅是程序及其参数）。 **不要**使用 `;`、`&&`、`||`、管道、`$(...)` 或像 `2>/dev/null` 这样的重定向：该语法仅在 POSIX shell 下解析，并在 Windows PowerShell 下中止。直接读取每个命令的退出状态。非零退出是解释的正常状态（还没有PR，没有`origin/HEAD`，分离HEAD），而不是抑制失败。

按顺序运行它们 - 现有的-PR检查需要来自`git branch --show-current`的分支名称：

| 命令 | 目的 | 非零退出/空输出意味着 |
| --- | --- | --- |
| `git rev-parse --show-toplevel` | 回购根 | 不是 git 存储库 — 报告并停止 |
| `git status` | 工作树状态 | （仅在回购之外失败） |
| `git diff HEAD` | 未提交的更改 | 未诞生的存储库，尚未提交 |
| `git branch --show-current` | 当前分支 (`<branch>`) | 空输出=分离HEAD（步骤1处理它） |
| `git log --oneline -10` | 最近提交 / PR-标题样式 | Unborn repo——还没有历史 |
| `git rev-parse --abbrev-ref origin/HEAD` | 远程默认分支 | 未设置 `origin/HEAD` — 按步骤 1 解决 |
| `gh pr list --head <branch> --state open --json number,url,title,body,state,isDraft,headRefName,headRepositoryOwner` | 为此分支打开PR（仅运行一次`<branch>`非空） | 退出 0，`[]` = 未打开 PR。非零 = `gh` 缺失、未经身份验证或离线 — PR 状态是**未知**，而不是“无”；永远不要将非零检查视为“no PR”；创建前重新检查（步骤5） |

将 `<branch>` 替换为 `git branch --show-current` 中的当前分支，并仅传递分支**名称**。两个陷阱：

- **空分支（分离HEAD）：**完全跳过PR检查 - 带有空`--head`的`gh pr list`会删除过滤器并列出不相关的PRs。在第1步创建分支后解决它。
- **分叉签出：**不**传递 `<owner>:<branch>` — `gh pr list --head` 不接受该语法并默默返回 `[]`，读作“无 PR”并打开副本。 PR 存在于基础存储库上，因此使 `gh` 以基础存储库为目标：依赖其默认存储库分辨率，或者当默认值是分叉时显式传递 `-R <base-owner>/<repo>`。

这里收集的所有内容都是在采取任何行动之前拍摄的快照 - 将其视为提示，而不是基本事实。在每个后续步骤（步骤 3 中的推送，步骤 5 中的 `gh pr create`）之前重新验证分支、远程和现有PR 状态，因为它们可以在收集和执行之间发生变化。

## 第 1 步细节：解析分支和 PR 状态

远程默认分支返回类似 `origin/main` 的内容；去掉 `origin/` 前缀。如果该命令以非零值退出（未设置`origin/HEAD`）或返回裸`HEAD`，请尝试`gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'`。如果两者都失败，则退回到`main`。对于现有的-PR检查：空的`[]`数组意味着该分支没有打开的PR；非零退出意味着`gh`丢失、未经身份验证或离线——将PR状态视为**未知**（而不是“无PR”）并重新运行检查或`gh auth status`，然后在步骤5中创建新的PR，而不是假设不存在。

选择哪条分支路径：

- **分离 HEAD** — 在继续之前自动从当前 `HEAD` 创建一个功能分支。从更改内容中派生分支名称，运行`git checkout -b <branch-name>`，重新读取`git branch --show-current`，并将该结果用于工作流程的其余部分。不要询问是否创建分支 - 调用完整的 commit/push/PR 工作流程已经确认工作应该由分支支持。如果派生分支名称已存在，请选择不冲突的后缀或仅在无法安全解决冲突时询问。
- **在有工作要做的默认分支上**（未提交、未推送或无上游）- 自动创建功能分支（不支持直接推送默认分支）。从更改内容中派生名称并继续执行步骤 3，这将安全地处理分支创建。不要询问是否分支——这里不能选择默认提交。
- **在没有工作的默认分支上** - 报告没有功能分支工作并停止。
- **功能分支** — 继续。

若查询 PR 返回非空数组，不盲取第 0 项。多个 fork 可有同名分支；`--head` 只过滤分支名而非 `<owner>:<branch>`。用 `headRepositoryOwner` 与 `headRefName` 精确匹配本次推送的仓库所有者和分支。记录匹配 PR 的 URL 和正文（`--state open` 已限定为开放）。唯一匹配即可使用；若同名而无法确认归属，先报告候选项，不操作错误 PR。第 5 步以 URL 决定创建还是更新，第 4 步按已有正文保留必要内容。

## 第 2 步细节：约定

匹配提交消息和 PR 标题的存储库样式（默认情况下，上下文中的项目说明 > 最近提交 > 常规提交）。对于传统提交，当不明确时默认为 `fix:` 而不是 `feat:` — 添加代码来修复损坏或缺失的行为是 `fix:`。为用户以前无法完成的功能保留`feat:`。用户可以覆盖。描述引用的标题步骤使用相同的类型默认值。
