# PR 描述写作

## 核心原则

差异已在 GitHub 上可见。描述的存在是为了解释差异无法显示的内容：以前不可能的内容现在可以实现，什么内容被破坏而现在已修复，什么形状发生了变化。删除读者可以从差异本身重建的任何句子。

- 错误（列出已编辑的内容）：“添加 `evidence-decider.ts`，修改 `ce-commit-push-pr/SKILL.md` 来调用它，并更新两个测试文件。”
- 好：“证据捕获现在可以自动决定更改是否具有可观察的行为。CLI 工具和库现在与 Web UI 一起符合资格。”
- 不好（说明工作是如何完成的）：“`ce-code-review` 的审查者角色现在将他们的检查锚定到指定的规范框架。”
- 好：“`ce-code-review` 现在发现了过去错过的九个缺陷形状，并且不再阻止那些唯一声称‘可以更好’的发现。”

如果领导者描述了编辑过的内容，而不是使用此功能的人现在有什么不同，请重写它 - 重申差异是该技能旨在防止的故障模式。用结果语法编写的机制是通过相同的条件来判断的：“现在将其检查锚定到命名框架”是工作的完成方式，而“是”读者得到的机制仍然存在 - 下面的散文规则决定了该线的位置。对于面向用户的错误，首先将可见的 before/after 命名；仅当有助于评估风险时才提及技术原因。

**散文。** 通过`ce-noslop`技能写出标题和正文。标识符、路径、协议和错误文本保留在它们“是”声明或审查目标的地方——不要将机制语言淡化为模糊的简单英语。

## 项目PR-本体合约

在编写之前，从上下文中已有的项目活动指令和约定中解决PR主体要求，然后检查标准PR模板位置（存储库根、`docs/`、`.github/`、`.github/PULL_REQUEST_TEMPLATE/`）以及它们引用的任何贡献指南。必需的标题、字段、顺序、清单和样板定义了结构合同。将模板视为最低限度，除非项目明确需要 exact/template-only 主体或禁止添加；然后才可以添加超出项目允许的部分。在每个允许的部分中，应用该引用文档的价值优先、决策成本、证据和编辑规则。当这些默认值与项目的 PR-body 合约发生冲突时，项目合约获胜。

## 步骤 Pre-A：解析范围和基数

两种模式：

- **当前分支模式**（默认）- 描述 HEAD 与存储库的默认基础。
- **PR 模式** — 当调用者传递 PR 引用时描述特定的 PR。

对于PR模式，首先获取元数据：

```bash
gh pr view <ref> --json baseRefName,headRefOid,url,body,state,isCrossRepository,headRepositoryOwner
```

如果`state`不是`OPEN`，报告并停止。将`baseRefName`用作`<base>`，将`headRefOid`用作`<head>`。

对于当前分支模式，按优先级顺序解析`<base>`：`git rev-parse --abbrev-ref origin/HEAD`（剥离`origin/`）→`gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'`→通过`git rev-parse --verify origin/<candidate>`尝试`main`/`master`/`develop`。如果没有解决，请询问用户。 `<head>` 是 `HEAD`。

**基本远程：** `origin` 适用于当前分支模式和相同仓库 PRs。对于叉子 PRs，将 PR 的基部 owner/repo 与 `git remote -v` 进行匹配。如果没有本地远程匹配，请跳到 `gh` 后备 — 不要与 `origin` 进行比较（错误的基数）。

```bash
git fetch --no-tags <base-remote> <base>
git fetch --no-tags <base-remote> <head>   # PR mode only: <head> is headRefOid and may not be local
git log  --oneline "<base-remote>/<base>..<head>"
git log  --format=fuller "<base-remote>/<base>..<head>"   # full commit messages for related-reference discovery
git diff           "<base-remote>/<base>...<head>"
```

如果提交列表为空，则报告“没有要描述的提交”并停止。

**后备** — 当本地 git 无法到达引用时使用 `gh pr diff <ref>` 和 `gh pr view <ref> --json commits`（分叉 PR 没有匹配的远程、浅克隆、离线、基于不相关历史的合并）。对于拒绝 SHA 获取但允许 `refs/pull/` 的 GHES：

```bash
git fetch --no-tags <base-remote> "refs/pull/<number>/head"
PR_HEAD_SHA=$(awk '/refs\/pull\/[0-9]+\/head/ {print $1; exit}' "$(git rev-parse --git-dir)/FETCH_HEAD")
```

请注意在面向用户的摘要中何时使用 API 后备。

## 步骤 A：调整描述大小

**大小取决于决策成本，而不是差异形状。**决策成本是审查者在批准之前仍需要计算出的量；它没有改变行数、文件扩展名或视觉表面。与 500 行机械重命名相比，5 行排名或部署更改可能会给审查者带来更多不确定性。

从**完整的单行提交列表和最终的三点差异**构建紧凑的内部**范围图**。使用oneline科目进行全方位覆盖；使用最终的差异来合并重叠，放弃仅修复的工作，并纠正陈旧的主题；仅当主题仍然不透明或与差异冲突时才查阅更完整的消息。将其分为实质性成果集群（一个即可），命名涵盖它们的一个总括成果，并确定每个集群的**实质性声明**——什么是可能的、固定的、风险较大的，或者审查者必须评估哪些设计决策。

将雨伞表述为对于使用它的人来说现在是不同的，而不是表述为产生它的机制。标题和开头都继承了地图的描述级别，因此机械形状的伞不是后续步骤可以纠正的东西 - 每次后续检查都会与它进行比较并同意它。从整个范围中得出保护伞，而不是从最新的提交、跟踪器标题、分支名称、原始请求或工作如何开始的故事中得出保护伞 - 打开分支的事件、错误报告或请求是一个集群的起源，而不是保护伞，并且在范围提供对等结果时引导它的描述误读了地图。

地图不是主体内容：不要扩展主体来枚举伞已经覆盖的集群。 **按运行时用途而不是扩展名对每个更改的文件进行分类**（markdown/YAML可能是惰性文档或运行时代理指令、配置、产品内容或部署行为）。陈述差异本身无法证实的主张；其余的保持隐式。

**程序高度（多PR/系列）。**程序高度是指该PR位于较大作品中的位置。在PR-本地映射之后，检查此PR是否位于更大的程序内（多PR项目、堆栈、系列、多单元计划）。仅使用现有的信号：用户prompt/conversation、已知的计划路径、现有的PR正文、提交消息或上下文中的sibling/series语言。不要**发明一个系列，也**不要**仅为此步骤运行存储库范围内的 open-PR 扫描。

当存在项目上下文时，将图扩展为： (1) **项目结果** — 用一句话来实现端到端交付； (2) **这个PR的贡献**——当地的保护伞； (3) **邻居** — 先前工作（**导入**）and/or 剩余工作（**导出**），每个仅在已知时进行。地图的顺序是**程序→导入（如果有）→此贡献→导出（如果有）**；步骤 C 决定开口携带多少。早期PRs需要引出；中间需要两者；后期需要导入（并说当 true 时弧完成）。当未知时省略前一个或下一个——两者都不要发明。审查者无法从这个 PR 的差异中获得程序安排，这本身就是决策成本。当程序上下文不存在时，仅保留 single-PR 保护伞。

- 不好（对于中间PR来说太本地化）：开头“问题关闭现在撤销服务器上的活动会话”。没有放置在身体的任何地方。
- 好：同样的开头，然后是一个块：“在刷新路径拒绝后继续会话撤销重写；多设备撤销仍然是后续的。” - 结果是独立的，因此该块添加了程序及其邻居，而不是结果的第二个副本。
- 好（结果并不独立）：“会话现在带有一个撤销纪元 - 该字段使服务器端撤销成为可能。还没有任何东西读取它。”在这里，程序是赋予变化其意义的部分，因此连接是开场一个想法的一部分，而不是其后的一个块。
- Early/late：命名第一个切片 + 残差，或完整弧 + 已经落地的内容 - 相同的三个字段，省略未知邻居。

**在编写之前写下完成的地图** - 在程序高度检查之后，因此它带有两半：雨伞；集群及其主张；程序放置或“无”（三行或四行）。步骤E根据这张书面地图而不是记忆来审核开口。

> 更喜欢仍然让审查者决定的最短描述 - 上下文（包括存在的程序放置）、证据和他们无法从差异中获得的剩余不确定性，以及他们无法获得的东西。

决策成本提高了内容底线，而不是长度上限（高不确定性*小*差异会获得更明显的领先优势，而不是论文）。不确定性最多会在下表中移动一行。除非PR已经很大，否则将风险纳入叙述中。仅当证据改变对重大主张的信心时才包含证据。放置在身体中的测量数字命名了它的界限，例如它的样本计数和分布、它的工作负载或它清除的阈值。结果，不会声明没有界限的数字：将其标记为不确定或将其忽略。调整大小时减去修复提交。大PRs需要更多选择性，而不是更多内容。

| 更改个人资料 | 描述方式 |
|---|---|
| 小 + 简单（打字错误、配置、dep 凹凸） | 1-2 句话，无标题。大约 300 个字符以下。 |
| 小+不平凡（错误修复、行为改变） | 3-5句话。除非有两个不同的问题，否则没有标题。当错误可观察到时，用户可见before/after。 |
| 中等功能或重构 | 开头（一两个句子），然后只有每个部分回答一个剩余的审稿人问题；提出设计决策。 |
| 大型或具有建筑意义的 | 同样，加上 3-5 个设计决策标注和一个简短的测试摘要。目标 ~100 行，上限 ~150 行。许多机制→汇总表，而不是每个机制的 H3。 |
| 性能提升 | Before/after 测量值作为Markdown表。 |

项目PR-主体合同设置了结构楼层；该表调整了其中的内容，而不是与之相反。小+简单：价值主导的句子就是整个描述。

**中号和大号：读者可以在任何地方停下来。**开头是一两个句子，承载一个想法——现在不同了，它取代了差距或失败——所以停在那里的审稿人知道PR的作用。步骤 C 决定该想法必须包含哪些内容以及该想法之后的块中应包含哪些内容。每个进一步的部分都是为了回答审稿人剩下的一个问题；项目符号是一个子句，其推理是根据设计决策而不是在项目符号内部进行的。故意推迟的范围已声明一次。显示哪些部分和设备取决于审查者仍然无法从差异中获得的内容（视觉辅助工具，步骤 C）——这不是部分列表。

## 步骤 B：撰写标题

`type: description` 或 `type(scope): description`。使用与技能步骤 2 相同的 `fix:`/`feat:` 默认值按意图键入。范围（可选）：最窄的有用标签。描述：从范围图的总体结果来看，不是一个集群或机制；根据项目背景，标题可以在项目下列出PR的贡献，而无需重述整个系列——它不能让另一个重大成果听起来是偶然的。命令式，小写，少于 72 个字符，无尾随句点。匹配最近提交约定。 **未经用户明确确认，切勿使用`!`或`BREAKING CHANGE:`。**

## 步骤B1：解决相关工作参考

在编写正文之前，从用户提示、调用者切换、分支名称、完整提交消息、现有 PR 正文、PR 模板、plan/debug 注释以及上下文中的可见 URL 或 ID 收集候选工作项引用。重写 PR 时保留现有的相关引用，除非用户要求删除它们。

此步骤决定**跟踪器** close-vs-link 语义。兄弟PR/系列叙述属于步骤A的程序高度，而不是在这里——上下文中已经存在的兄弟PR编号在有用时仍可能显示为非关闭相关参考。

将每个候选人分类为：

- **结束引用** — PR 完全解析该项目，并且跟踪器的结束语法是已知的。
- **非关闭参考** - 相关、部分、调查、后续、仅验证或跟踪器语义未知。
- **不确定** — 跟踪的 bug/incident/investigation 清晰，但缺少 ID 或关闭与链接意图。询问（交互式）或使用非关闭/省略（非交互式）；永远不要发明结束语。

不要发明结束关键字。魔术词是工作流程操作，而不是装饰。如果不明确、中立的相关引用文档或省略 — 不要将 ID 分散在摘要中。

不要在散文中的close/fix/resolve/address/report措辞旁边放置非结束引用。用一句话写出行为范围；单独放置跟踪器 ID。准确使用表格的非结束参考标签；不要替换诸如 `Refs`、`References` 或 `Toward` 之类的同义词，除非项目记录的跟踪器约定需要一个同义词。对于非结束引用，跟踪器 ID 仅出现在相关引用句子或块中，而不会出现在 summary/opening/body 散文中。

- 坏：“从 #123 开始关闭一条腐败路径”
- 不好：“这解决了 #123 中报告的与重试相关的损坏路径。”
- 好：“这涵盖了重复行重试路径；并发取消仍然是后续工作。”
- 好：“相关：#123”

| 追踪器 | 结束参考 | 非关闭参考 | 笔记 |
|---|---|---|---|
| GitHub 问题 | `Fixes #123`；交叉仓库：`Fixes owner/repo#123` | `Related: #123`；交叉仓库：`Related: owner/repo#123` | 结束关键词：`close(s/d)`、`fix(es/ed)`、`resolve(s/d)`。仅当 PR 针对默认分支并真正解决问题时才使用关闭。每期结束时重复关键词。 |
| 线性 | `Fixes ENG-123` | `Related to ENG-123` | PR 描述中的魔术词，而不是 PR 注释。当意图匹配时，多个问题可能会共享一个神奇的词，例如`Fixes ENG-123, DES-5 and ENG-256`。 |
| 其他追踪器 | 项目记录的结束关键字仅在已知时才记录。 | `Related`下的完整 URL 或跟踪器 ID。 | 永远不要猜测关闭动作。 |

当主体很小时，结束引用可能会存在于开口中。非闭合引用总是在 validation/evidence 之前有自己的句子或 `## Related` 块。一次真正的平仓可以是单线 (`Fixes ENG-123.`)；混合项目将结束项目符号和非结束项目符号分开。

## 步骤B2：判断新概念

确定更改是否引入了本存储库的读者可能不知道的概念（模式、技术、库、领域思想）。当技能的概念教学门关闭时完全跳过（SKILL.md步骤4）。

**首先从 Pre-A diff 中收集候选者**（第一次真正使用依赖项、diff 引入的技术、代码现在编码的领域思想）。大多数 PRs 都没有 — 停止；缺席是常见情况。

**根据基本引用检查每个候选者，而不是工作树**（工作树包含此 PR 自己的代码）：

```bash
git grep -il -e "<term>" "<base-remote>/<base>" | head -5
```

每个候选人一次通话（上限第二）。输出为空 → 底座不存在。仅当新的*和*可转让时才可教授。永远不要教：既定模式、普通refactors/renames/dep颠簸、项目内部管道。如有疑问，请省略。在 `gh`-后备路径上，仅根据 diff 上下文进行判断并倾向于保守。

- 不好：在 DI 密集的代码库中为一个新的构造函数参数教授“依赖注入”。
- 好：在 PR 上教授无限滚动，首先用它代替分页。

**在 `## New concepts` 下撰写**（步骤 C 放置它），最多 2 个概念（每个约 10-25 行）：(1) 简单来说是什么，(2) 为什么在这里与明显的替代方案相比，(3) PR 中的一个示例，(4) 何时不使用它。对于架构，更喜欢美人鱼，对于机制，更喜欢短代码块，对于权衡，更喜欢表格。浓密就好；长则不然。切勿手绘方框图。添加到步骤 A 的尺寸调整 — 不计入尺寸行。

重写时逐字保留现有的 `## New concepts` 部分和解释文档链接（与 `## Demo` 相同的规则），除非用户的焦点要求刷新。 Description-only/update 永远不要写 repo 文件。 **存档** 当第 5 步确认应用且 `pr_teaching_archive` 打开时：内容 → `<root>/explainers/` 根据 `references/apply-and-handoff.md` 中的“解释器存档”。

## 步骤C：组装车身

当项目PR主体合同提供标题或订单时，保留该结构并将适用的元素放置在其允许的部分内。否则：打开→正文部分，每个部分回答剩余的审稿人问题→当他们需要自己的块时相关参考→测试计划（如果不明显）→当标签计划在手时会议解决的出处→步骤B2产生一个新概念部分→证据块（如果存在）→当步骤D需要时进行品牌化→当贡献者信用需要时共同创作预告片。

当项目 PR-body 合同提供开头的标题或位置时，将其放置在那里，而无需发明或重命名标题。否则，如果正文使用任何 `##` 标题，开头将位于 `## Summary` 下；否则就是裸段落。第一个标题上方没有孤立的开头。

开头带有一个想法。测试的是只读了它的审稿人是否能说出这个PR改变了什么以及为什么它会变成这样。通常，一个想法本身就是本地结果 - 地图的“此贡献”槽。有时，局部结果并不能独立存在，因为项目赋予了它其形状或意义。然后，与程序的联系是一个想法的一部分，属于开场白，任何一半都可能导致——无论哪一个对于这一改变来说读起来更好。命名该PR提供的程序的哪一部分是保持该开场诚实的原因——一个命名弧线的开场，但让审查者无法说出该PR改变了什么，无法通过相同的测试。一个想法不需要的所有东西——弧线的其余部分、延迟的范围、差异提供的实现细节——在开始后立即放入一个短块中。该块提供程序结果以及已知的导入和导出，并且从不重述结果。

当“原因”是结果形成的原因时，“原因”就属于该想法的内部；而当“原因”是支持已经存在的结果的证据时，“原因”就属于该想法的下方。扩大开头直到两者都适合是失败的：过去的两句话它带有第二个想法，无论它被标点什么。

**会话解决的出处：**当一项计划已经在手（调用者路径或对话）时，其关键技术决策带有 `session-settled:` 标签，一个静态句子命名解决的决策和类（例如，“从规划中进行的会话解决的决策：X（用户主导，超过 Y）；Z（用户批准）。”）。仅当调用者标记它们时才添加冲突下继续子句。从来没有未完成的项目分类账；当没有计划在手时，永远不要寻找计划。

**贡献者信用：** 仅当此 PR 由作者以外的其他人发布作品时才适用。对于现有的PR，作者是PR的作者；对于新的PR，它是交付人，其身份是配置的`git config user.name`和`user.email`（他们也可以在另一封电子邮件下提交）。证据是由这样的人编写的 Pre-A 提交、命名其中一个的 `Co-authored-by` 预告片，或者这项工作继续或取代另一个 PR。模型、工具和机器人属性永远不会被计算在内。否则什么也不加。

如果适用，请在正文中列出这些贡献者的名称，并链接 PR 这项工作将继续或在有时替换。重写时，保留现有的贡献者信用。

壁球合并为每个 PR 保留一位作者，因此其他贡献者只能作为壁球消息中的预告片幸存下来。如果存储库压缩合并（其记录的约定，或 `squashMergeAllowed` 来自 `gh repo view`），则以 `Co-authored-by: Name <email>` 预告片结束正文，每个贡献者一个。它们是正文的最后一段，位于任何模板部分之后，因此当正文成为挤压消息时 git 会解析它们。准确复制提交作者或现有预告片中的每个身份；对于其提交不在范围内的替换的PR，请从PR的提交中读取它们。切勿猜测或构建电子邮件：没有贡献者将仅注明姓名。

**证据：** 保留现有的 `## Demo` / `## Screenshots`，除非焦点要求刷新或稍后提交更改其屏幕截图显示的内容 (`references/visual-evidence.md`)。将调用者传递的捕获拼接为`## Demo`，并将本次运行的屏幕截图作为`## Screenshots`。放置在徽章之前。切勿将测试输出标记为“演示”或“屏幕截图”。 SKILL.md 步骤 4（通过 `references/compose.md`）决定是否包含验证注释或跳过它们。

**视觉辅助：**图表或表格比散文更快（流程、权衡、可观察行为改变时的before/after比较）；仅当审查者从错误的位置开始时才提供导航提示（从哪个文件开始，或者审查者可能会错过的小但决定性的块）——绝不是已更改文件的列表，差异已显示；跳过所有这些simple/rename/dep-bump。内容模式决定，而不是大小或文件数量。散文胜于冲突。 **GitHub：**永远不要在列表项前添加`#`前缀（自动链接作为问题）；使用 `org/repo#123` 或完整 URL 来获取真实参考。使用完整 URL 链接存储库文件，例如 `gh browse -n --commit=<head-sha> -- <path>` 打印的内容：相对路径在 PR 自己的 URL 和 404 下解析。 PR 未提交的文件（例如本地测试输出）不会获得链接。

## 步骤 D：通用 Compound Engineering 品牌

对于**新的PR主体**，仅当解析的品牌门打开时才附加以下内容；否则省略它。

```markdown
---

[![Compound Engineering](https://img.shields.io/badge/Built_with-Compound_Engineering-6366f1)](https://github.com/EveryInc/compound-engineering-plugin)
```

请勿将型号或宿主属性添加到**此品牌块**。如果项目的PR主体合同要求model/harness披露，请根据项目合同填写*该*部分（请参阅“项目PR主体合同”）。

对于 **现有的 PR 主体**，逐字保留现有的品牌块（包括旧版 model/harness 徽章）。切勿在不存在时添加内容，也切勿刷新、标准化或删除它，除非用户明确要求删除或替换该确切内容。品牌本身永远不会产生重写意图。

## 步骤 E：预申请覆盖范围审核

在返回标题和正文之前，请对照步骤 A 中的范围图和材料声明进行检查，如果错误则进行修改：

- 保护伞本身是一种结果——对于现在使用它的人来说有什么不同——而不是产生它的机制吗？在下面的两个问题之前先检查一下：两者都与伞进行比较，因此当伞是机制形状时，两者都同样容易通过。
- 标题是否表达了总体结果而不是一组或机制？
- 开头是否表达了相同的保护伞——每个同行的结果都以地图命名，平等——而不是工作开始的集群？如果地图具有三个对等结果，并且开场以其中一个开头，并将其他结果提到“也”或“附带”，则从地图中重写它。
- 开头是否用一两句话表达了一个想法，只读了它的审稿人能否说出这个PR改变了什么以及为什么它会变成这样？尚不了解该项目的读者是一个测试。如果没有程序，本地结果看起来没有动机，那么开头就缺少这种联系。如果开头指定了弧线，但审查者无法说出该 PR 提供了它的哪一部分，则它会错过结果。移出某个想法不需要的任何内容——其余的弧线、延迟或差异已经提供的实现细节。根据上述散文规则，本身就是结果的机制（原子性、协议或API保证）保留在开头。
- 是否有任何部分、表格或提示重申了“文件更改”选项卡或差异已显示的内容？剪掉它。是否有任何部分回答了审稿人剩下的问题？剪掉它。
- 每一个物质成果都是由伞框或主体代表的，还是因为它只是支撑而故意省略的？
- 是否存在差异无法证实的每项主张——以及差异*确实*显示的任何主张都不必要地重述？
- 是否确实检查了程序高度（地图上显示“无”或为程序命名）？当程序上下文存在时：引导是否将这个PR放在弧上（程序+这个贡献，当已知时引入引入and/or引出）？当程序上下文不存在时：身体会发明一个多PR系列吗？如果是这样，就剪掉吧。
- 改变决策的证据是否是一个既定的结果（不是无法解释的“测试通过”），所证明的结果与假设和mixed/negative结果不同？
- 是否可以在不降低审查者信心的情况下删除*描述*的任何句子或部分？如果是这样，则将其删除，但项目的 PR 正文合同所需的标题、字段、清单或样板除外。启用时保留步骤 D 品牌、步骤 C 包含时保留会话确定的出处句子、步骤 C 包含时保留贡献者信用 — 所有这些都是有意为之，而不是无稽之谈。
