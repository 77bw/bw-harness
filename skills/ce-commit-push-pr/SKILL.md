# Git 提交、推送和 PR

**询问用户：**使用当前工具列表中已有的主机阻塞问题工具（按功能匹配，而不是按主机特定名称匹配）。当前工具列表中的存在证明该工具存在；永远不要调用面向用户的提问工具来发现它是否存在。如果列出了匹配的工具但已卸载，请使用主机的工具发现原语来加载该功能 - 不要搜索另一个主机的工具名称。仅当列表中没有此类工具或真正的问题调用错误时才回退到聊天中提问，并且永远不要默默地跳过问题。

## 模式

- **仅描述** — 用户只需要*一个描述（“write/draft一个PR描述”、“描述这个PR”、粘贴的PR URL或数字）。仅运行步骤 4 并打印它。仅在要求时应用。传递任何粘贴的 PR 参考，以便 Pre-A 解析范围。
- **描述更新** — 刷新或重写现有 PR 的描述，无提交或推送意图。通过以下上下文规则解析 PR 存在：退出 0 `[]` 是“无打开 PR”（报告并停止），非零退出是 **未知**（解析身份验证或连接，然后停止，直到知道存在）。 **打开 PR** 后，在该 URL 上以 PR 模式运行步骤 4，然后通过 `gh pr edit` 预览、确认和应用步骤 5。
- **完整工作流程** — 否则：步骤 1-5。当意图或偏好需要堆栈时，请输入 **堆栈模式**。

**`mode:pipeline`修饰符**，由精心策划的调用者设置，例如`lfg`。以非交互方式运行已解决的模式并抑制每个阻塞询问。每个抑制的询问都采用保守的默认值：没有现有的-PR重写，保留分支，无法解析的基础停止而不是猜测，并且直接应用描述更新预览，因为该调用是应用意图。管道堆栈模式仅使用调用的意图和范围，并将状态传递到切换中。

## 堆栈模式（选择加入）

**仅选择加入。** 当意图或长期偏好需要多个PR堆栈时输入它。显式堆栈请求是**必需的意图** - 不要将其作为具有自定义 `--base` 的单个 PR 重新读取。 **不要**主动建议 PR 堆栈。当用户**不**要求一个时，**拒绝**无意义的堆栈（一个逻辑更改，人为切片）并保持单一PR。

在堆栈模式下，在步骤3**之前加载`references/stack-submit.md`，并仅遵循其探测、拓扑和追溯构造；逐层提交流程取代了普通的步骤 3。 **不要在那里提交。** 步骤 5 处理提交、`gh stack` CLI 依赖项和残差，以及切换姿势：默认情况下`posture:stack-ready`，`posture:stack-land` 仅在明确的土地意图上，从 **底部打开非草稿** PR。请勿在该技能的参数提示中添加`posture:`。

## 语境

**在步骤 1 之前阅读 `references/context.md`。** 它定义了命令表、退出代码含义、fork 和 detached-HEAD 陷阱，以及步骤 1-2 使用的分支和 PR 解析。它的两条规则也属于这里。永远不要问是否要分支：一个分离的HEAD，或者有工作的默认分支，会创建一个，而没有工作报告的默认分支会停止。对于传统提交，当不明确时默认为 `fix:` 而不是 `feat:`，除非用户覆盖。

跑步遵循三个规则。

**每个`git`和`gh`探针都是它自己的argv形式调用**，收集和重新验证类似，其退出状态是控制流。引用文档给出了原因并命名了该技能所钉的两个复合配方。

**探测输出是快照。** 在每个后续操作之前重新验证分支、远程和 PR 状态：步骤 3 的推送、步骤 5 的创建。

**仅针对基础存储库的查询中的 exit-0 `[]` 表示“未打开 PR”。** 非零退出是 **未知**，绝不是“无”。在分叉签出时，使用 `-R` 定位基础并仅传递分支名称，因为 `--head <owner>:<branch>` 默默地返回 `[]`。对于结果，不要**盲目地采用索引 0：匹配头所有者和分支，并在不明确的匹配上停止。请注意该条目中的 URL 和正文 — 步骤 5 使用 URL 选择现有的-PR 路径，步骤 4 重写现有正文。

## 第 3 步：承诺并推动

**阅读 `references/commit-and-push.md`** 了解 commit/push 机制以及通过 `references/branch-creation.md` 进行的默认分支处理。如果堆栈模式提交了其层，则跳至步骤 4；第 5 步提交它们。

**项目发布门。** 在发布提交之前，从项目的活动指令和上下文中已有的约定以及管理提交路径的任何其他范围指令中解决每个适用的预推送或审查就绪要求。只有对所发送的确切提交状态有效的证据才能满足他们的要求；否则在外部写入之前停止并报告丢失或失败的内容。如果没有，请继续。当输入和相关环境不变时，重用先前成功的检查；单独的新提交 ID 并不会使它们失效。捕获输出时保留每个检查的实际退出状态，并在发出发布调用之前完成对门的评估。

切勿使用 `git add -A` 或 `git add .`。在添加和提交中命名文件，以便排除不相关的暂存文件。荣誉`exclude:<paths>`：离开并举报。

## 步骤 4：撰写 PR 标题和正文

**您必须完整阅读`references/pr-description-writing.md`** - 它定义了标题和正文内容规则，包括在重写时保留现有`Related:` / `Fixes` 的规则。然后阅读 **`references/compose.md`** 了解在撰写之前要做出的三个决定：证据决定，当 diff 更改渲染 UI 时决定屏幕截图；教学决策，其中`pr_teaching_section`默认**打开**，`pr_teaching_archive`默认**关闭**，并且只有**活动（未注释）**键发生变化；以及品牌决定，其中品牌**关闭，除非**此调用携带`branding:on`或用户在此提示中要求Compound Engineering品牌。

每次运行时都要阅读这两个引用文档，即使本次会话已经阅读了它们。跳过 `compose.md` 会跳过证据决策。

如果步骤 1 找到现有的 PR，请将其 URL 传递给步骤 4，以便 PR 模式获取现有的正文。

## 第5步：申请并报告

**阅读 `references/apply-and-handoff.md`** 了解应用、预览、存档和移交。在`gh pr create`之前，重新检查PR是否存在：匹配的PR采用现有的-PR路径，exit-0`[]`创建非零块。通过 `--body-file <path>` 传递主体，绝不是 stdin — `gh` 以空主体退出 0。

**此处决定完成。**交互式完整工作流程或管道堆栈提交**未完成**，直到 `ce-babysit-pr` 拥有已发布的 PR 的后续内容。仅报告 PR URL 并不成功。加载被叫方选择监听模式。如果在此会话中运行它，则继续，直到其停止条件允许最终报告，仅当其武装唤醒源将该代理带回来时才结束转弯。

只有 `babysit:off`、CE 配置的 `auto_babysit: false` 或 `references/apply-and-handoff.md` 中的“不触发”情况会跳过它。请求 PR 链接、返回报告或不合并都不是跳过。没有其他手表可以替代这种交接：不是`ci-watcher`，不是`gh pr checks --watch`，不是主持人本身的PR手表工具，不是手动投票，不是“稍后”。 `ce-babysit-pr` 决定它如何被唤醒。如果`ce-babysit-pr`无法加载或启动，则停止并报告其阻塞。
