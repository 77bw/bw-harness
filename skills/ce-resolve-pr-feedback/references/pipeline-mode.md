# 管道模式

当调用携带 `mode:pipeline` 时阅读此内容 — 由 `ce-babysit-pr` 或 `lfg` 等编排器设置。其行为与普通完整或目标模式完全相同，但存在三个差异。

## 1. 切勿调用阻塞问题工具

出于任何原因。跑步是无人看管的。阻塞问题会阻碍调用编排器的循环；没有用户可以回答它。

## 2. 保留类型化的决策残差

没有人会在无人值守的运行中读取交互式摘要，因此 PR 线程是记录所在的位置。对于每个 `needs-human` 项目，将其 `decision_context` **发布在其线程上作为回复**，简明扼要：该项目是什么，为什么需要人工调用，选项和您的精益。然后让该项目覆盖的所有线程保持打开状态。带有该回复的开放线程是持久的记录，在人们会看到的地方。切勿解析 `needs-human` 线程。切勿编写自己的 PR-body 部分来列出未决决定。勾选修复已关闭的 `## Unapplied review findings` 项目符号是另一回事，并且仍然是允许的； SKILL.md 定义了该规则。发表回复只是为了进行分析，而不仅仅是为了指出线程已打开。

完全按照标题定义返回 `needs-human` 对象：`type: "needs-human"`、`sources` 列出该项目涵盖的每个线程、评论或评论正文的稳定获取的 ID 和类型、`decision_context.quoted_feedback`、`decision_context.investigation`、`decision_context.decision_reason`、`decision_context.options`、`decision_context.recommendation` 和 `thread_urls`。 `thread_urls` 必须包含该项目涵盖的每个仍打开的线程。仅当所涵盖的源不是审阅线程时，它才可能为空。将该对象原封不动地返回给调用者。发布的回复本身并不是完成的交接；仅当决策有效负载到达顶级协调器时，切换才完成。

## 3. 不收敛（错误方法集群/跑步机）

调用者可以传递 `trajectory`：上升的 `unresolved_trend`、跨越传递的 `new_threads_this_tick > 0` 或任何 `invariant_rounds[].rounds >= 2`。当出现这种情况时，根据反馈的来源进行分组，并在修复任何问题之前决定如何处理每个根：

- **升级** - 在方法层面上对根决策本身提出**一个** `needs-human`（例如“正则表达式在这里是错误的工具 - 选项：详尽的表/真正的解析器/接受已知限制；精益：……”），并在**任何修复、提交或推送之前执行此操作。除非评估准则的权威约束条件成立，否则根本决策是受判断约束的，因此它首先会经历评估准则的“升级前裁决”步骤；信封内的裁决将作为该根的下一个修复应用，并且仅当裁决无法做出决定时才会提出升级。在两种情况下升级。首先，根的反馈“明显”不收敛：几个尼特共享一个根，“你的正则表达式错过了案例X”在X之后重复X，或者机器人在每次提交后重新发布新的尼特没有结束。其次，修复将开始根的第三个记录回合：`invariant_rounds[].rounds >= 2`对于密钥，此传递将继续（修复完成后记录回合）。
- **执行已回答的升级** - 当打开的线程已经在根上承载了人类的决定时，该答案将授权下一步操作；应用它。不要再次提高相同的`needs-human`；呼叫者的记录存储拒绝重复。
- **否则像往常一样修复** - 一批正常的不相关的有效尼特只需一次修复即可。

在**修复**结果中，为**每个**根返回一个稳定的`invariant_key`（`A-Za-z0-9._:-`的1-120个字符），以及根覆盖的线程和评论。固定在一次传递中的无关根携带不同的密钥，因此每个根都会累积自己的轮数。不要运行`pr-snapshot`；调用者记录该项目的已发送标记上的每个键。
