# 评价标准

**协调器**应用此来决定**在**发送任何修复之前**每个项目的结论。这就是决定有效性的地方：判断在这里发生，在同时容纳每个线程的一个上下文中，而不是在无法看到作者设计意图的孤立修复程序中。当判决开启时阅读实际代码；永远不要仅根据评论文本来判断有效性。

应用此评分标准的输出是每个项目的判决，分类为：
- **修复列表** -- `fixed` / `fixed-differently` 意图；发送给修复者。
- **回复列表** -- `replied` / `not-addressing` / `declined`;回复此处撰写的文本（您手头有证据），无需更改代码。
- **人类列表** -- `needs-human`; `decision_context` 在此创作。

## 默认为修复

大多数评论反馈（包括 P0-P2，包括挑剔的内容）都是正确的，值得修复。处理列表并修复：当比建议的方法更好的方法是正确的选择时，判决`fixed`或`fixed-differently`。根据每个项目的优点来判断，无论其来源（人工审查者或审阅机器人）或形式（内联线程、正式审阅机构或顶级评论）——正确性并不取决于谁提出它或在哪里提出。

下面的检查是您在阅读时注意到的具体信号，而不是针对每个项目仔细考虑的清单。当没有信号出现时，标记要修复的项目并继续；不要制造怀疑或风险来逃避工作。 “我感到不安”并不是一个信号，而是一个信号。 “我读了来电者的信息，这打破了X”。

**有效的修复是项目的调用，而不仅仅是危害。**如果项目的活动说明和约定已经在您的上下文中包含审查或创作指南（发现是什么，如何应用对一类文件的反馈），请将其应用于此处作为判决的框架，而不仅仅是作为下面“修复会使代码变得更糟”下的否决。当这些说明将文件类别的反馈路由到项目本地技能或过程时，请在判断该类别的项目之前调用或阅读它。如果它说某类发现已得到解答而不是固定，那就是结论。

## 指令散文不是代码（技能、代理提示、规则文件）

当目标文件是代理指令散文时——`SKILL.md`、技能的`references/`、角色或系统提示、项目规则文件——“默认修复”不会转移，因为风险以另一种方式运行：自然语言条件总是可以变得更加具体，因此审查者可以无限期地针对任何规则产生看起来有效的边缘情况，并且修补每个规则会稀释而不是加强规则。对于这些文件：

- **所述条件已经决定的情况不是修复。**阅读查找目标的规则并询问其条件是否涵盖该情况（“仅在分支从未发布的肯定证据上重命名；任何其他结果保留名称”已经决定无法访问的远程）。如果是 -> `not-addressing`，引用条件。如果是一个问题 -> `replied`。
- **仅修复条件或层。** 当条件本身错误或缺失（目标、完成状态或安全故障方向）时，或者当执行该工作的技能的机制位于错误的文件中（在委托该工作的技能中规定的命令；放置在代理在应用时不会读取它的位置的规则）时，标记为修复。然后，您交给修复程序的修复指令是“将条件重述为...”或“将其移动到<执行该操作的文件>”，而不是“添加案例”。
- **针对此 PR 的前一轮添加的文本的发现意味着规则表述错误，而不是它需要更多情况。** 检查分支上的 `git log` 是否有接触同一块的早期审查修复提交。在针对同一块的第二轮中，停止修补：将该块上的每个发现折叠到**一个类项目**中（所有反馈 ID 和评论文本，因此修复程序会看到重述必须仍然提供的每条路径），并指示“删除添加内容并重述此块作为其目标、完成条件和安全方向；重新验证所提供的添加内容的每个路径，包括本轮的发现不会重新引发的任何路径”。一个修复者重述一次，并且每个覆盖的线程都会得到回复并根据该结果得到解决。这适用于块，而不是PR；其他文件仍得到普通判断。
- 相同PR（脚本、测试、源代码）中的普通代码保留普通的标题。

## 读多深

阅读足够的内容来决定判决，不再阅读：

- **清晰的nit或明显有效的发现**（拼写错误，差异已经显示的错误，命名）->注释加上差异中已有的行就足够了。标记以修复。
- **有争议的发现，或看起来是故意的代码**（该发现断言代码有一个错误，其中代码有意读取、触及不变量或与附近的模式相矛盾）-> 在接受之前进行深入阅读：打开引用的文件，读取调用者，检查不变量或测试是否会使审查者出错。 **这是一个自信错误的审查者被抓住的地方。** 新的审查者——尤其是机器人——通常看不到代码还取决于什么，或者代码是这样的原因。
- **在覆盖有意为之的代码之前恢复作者的意图。** `git log`/`git blame` 行，阅读 PR 描述和周围的代码。作者的意图是孤立的审稿人所缺乏的；将其与发现进行权衡，而不是假设审稿人看到了更多。
- **Dedup 按文件读取。** 同一个文件的多个线程：读取一次，一起判断。

## 跨项目推理（当判断多个项目时）

你可以同时持有每个线程——使用它：

- **按根本假设进行聚类。** 如果一个来源（通常是机器人）在多个线程中提出相同类型的主张，并且您发现它在一个地方不成立，请仔细检查兄弟姐妹：一个系统性错误的前提会产生一组看似合理但错误的发现。这是集中判断而不是每个孤立代理的最大优势。
- **汇聚请求是一个强烈的修复信号。** 多个独立审查者要求的相同更改很少需要转移。
- **经过验证的发现可以跨越 PR 本身引入的站点（修复类，而不是一个实例）。** 这是错误审查者集群的镜像：审查者通常会标记一次出现的情况，而不是全部。当您接受调查结果时，请检查此更改是否还引入或触及了受**相同不变式**管辖的*其他*站点，这些站点承认**相同的修复，无需针对特定站点进行判断**。当这些站点是具体可识别的并且它们的处理是明确的时，将它们折叠到**一个**类修复中（参见完整模式步骤3），这样未标记的双胞胎以后就不会回来了。保持类范围狭窄：仅行为**此PR更改**，而不是触摸文件中每个预先存在的事件；排除任何不变或正确处理不同的站点（文档与代码与固定装置、兼容性或有意保留的路径）。如果等效或处理本身就是一种判断，请将它们分开——错误的“类完成”比多一轮更糟糕。
- **对早期审查修复添加的代码的发现询问该修复是否是正确的层。** 检查发现的行是否来自此分支上较早的审查修复提交（这些行上的`git log`或`git blame`）。如果他们这样做了，那么早期的修复和这一发现有一个共同的前提：失败需要更多代码。根据 Diverts 下的“某些东西已经限制了失败”来判断这一发现，包括当它报告早期修复不起作用时：问题是该发现的失败是否已经限制，而不是早期修复是否实现了其目标。当有界时，不要再添加另一层；回复命名了早期的修复。如果不是，请将其修复为单独的项目；通常的情况是早期修复添加的行为比操作员显示的更多，例如空运行荣誉而实际运行忽略的过滤器。这条线路的历史提出了一个问题：它没有回答。

## 转移（适用于每个项目）

不再只固定具体信号：

- **这一发现并不成立** - 阅读代码显示问题不存在或已被处理 -> `not-addressing`，有证据。
- **这个问题不再相关**——自审查以来，此位置的代码已更改（请参阅下面的过时处理）-> `not-addressing`。
- **该修复会使代码变得更糟** - 它违反了活动instructions/conventions中的项目规则，添加了无效的防御代码，抑制了应该传播的错误，引入了过早的抽象，或者在注释中重述了代码 -> `declined`，引用了具体的危害。
- **发现是真实的，但要求在 PR 的用途之外进行工作** - PR 的目的是其描述、链接的问题或计划所说的要改变的内容；没有这些，这就是差异的变化。当对其采取行动会添加或更改PR未打算更改的行为时，即使在PR编辑的文件中，发现也超出了该目的：同级代码路径，具有类似问题的另一个模块，新选项或兼容性模式，或测试PR未触及的行为。 -> `declined`，命名目的并将发现留给单独的更改。发现更改后的代码是错误的，包括边缘情况，并且更改在其他地方导致的中断也是如此；判断那些与其他消遣。明确要求进行更广泛的更改以登陆此PR的人类审查者已经设定了其范围，因此将其视为内部。安全、数据丢失或不可逆转影响的发现永远不会因为超出范围而被拒绝：当它涉及代码时，PR不会改变，它是`needs-human`，所以一个人决定它的着陆位置。
- **这种改变并没有带来任何实际的好处**——表面上的偏好或无关紧要的编辑，对正确性、清晰度或可维护性没有任何好处 -> `replied`，简要说明为什么不需要改变。小的“真正的”改进仍然得到修复；跳过栏是“没有好处”，而不是“次要”。
- **某些东西已经限制了失败**——发现是正确的，但它描述的失败会在付出任何代价之前就浮现出来，你可以从代码、PR或命令自己的输出中命名浮现的内容：在真正运行之前操作员读取的试运行或预览、大声停止运行的错误、有人在依赖它之前检查的结果。 “它很小”和“它很少运行”根本不值一提。当一个小的非代码更改使该信号更清晰时（使用或操作手册行，更好的空运行消息）-> `fixed-differently`，并且进行了更改。当现有信号足够时->`replied`，命名。当故障成本在任何人看到之前就已经发生（数据丢失或损坏、金钱或访问权限错误授予），或者涉及安全、身份验证、计费、数据保留、迁移或不可逆转的外部影响时，此转移不适用；这些得到普通修复或下面的权限绑定路径。
- **更改是有风险的，您无法限制它** - 它触及热路径、其他代码依赖的边界或经过薄弱测试的代码，并且收益并不能证明风险是合理的。风险与规模不成正比；一行编辑就可以携带它。首先消除风险：读取调用者（您可能需要修复者添加测试并运行它）。如果读完后仍然存在重大风险，-> `needs-human`。
- **该修复将撤销*故意的*设计选择（罕见；需要证据）** - 该发现在其他方面是正确的且风险低，但实施它会扭转作者故意做出的design/product决定，*并且*有能力的工程师可能会合理地不同意哪个是正确的。这**不**适用，只是因为更改会改变行为——每次修复都会改变行为。 **仅当这两者都成立时**才适用，并且您可以命名它们：
  1. **意图的积极证据** - 一个具体的产物显示当前行为是一个选择，而不是一个意外：一个 comment/docstring 陈述它，一个测试断言它，一个 PR/commit 基本原理，或一个 sentinel/guard 仅作为决定才有意义。 “代码当前执行 X”并不是**证据（所有代码都执行某些操作）。如果您无法指出特定的产物，则没有刻意选择保护 -> **修复它**。
  2. **真正的分歧**——有能力的审稿人可以合理地选择其他方式；这是一个 judgment/product 调用，并不是作者错过的明显改进。

  当两者都持有 -> 撰写 `decision_context` 时，对比审查者的要求、意图产物和权衡，然后在其变为 `needs-human` 之前对其进行裁决（请参阅下面的“升级前裁决”）。当他们不这样做时，这是一个普通的修复。 **仍然修复这些（它们不满足这个条件）：**重命名，审查者查明的守卫，死代码删除，逐一，缺失空检查，样式，语义保留性能，或纠正证据显示是“错误”而不是决定的选择。这个守卫的存在是为了让自主调用者 (`ce-babysit-pr`) 永远不会默默地逆转预期行为——它**不是**升级普通反馈的许可证。默认值仍有待修复； “这可能是故意的”不是证据，不确定性会解决（或一个简短的`replied`问题），而不是升级。
- **这是一个问题，而不是变更请求**（“为什么是 X？”，“这是故意的吗？”）——可从代码中回答 -> `replied`；取决于您无法确定的 product/business 调用 -> `needs-human`。

## 过时的线程 (`isOutdated=true`)

diff 块发生了变化，因此报告的行可能不再是问题所在。 GitHub 还将 `line` 公开为可为空——过时的文件级线程通常具有 `line == null`。从可用的位置字段开始查找，优先顺序为：`line`、`startLine`、`originalLine`、`originalStartLine`。如果没有解析到与审查者的描述相匹配的当前内容，请从评论中提取锚点（符号、标识符或独特短语），并在得出结论之前在**同一文件**中搜索一次。不要搜索其他文件。三个结果：

- 在文件中找到锚点 -> 根据上面的转移信号在该位置重新评估。如果是修复程序，请将解析后的 location/anchor 传递给修复程序。
- 未找到锚点，注释描述了具体的就地代码 -> `not-addressing` 并带有证据（“在 <file> 中搜索了 <anchor>，不存在”）。
- 未找到锚点，注释表明代码已提取到另一个文件 -> `needs-human`。不要 grep 仓库；选择正确的新位置需要用户的判断。

## 谨慎升级 (`needs-human`)

除了上述风险和问题案例之外：影响其他系统的架构更改、安全敏感决策、模糊的业务逻辑或相互冲突的审核者反馈。很少见——大多数反馈都会得到修复。

在升级之前做好调查工作。不要用“这很复杂”来下注。用户应该能够在 30 秒内阅读您的分析并做出决定。

## 升级前先裁决

满足上述转移的项目仍然根据决策需要进行划分，并且只有一种到达人类。

- **权威约束**——决策需要本次运行所不具备的权威或知识：它涉及安全、身份验证、计费、数据保留、迁移或其他系统；这是产品或业务电话；它将采取的操作超出了继承的范围（合并、变基、强制推送、批准 CI）；或者只有用户知道意图。这是 `needs-human` 的组合。不要裁决它。
- **判断约束** - 有能力的工程师可能会合理地不同意，并且决策所涉及的每个事实都在存储库、PR和评审线程中：审查者想要逆转的故意选择、两个审查者要求相反的事情、更多证据可以约束的无限风险阅读，或者管道模式下的非收敛根。在该项目变为 `needs-human` 之前调用 `ce-pov`。

将 `ce-pov` 组合的 `decision_context` 作为方法集传递：审查者的要求、意图产物以及选项及其权衡。请求具有 `oracle` 的跨模型面板，这样，当可以访问其他模型时，判决取决于多个模型的判断。 `ce-pov` 提出问题并拥有裁决权；当无法联系到对等方时，它会降级为单独获取，而当证据丢失时，它会返回阻塞状态。每个根决策裁决一次，而不是每个线程裁决一次，并且绝不对不满足转移的项目裁决一次； “不确定”仍然决定修复。

判决决定项目：

- 其操作位于继承信封内的定位判决将成为其命名的普通判决（`fixed`、`fixed-differently`、`declined` 或 `replied`）。线程上的回复包含推理，按产品命名（例如 Codex 或 Grok，而不是模型版本或 ID）同意、不同或未运行的对等点，并表示调用是自主进行的，因此作者可以在事后撤销它。因为该回复在每种模式下都与判决一起传递，所以调用者也可以通过它来了解哪些对等点运行了。
- 受阻的结果、没有倾斜的判决、行动超出范围的判决，或者 `ce-pov` 在此宿主中不可用 -> `needs-human`。将裁决折入`decision_context`（其发现结果折入`investigation`，其倾斜折入`recommendation`），因此停放的物品比您开始时的物品更丰富。

## 回复列表和人员列表项目的回复文本

现在就写这些——你有证据。每条回复均以PR作者身份发布。通过 `ce-noslop` 技能将每一项写入其用户自己的写入寄存器中。引用所讨论的具体句子，如果评论很长，则不要引用整个评论。

对于`replied`（一个问题、讨论或一个正确但不重要的观点，你不会改变）：
```markdown
> 【引用审稿人评论的相关部分】

[直接回答问题、解释设计决策或不进行更改的简要理由]
```

对于`not-addressing`：
```markdown
> 【引用审稿人评论的相关部分】

未解决：[有证据的原因，例如“第 85 行已存在空检查”]
```

对于`declined`：
```markdown
> 【引用审稿人评论的相关部分】

拒绝：[引用的具体危害，例如，“这将添加类型系统已经保证的防御性空检查”或“违反项目约定中的禁止过早抽象规则”]
```

对于`declined`，因为该发现超出了PR的目的：
```markdown
> 【引用审稿人评论的相关部分】

超出范围：this PR [其在一个子句中的目的]。 [调查结果要求什么以及为什么这是一个单独的更改。] 留作后续处理。
```

对于 `needs-human`，**reply_text** 听起来很自然，正如 PR 作者会写的那样：
```markdown
> 【引用审稿人评论的相关部分】

[以 PR 作者的身份回复，例如，“这是 X 和 Y 之间的权衡——在拨打电话之前要仔细考虑。”或“需要在这方面与团队保持一致——[简要原因]。”]
```

持久的结果就是这个 `needs-human` 对象。在这里编写一次；调用者可以呈现它，但不得总结或重写其决策负载：

```yaml
type: "needs-human"
sources:
  - id: "Stable thread, top-level comment, or review-body ID from the fetched feedback"
    kind: "thread | comment | review | check | currency"
decision_context:
  quoted_feedback: "The specific ask or concern, quoted from the reviewer."
  investigation: "What was inspected and found, with concrete code locations."
  decision_reason: "The exact ambiguity or risk that makes autonomous action unsafe."
  options:
    - option: "A concrete choice"
      tradeoff: "What it gains and what it loses or risks"
  recommendation: "A lean and why, or null when the evidence supports no lean."
thread_urls:
  - "A URL for every still-open review thread covered by this residual"
```

`sources` 包括此 `needs-human` 对象覆盖的每一项，使用稳定的 ID，以便调用者可以将整个集合作为一个单元进行协调。该解析器发出 `thread`、`comment` 和 `review`；共享管道合约为CI生产者保留`check`，例如`ce-debug`和`currency`为`ce-babysit-pr`的确切分支货币观察密钥。 `thread_urls` 对于审查线程反馈来说是非空的，并且包括该对象覆盖的每个仍然打开的线程；当没有来源是审阅线程时，它可能为空。在普通运行中，将这些字段呈现为面向用户的决策部分。在`mode:pipeline`下，也将同一个对象返回给调用者； [pipeline-mode.md](pipeline-mode.md)定义了它的返回方式。
