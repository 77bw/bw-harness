# Git 承诺

从当前工作树创建精心设计的本地提交。没有推动，没有 PR — 使用 `ce-commit-push-pr` 来实现完整的交付流程。

**完成时间：** 每个逻辑更改都使用显式文件列表和说明结果的消息提交，并且 `git status` 清除了这些更改。 **停止时：**树是干净的（没有什么可提交的）。

## 语境

收集每个命令的上下文作为其**自己的** shell 工具调用（仅限程序 + 参数）。 **不要**与 `;`、`&&`、`||`、管道、`$(...)` 或重定向连接 — 该语法在 Windows PowerShell 下失败。非零退出是解释的正常状态，而不是抑制失败。

| 命令 | 目的 | 非零/空的意思 |
| --- | --- | --- |
| `git status` | 工作树状态 | 不是 git repo — 停止 |
| `git diff HEAD` | 未提交的更改 | 未出生的存储库/尚未提交 |
| `git branch --show-current` | 当前分行 | 空=分离HEAD |
| `git log --oneline -10` | 最近的消息样式 | Unborn repo——没有历史 |
| `git rev-parse --abbrev-ref origin/HEAD` | 远程默认分支 | 没有 `origin/HEAD` / 裸 `HEAD` — 尝试 `gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'`，否则 `main` |

将其视为快照。如果有任何更改，请在提交之前立即重新读取分支和暂存集。

**默认分支名称：** 从 `origin/HEAD` 中删除前导 `origin/`（因此 `origin/trunk` → `trunk`）。对所有“默认分支上”都使用这个裸名称吗？检查——永远不要与 `origin/<name>` 进行比较。

## 工作流程

0. **收集** — 运行上面的每个 Context 命令（每个命令都有自己的 shell 调用），然后继续。

1. **无需提交** — 如果 `git status` 显示没有暂存、修改或未跟踪的文件，请报告并停止。不要单独使用`git diff HEAD`作为清洁度（它会丢失未跟踪的文件）。

2. **首先分支** — 如果分离 HEAD，或在默认分支（`main` / `master` / 上面的默认名称）上，从更改内容 (`git checkout -b <name>`) 创建一个功能分支，然后重新读取 `git branch --show-current`。不要询问 - 仅提交仍然不能仅将工作留在分离的 HEAD 或默认分支上。如果派生名称存在，请选择一个不冲突的后缀。

3. **约定** — 匹配上下文中已有的项目提交约定；否则匹配最近的日志模式；否则常规提交 (`type(scope): description`)。当使用常规提交且`fix`/`feat`都适合时，默认为`fix:`（修复损坏或缺失的行为）；为新功能保留`feat:`。用户覆盖获胜。

4. **逻辑提交** — 如果更改的文件明显分为不同的关注点，请进行单独的提交（仅限文件级别，最多 2-3 个，无`git add -p`）。如果有歧义，则提交一次。

5. **消息** - 主题是命令式的，并命名结果（现在可能或已修复的结果），而不是文件列表。仅当主题的动机或权衡不明显时才使用主体。当此提交的计划实施单元 ID 已在手（对话、调用者或属于一个单元的文件）时，请在括号中附加该单元的 U-ID — `(U3)` 表示单元 3。不要寻找计划。当提交跨越多个单元、单元不清楚或手中没有计划时，请省略。当提交包含其他人的工作而不会以其他方式登陆到他们的名字下时（从他们的分支或 PR 移植，或从他们的补丁应用），请在消息结尾处为每个工作人员添加 `Co-authored-by: Name <email>` 预告片：其提交作者和他们的 `Co-authored-by` 预告片名称。从这些提交或补丁中准确复制每个身份。切勿猜测电子邮件：如果没有记录任何电子邮件，请在邮件正文中命名它们。

   - 不好：`Update checkout.rb` / `Add tests and fix stuff`
   - 好：`Fix double-submit on checkout`
   - 好：`Add per-subscription mute (U3)`

6. **阶段和提交** — 阶段**仅命名文件**（从不`git add -A`或`git add .`）。当调用携带它时，尊重`exclude:<paths>`：无论发生什么变化，这些文件都保持未提交状态；在报告中说他们被排除在外。使用文件写入工具将完整消息（主题行、空行、可选正文）写入存储库外部的文件，然后按每个提交组的两次调用进行暂存和提交：

```bash
git add file1 file2 file3
```

```bash
git commit -F <message-file> -- file1 file2 file3
```

没有 shell 会使用 `-F` 解析消息：`$`、引号、反引号或多行正文在任何 shell 下都按字面意思传递，无需满足引用规则。 Git 的正常空白清理仍然适用（尾随空格被修剪，空行运行被折叠），这对于提交消息来说很好。

`git commit` 上的尾随路径列表是必需的：裸露的 `git commit` 占用整个索引，因此在此运行之前已经暂存的任何内容（调用者的 `exclude:` 路径，或用户暂存但未命名的工作）都将进入提交。命名路径会准确提交组，而不会影响其他索引条目。

7. **确认** — `git status`；报告哈希值和主题。
