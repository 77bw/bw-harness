# 跨模型 POV 面板

该协议获取独立的对等 POV，调和重大分歧，并返回一个 ce-pov 决策。 ce-pov仍然是决策者：同行进行交叉检查，从不替代或投票。该面板是只读且非阻塞的；每个分支都以面板 POV、带有可用性说明的单独 POV 或普通 POV 的明确的缺失上下文结果为结束。

## 1. 确定主题、主持人、参与者

在花费之前解决对话速记问题：“方法”、“这些选项”和“提出的三个选项”是指由活跃对话识别的单个明确主题。当多个可能的主题会实质上改变 POV 并且上下文无法区分它们时，将缺失的上下文返回给调用者。

为主机和每个对等点保留四个单独的身份：

- **目标** — 面向用户的选择（`codex`、`claude`、`grok`、`cursor`、`composer`、`opencode`、`antigravity`或`pi`）；
- **harness/intermediary 路线** — CLI 或运行它的中介；
- **请求的模型** — 显式模型或路线声明的默认值；和
- **服务模型** — 工作人员收据（报告哪个模型应答的路线适配器）名称的模型，否则 `unverified`。

请求的模型是关于请求的事实并且始终是已知的；服务模型是关于后端的声明，只能从收据中得知。 `unverified`表示不存在收据，并不是型号未知。在用户阅读的任何内容中，通过其目标和请求的模型来命名对等体。仅当收据与请求不一致或路线请求无模型时（光标 default/Auto，OpenCode auto），才添加服务警告。具有所请求型号的无收据路线在面板记录中带有 `model_actual: unverified`，并且不需要在聊天记录中进行说明。

从主机提供的标记和服务证据来证明主机，而不是从另一个安装的 CLI 或主目录。仅当对等方所服务的模型系列与主机的模型系列明显不同时才设置`independence_verified: true`。否则保留有用的交叉检查但标签独立性未经验证；不要将其呈现为不同模型的佐证。如果寄宿家庭未知，自动发现会排除任何无法验证独立性的候选者，而不是猜测。

将主机宿主及其服务系列作为两个单独的令牌进行证明：

```bash
XHOST_SEEN=;
if [ "${CLAUDECODE:-}" = "1" ]; then XHOST_SEEN="$XHOST_SEEN claude"; fi;
if [ -n "${CODEX_SANDBOX:-}${CODEX_SANDBOX_NETWORK_DISABLED:-}${CODEX_SESSION_ID:-}${CODEX_THREAD_ID:-}${CODEX_CI:-}" ]; then XHOST_SEEN="$XHOST_SEEN codex"; fi;
if [ "${GROK_AGENT:-}" = "1" ] || [ -n "${GROK_SESSION_ID:-}" ]; then XHOST_SEEN="$XHOST_SEEN grok"; fi;
if [ -n "${OMPCODE:-}" ]; then XHOST_HARNESS=omp; XHOST_FAMILY=unknown;
elif [ "${CROSS_MODEL_HOST_HARNESS:-}" = pi ]; then XHOST_HARNESS=pi; XHOST_FAMILY=unknown;
elif [ "$XHOST_SEEN" = " claude" ] || [ "$XHOST_SEEN" = " codex" ] || [ "$XHOST_SEEN" = " grok" ]; then XHOST_HARNESS="${XHOST_SEEN# }"; XHOST_FAMILY="$XHOST_HARNESS";
elif [ -n "$XHOST_SEEN" ]; then XHOST_HARNESS=unknown; XHOST_FAMILY=unknown;
elif [ -n "${CURSOR_AGENT:-}${CURSOR_CONVERSATION_ID:-}" ]; then XHOST_HARNESS=cursor; XHOST_FAMILY=unknown;
elif [ -n "${OPENCODE_TERMINAL:-}" ]; then XHOST_HARNESS=opencode; XHOST_FAMILY=unknown;
else XHOST_HARNESS=unknown; XHOST_FAMILY=unknown; fi
```

两个令牌都来自与上述目标相同的对等密钥词汇表，而不是来自提供商的公司名称：`<host-serving-family>` (`XHOST_FAMILY`) 是`codex`、`claude`、`grok`、`composer`、`gemini` 或`unknown`。 `<host-harness>` (`XHOST_HARNESS`) 为 `codex`、`claude`、`grok`、`cursor`、`opencode`、`antigravity`、`omp`、`pi` 或 `unknown`。该片段是证据，而不是结论：它解析了其环境标记已命名的宿主，并且在您可以从自己的运行时识别的宿主上产生 `unknown`，证明您所知道的。代码片段未命名的宿主此处不需要新分支。

Claude Code、Codex 和 Grok 各自服务于自己的模型系列，因此当该宿主的标记是唯一存在的此类标记时，该片段会从该系列中获取该系列。另一个宿主可以复制这些标记之一（oh-my-pi 设置 `CLAUDECODE=1` 无论模型为其提供服务），并且从另一个宿主内部启动的会话会继承该宿主的标记。因此，该片段将家庭 `unknown` 留在为任何模型（oh-my-pi 或 Pi）提供服务的宿主上，或者当存在多个标记时。将片段名称传递给家人。在它离开系列 `unknown` 的地方，仅从运行时发布的模型 ID 设置它作为服务于该会话的模型，并且仅当该 ID 映射到`codex`、`claude`、`grok`、`composer` 或`gemini` 时。请求的型号、该型号自己的声明以及产品名称都不是该 ID。切勿从 Cursor 品牌推断服务家庭。

第 4 节将 `XHOST_FAMILY` 作为工人的第一个参数，将 `XHOST_HARNESS` 作为 `CROSS_MODEL_HOST_HARNESS`；任一槽中的提供者名称（例如 `anthropic`、`openai` 或 `xai`）都会使工作人员拒绝该作业并且不会产生任何产物。

`Cursor` 和 `Composer` 是不同的目标：

- `cursor`使用`cursor-agent`，没有强制模型，允许Cursor配置default/Auto选择。没有要求型号，因此除非收据可以识别型号，否则请报告`Cursor default/Auto; serving model unverified`和`independence_verified: false`。
- `composer`通过`cursor-agent`请求当前兼容的Composer模型。
- `grok`更喜欢原生Grok CLI； Grok 通过 Cursor 是不同的路线和接收者。第 3 部分绑定哪个令牌。
- `antigravity`通过Google Antigravity的ACP运行时运行Gemini模型，其服务家族是`gemini`。对 Gemini 对等点的请求会绑定此目标。 `CROSS_MODEL_PEERS` 仅通过文字标记 `antigravity` 来批准它，因此跳过此处命名该标记。当主人的服务家庭为`gemini`或其挽具为`antigravity`时，它绝不是同伴。
- `pi` 在其自己配置的模型上运行 Pi 编码代理，除非 `provider/model` 引脚指定一个。 Pi 服务于任何提供者，因此它的服务家族是未知的，并且它的 POV 从来都不是独立的。当主机的宿主为`pi`时，它永远不是对等体。

仅应用一个参与分支：

`oracle` 是面板行为的简写，而不是关键字门。咨询其他模型、收集独立同行意见、与指定同行进行压力测试或调和他们的分歧的明确请求会进入相同的协议，即使该请求从未说过`oracle`。单独请求 ce-pov 则不然。

- **命名同行：** 精确且无上限。宣布并运行每个指定的目标。显式名称会覆盖 `oracle` 发现及其上限。切勿将命名的 `Cursor` 重写为 Composer 或用另一个模型替换显式命名的模型。
- **裸`oracle`：**使用对话首选项、本地配置、活动项目约定选择最多两个可到达的、可证明不同模型的目标，然后是默认顺序`codex -> claude -> grok -> antigravity`；宣布选择并运行它。调用`oracle`授权针对当前项目的普通只读咨询。
- **显式未命名交叉检查：**跳过校正成本检查并使用下面的计数规则；宣布选定的对等点并运行它们。
- **没有明确的交叉检查：**在ce-pov独立形成其POV之后，仅当有意义的下游工作将在错误出现之前建立在采取的基础上时才提供，或者它提供共享的、公共的、安全的或数据的承诺。 1 级收养不符合资格；第 2/3 级符合资格。热情的祈祷（会议中期的第二意见）永远不会提供。

对于计数规则：零可达意味着单独加上一条可用线。一个或多个自动选择的对等点意味着在分派之前有一条简洁的进度线命名选定的目标。光标默认值和 Composer 永远不会自动选择；它们在命名或配置为首选项时运行。

**先前意见主题。** 当主题是已经形成的位置时 - ce-pov 自己的先前 POV 或用户陈述的视图 - 该位置是主题产物并在有效负载中运送；同行们用自己的结论回答根本问题，那些`independent`声音进入融合（与`skeptic`模式不同，批评没有）。根据第 4 节的第一轮排序，在专家组请求（传票）之后形成的任何新的主机元判断都将被保留。用户提供的立场与主持人创作的立场的处理方式相同——作为主题发布，绝不屈服。

## 2. 规范范围并冻结存储库身份

将允许的读取范围标准化为：

- 一个存储库相关的工作空间根；和
- 可选的有序包含和排除路径模式。

将相同的表示传递给每个对等提示和路由适配器。默认是存储库根目录。用户或主机提供的较窄范围具有约束力，并且永远不会扩大。在同一主机上启动的同行检查现有主题文件并直接从该共享工作树支持证据；将它们指向这些文件，而不是将其内容复制到有效负载中。仅当材料仅存在于对话中或在工作区中不可用时才内嵌传递材料。

将包含和排除路径模式视为协作模式，除非具体适配器将它们转换为文件系统控件。永远不要将仅提示模式、工作目录或只读标志作为机密边界，也永远不要承诺可读范围内的秘密是不可访问的。同行可以在声明的范围内搜索和阅读，但不得改变项目或故意在项目之外进行检查。每个路由都会拒绝对等方的写入请求，并在存在适配器的只读模式的情况下运行该适配器的只读模式，但 Codex 适配器不会强制执行其只读模式，因此没有路由是写入沙箱。

在初始调度之前，捕获一个**存储库范围身份**：已提交的修订版以及规范化范围内的脏内容和未跟踪内容的摘要。将其包含在每个对等有效负载中。在每次协调调度之前和最终折叠之前重新验证它。如果发生更改，切勿将过时的声音协调或折叠到当前项目中：披露更改并重新启动新身份上的所有声音或返回不完整的面板结果。

调用者将在 SKILL.md 阶段 1 中创建的已解析绝对值 `$SCRATCH_DIR` 传递给此面板。将有效负载、原始输出、日志和结果产物保留在那里；不要重建此参考中的临时根。在调度之前在`umask 077`下创建每个有效负载，然后在`chmod 600 "$PAYLOAD_PATH"`下创建；不要单独依赖环境 umask 或模式标志。

## 3. 解决并公布一条固定路线

路由仅在硬边界内适用。所要求的目标加上安全性、权威性、独立性、阅读范围以及外部接收者可以接收项目内容的规则是持久的；具体模型 ID、CLI 标志和可用性是适配器默认值。

对于每个对等点：

1. 探索当前路线和模型功能，而无需授予流程项目内容或存储库访问权限。
2. 首先尝试声明的首选映射。
3. 如果观察到该默认值不可用、过时或不兼容，则仅选择同一请求目标、模型系列和推理层中最接近的兼容等效项。记录观察到的当地事实并替换。显式用户模型请求不能成为另一个模型。对于`antigravity`，worker自己从`gemini-4-argon`到`gemini-3.8-flash`的回退是首选映射，因此主机不会为其传递任何替换模型。
4. 解决一个具体目标、型号选择、利用路线、提供商和每个中介。确认每个实际收件人均位于允许的外部收件人的白名单中。
5. 出发前用普通语言宣布选定的目标和路线。

传递给worker的固定路由恰好接受这些令牌；工人拒绝任何其他事情（包括像`codex-cli`这样的路线形状的猜测）：

| 目标 | 路由令牌 |
|--------|----------------|
| `codex` | `codex` |
| `claude` | `claude` |
| `grok` | `grok-cli`（原生CLI）或`grok-cursor`（通过 Cursor 中介） |
| `cursor` | `cursor` |
| `composer` | `composer` |
| `opencode` | `opencode` |
| `antigravity` | `antigravity` |
| `pi` | `pi` |

主机宿主不选择 Grok 路线。安装 CLI 后，目标 `grok` 会绑定 `grok-cli`。仅当用户通过 Cursor 请求 Grok 时，或者当 grok CLI 不存在且 Cursor 是受制裁的接收者时，才绑定 `grok-cursor`。

二进制存在仅证明一条路线是候选路线。仅当当前主机上下文使该证据具有权威性时，预调度能力证据才可以细化固定路由。不要在那里进行预检身份验证：具有提供者能力的工作人员尝试拥有身份验证真相，并且有效的产物是可用性证明。根据结构化诊断对失败的运行进行分类，而不是根据通用终端状态进行猜测。

派出的工人只运行固定路线。它必须将故障返回给主机，而不是自动跳到另一个提供商或中介。如果重试会添加意外的收件人或中介，请在主机上解决该问题，解释更改，并在开始新的固定路由作业之前询问。单独控制外部咨询的活跃用户、项目或组织指令也需要批准。否则，显式对等、交叉检查或 `oracle` 调用有权继续。无法在这些规则内运行的命名对等点会被报告，而不会被默默地替换或删除。

发送前的更新应说明谁将检查该主题，并且该评论是只读的。不要背诵范围机制，承诺存储库秘密不可访问，或描述探测结果、CLI版本、模型层、提交哈希、存储库身份、路由运行状况、作业生命周期或临时路径。仅当合作范围限制实质性改变用户的选择时才提及。除非用户提供了可识别的名称，否则将代码库称为“此项目”或“存储库”。

## 4. 发送、等待、收获、收集

准备一个完整的规范有效负载，其中包含框架问题、主题形状、规范化读取范围、存储库范围身份、模式、工作区中已有主题材料的路径以及此处不可用的所需对话材料。让同行检查并对照共享工作树。不要仅仅为了向同行介绍情况而复制可读文件或添加主机策划的架构摘要。

对于初始 `independent` 轮，排除 ce-pov 的位置和所有其他声音的结论。正在评审的提案、文件或方法集是主题，并且仍然完全可用；独立性意味着保留先前对其的判断，而不是保留产物。主持人自己的论点——候选人风险列举、作为事实陈述的决定性前提、倡导框架和评估选项标签——是协调轮材料，而不是第一轮材料；独立轮仅包含框架问题、主题、阅读范围和证据。按来源定义第 1 轮证据：源定位事实和用户决策相关需求是第 1 轮材料，而主机解释、风险排名和推荐结果不是第 1 轮证据（例如，“PATH 中的文件包含 X”是第 1 轮证据，而“X 是有风险的选项”等待协调）。为内嵌的仅对话材料添加标签。当用户的目标影响决策时，请包括该目标、他们持有该目标的强烈程度以及他们为此提供的任何证据。在有效负载中声明拒绝每个提供的选项或框架本身是有效的位置。当 ce-pov 在会话中创作主题时，即使保留完整的主题文档，也要以有效负载自己的语言对称地呈现选项。当主语本身是一个已经形成的
职位（第 1 节），上面保留的材料列表仅适用于响应专家组请求而生成的新主机框架：该职位自己的场所、标签和宣传船作为主题产物完好无损，并且只有在专家组请求等待协调后形成的主机元判断 - 同行仍然返回自己的独立裁决。对于`skeptic`模式，包括ce-pov的位置，因为批评它是任务。调节有效负载遵循第 5 节，并有意包括已经形成的位置。

验证相同的完整有效负载是否适合每条选定的路线；切勿根据提供者截断它。不能接受它的路由在普通的部分面板降级规则下是不可用的。

使用此技能目录中的 `scripts/cross-model-pov.sh` 为每个对等点运行一条已解析的固定路由，并使用 `scripts/peer-job-runner.py` 进行分离的生命周期控制。将实际的存储库根与任何较窄的读取根分开传递，并在存储库外部将回合输出目录预先创建为私有临时目录。对于指定的同事，根据具体目标开始一项工作；对于选定的面板，为每个选定的对等点启动一项作业。在等待之前启动所有作业。

**默认情况下，同行预算不需要您提供任何东西。** 该技能的工作人员会在 600 秒处停止，而运行者主管会得出 1230 秒的下限，因此运行者窗口已经比工作人员的上限长，并且不会杀死任何健康的东西。

**升高 `CROSS_MODEL_HARD_SECS` 自动加宽运行器窗口。** 运行器从环境旋钮 (`max(1230, knob + 30)`) 获得其监控硬上限。不要在此处设置数字 `CE_PEER_HARD_SECS` — 并清除起始前缀 (`CE_PEER_HARD_SECS=`) 上的任何环境值，以便过时的导出不会削弱派生。不要将 *已解决的* `CROSS_MODEL_HARD_SECS` 重新导出到工作程序的命令行上：这会将回退转换为覆盖并剥夺工作程序自己的默认值。

每个工作人员写入`<run-dir>/pov-<target>.json`，其中`<target>`是已解析的路线目标，`grok-cli`/`grok-cursor`折叠为`grok`。将该路径准确地作为 `--result-path` 传递到 `peer-job-runner.py start`，因此 `done` 是产物的密钥，并且 `result <job-id>` 可以读取它，而无需猜测文件名或主机的提供程序密钥。

**运行器前缀。** 下面的每个运行器调用都以这两行开头，位于与命令*相同的*工具调用中，因为每个工具调用都是一个新的 shell。将`SKILL_DIR`设置为**该**技能的`SKILL.md`的绝对目录； shell 的工作目录是用户的项目，而不是技能目录。不要对 `python3` 进行硬编码：在本机 Windows 上，它解析为 Microsoft Store 存根，该存根在不运行 Python 的情况下退出，并且仍然满足 `command -v`，因此前缀探测执行而不是存在。

```bash
SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>";
PY="$(for c in python3 python py; do command -v "$c" >/dev/null 2>&1 && "$c" -c '' >/dev/null 2>&1 && { echo "$c"; break; }; done)"; [ -n "$PY" ] || { echo "no working Python 3 interpreter on PATH" >&2; exit 1; };
```

- `deadline passed: reap <job-ids>, then wait once more; ...` — 使用运行程序前缀和以下命令在一次调用中获取列出的每个作业，然后再次运行 wait 命令。如果最后的等待打印同一行，则停止等待并将仍在运行的作业视为超时。

```bash
"$PY" "$SKILL_DIR/scripts/peer-job-runner.py" reap <job-ids...>
```

作业 ID 或作业目录路径是位置性的。 `--skill`、`--run-id`和`--label`仅用于启动；切勿将它们传递给 `wait` 或 `reap`。截止时间是工人自己的上限加上10秒（默认610秒）。从最后一个作业开始计算。该命令将主机环境中的 `CROSS_MODEL_HARD_SECS` 的上限传递给运行程序，运行程序会添加 10 秒本身并拒绝非普通秒数的值。工作人员继承相同的环境，因此导出较大值的用户可以保留更宽的窗口。切勿将 `CROSS_MODEL_HARD_SECS` 添加到启动命令的 `env` 前缀中：工作人员会看到此等待没有看到的上限。切勿设置较小的`CROSS_MODEL_HARD_SECS`来更快完成：有些同伴通常需要大约四分钟，而较短的上限会在他们跑完后让他们放弃。让每个等待调用运行其完整片段：当您的 shell 工具在命令退出之前交回控制权时（Codex shell 会话仍在运行，后台任务），请继续读取该命令的输出，而不是开始另一个等待。在等待之间，读取行显示 `done` 的任何作业的结果，而不是保留它直到其余作业完成。

对每个已启动的作业从其终止状态进行分类； `done` 本身并不能证明存在可用的产物。

仅通过运行者的所有权检查 `result` 界面读取产物和日志。仅接受模式形状的产物，其 `position` 是框架问题的固定答案，具有非空 `reasoning`、有效的 `movement` 和 route/model 收据元组。解决是对等方自己通过模式所需的`final`标志进行的声明，而不是对其散文的阅读：标记为`final: true`的解决的`Blocked — …`判决是一个可用的答案，而任何`final`不正确的成形产物都是占位符。工作人员在同一个硬窗口内，在具有最终答案要求的同一条路线上重试一次非最终产物，如果它重复出现或没有窗口剩余，则会丢弃带有 `peer skip evidence: non-final position` 的语音。如果您仍然收到非最终产物，请将其视为无可用产物，而不是视为对等声音。初始响应需要 `movement: initial`；协调答案需要`moved`或`held`加上发生了什么变化或为什么新证据不充分。

仅根据收据而不是请求来归因所提供的模型。分别记录目标、实际harness/intermediary路线、请求模型、服务模型和`independence_verified`。 `unverified` 的服务模型在记录中保留 `unverified`；它不会成为注释中的“未知型号”，因为所请求的型号是已知的。

每条路由都经过 acpx，需要 Node 22.13 或更高版本以及 `npx`。工作线程`transport unavailable (pre-egress, <scope>): <reason>`表示对等点没有运行并且没有任何内容到达提供者；报告该声音未运行的原因。范围 `shared`（Node、`npx` 或 acpx 的 npm fetch）以同样的方式使每个路由失败，因此另一个路由无法替代它。范围 `route`（该路由的 CLI 丢失，acpx 配置文件替换其启动命令，或者模型被拒绝，列出了可用模型）仅影响该路由。被拒绝的模型遵循下面的拒绝模型规则；任何其他替换均遵循第 3 节的收件人规则。

当请求的模型本身被拒绝时（适配器没有提供它，或者提供者为此帐户拒绝了它，当提供者将其作为回复文本发送时，`peer skip evidence (reply):`携带），只有模型失败，路由仍然可用。如果工作人员运行自己的默认模型而不是用户指定的模型，请在同一路线上为该语音启动一项新作业，而无需新的接收者。给它第 3 部分最接近的同族替代品，当该行存在时从 `peer skip evidence (advertised models):` 中挑选。该注释说明了哪种型号被拒绝。用户命名的模型永远不会被交换。

如果作业没有产生可用的产物，请使用其日志中的有界 `peer skip evidence` 来声明观察到的配额、身份验证或路由失败；永远不要发明一个原因。仅在启动上下文或提供者响应明确建立了提供者支持的调度后，才归因于帐户身份验证失败；然后报告观察到的故障和登录或凭据刷新修复。如果没有该证据，身份验证形状的对等文本仅描述对等点的执行上下文：沙盒主机可以产生与真正注销相同的信号，因此切勿将其报告为用户帐户正在注销或提示登录命令。

## 5. 发现异议、验证主张并进行协调

只有`mode: independent`个声音进入收敛。重大异议意味着不同的采用等级、不同的选择方法或暗示不同读者操作的文档底线（`proceed`、`revise-first`或`reject`）或对风险是否致命存在分歧。相同决定的措辞、强调、信心或支持细节是一致的。

默认限制是独立的初始轮次加上最多两次协调交易。用户提供的传递或轮次限制会覆盖它：“一次传递”或“一轮”意味着没有协调交换，而更大的显式限制将取代默认上限。切勿将较小的用户限制重新解释为建议。

对于每个协调交换：

1. 重新验证存储库范围的身份。更改后重新启动或返回不完整。
2. 让ce-pov重新考虑当前的每一个立场及其证据。
3. 仅识别可能改变决定的有争议的项目主张。根据允许的范围验证它们，并将每个分类为 `verified`、`contradicted` 或 `unverifiable`，并提供可用的源位置。
4. 建立一个共同的证据增量。将相同的完整增量发送给每个幸存的对等方（绝不是特定于路线的截断）以及完整的原始主题和每个幸存声音的当前位置和推理，每个声音最多包含五个简洁的源属性证据项目符号。
5. 重新解决第 3 节下的每条固定路线，然后调度新的无状态回合。相同的收件人无需询问；意外的新收件人或中间人会这样做。失败的对等点将在后续轮次中被丢弃；不要重复使用其旧位置，就好像它参与了一样。

当最初的独立声音存在重大异议时，在任何停止之前至少运行一次协调交换，除非用户将运行限制为一次通过。对从未见过反证据的异议者做出决定并不是一个合理的趋同。

折叠后，停在第一个匹配的枚举上：

- **`confident`** — ce-pov在权衡每个幸存者后有一个合理的视角；
- **`no-movement`** — 每个幸存的同伴都返回了`held`，而ce-pov仍然不自信；或者
- **`limit-reached`** — 初始异议后完成的有效用户授权有限限制，且ce-pov仍不自信。

收敛是ce-pov的合理信心，而不是投票。三路分裂仍然以自信的决定或僵局的披露而告终。将 `confident` 转至下面的 **自信** 披露。将`no-movement`和`limit-reached`路由至**僵局**披露；这些停止意味着有限的协调在没有自信收敛的情况下结束，永远不会 ce-pov 应该推断出一个确定的结果。

瓶盖停止自动调度；这是一个检查点，而不是证明另一轮毫无用处。在检查点，确定有界扩展是否可能改变结果。仅当 ce-pov 能够指出未解决的决策相关问题、延期将引入的新证据或框架，以及为什么会改变立场时，才建议具体数量的额外交换。否则建议停止。更多轮次需要用户批准，除非用户提前提供了更大的限制；每次批准都会建立一个新的有限上限，而不是一个开放式循环。

## 6. 决定并披露

以 ce-pov 的 POV 主导活动主体形状，随后是紧凑面板
笔记：

- **自信：**说明声音是否一致。并发性提高了信心，但并不能消除相关模型的盲点。如果ce-pov决定反对，请指出不同意见以及为什么其结果占上风。仅对同行的判断提出同行同意；将您在面板后添加的任何建议命名为您自己的建议。
- **僵局：**说明ce-pov的当前位置，每个幸存同伴的位置和动作，每个声音的最后状态，以及分歧是证据差距还是判断差异。有真实依据时推荐；否则就可以通过材料权衡说“两者都是可行的”。在上限中，添加**更多轮次：**推荐具有新证据路径的特定有界扩展，或者建议停止，因为没有额外的交换可能会改变结果。
- **部分：**幸存和删除的目标的名称以及观察到的失败状态（例如配额、身份验证、超时或在有界重试中幸存的非最终占位符位置）。
- **无幸存者：** 提供单独的 POV，但“跨模型检查不可用或不完整”。当存在传票但小组分支从未进入（没有可到达的对等点，或者分支从未进入）时，仍然说明小组状态 - 尝试了哪些对等点，或者没有运行以及观察到的原因 - 而不是发送一个纯粹的单独判决。

在小组记录中保留目标、路线、请求的模型、服务的模型和独立收据，但保持默认聊天记录与决策相关：按目标和请求的模型、其位置和运动、任何观察到的失败以及仅在收据不同意、未请求模型或独立性影响可信度的情况下命名对等体或独立性警告。不要转储路线或模型诊断，除非它们实质上改变了结论或用户提出要求。切勿将位置归因于未运行的模型。

面板本身永远不会发生变化。交付后，应用SKILL.md阶段4的四部分连词：原始提示明确授权指定的下游操作，结果不陷入僵局，操作保留在继承范围内，并且是非破坏性的，否则已授权。所有四个人都必须通过交接；否则返回判断，不启动下游工作。调用工作流保留延续的所有权。

## 7. 怀疑模式和退化

当被要求挑战ce-pov而不是形成独立的POV时，设置`mode: skeptic`。将有效的归因批评折叠到 ce-pov 一次，但不要将该声音纳入收敛。披露是否改变了 POV。失败的怀疑论者会像任何不可用的同伴一样退化。

对等点永远不会阻止 POV。中途失败只会掉落该声音；过大的规范有效负载会丢弃无法接受相同有效负载的路由；没有幸存的同伴产生单独的 POV 和可用性说明。

区分路线级故障和调度基础设施故障。如上所示，运行并返回不可用产物的路由将被删除。但是，如果调度脚本本身意外失败（崩溃、任何作业开始前非零退出、未解析的脚本路径），请不要在第一个错误时删除该对等点。手动尝试相同的解析路线，保持选定的目标和模型、标准化读取范围以及固定的回合独立性规则。仅当每一次故障都是新的、似乎可以恢复的故障并且小组的总期限尚未过去时才继续尝试；一旦失败重复发生或截止日期已过，就停止并陷入单独的视角。手动恢复可能无法替代不同的目标、扩大读取范围或包含保留位置 - 这些使得恢复的对等点的结果不可信，而不仅仅是不可用。

## 8. 清理

在成功、失败、超时、中断和收获时，删除此运行的私有临时根下的每个使用的作业目录、轮输出目录、有效负载、原始日志和结果。切勿在当前运行根目录之外删除。同行推理和项目背景不得过时。

## 参与、公告和披露（从正文中移出）

传票（面板请求）是咨询或协调同行的**肯定**请求，通过对调用上下文（用户的措辞或调用技能的参数）进行推理来检测。拒绝协商的措辞（“单独 POV，不要交叉检查”）或仅仅重述过去的交叉检查，在没有要求的情况下命名相同的术语，并且不是传票：不会派遣同行，也没有项目上下文离开运行。对于肯定请求，呼叫者在一个通道中的释义永远不会取消另一个通道中仍然存在的传票；只有从上游每个可读通道中删除的召唤在这里是无法恢复的。调用指定对等点、显式交叉检查或 `oracle` 授权面板协议针对该项目进行正常的只读协商。在调度前公布选定的节点；仅当重试添加意外收件人或中介，或者活动指令需要单独批准时才询问。同行直接检查共享工作树并被告知不要编辑它。小组协议保留了公正的初始回合，限制基于证据的协调，同时尊重用户提供的通行证限制，并且仅归因于收据支持的独立性。
传票后交付的任何 POV 都会说明哪些同行参加了竞选，或者没有参加竞选，以及观察到的原因；如果传票后没有小组运行，请保持判决内容不变，但添加小组状态行，而不是发送裸露的单独判决。没有召唤的 POV 会保持独奏结果不变，没有小组注释。使主机自己的冻结位置远离独立对等方的初始上下文；仅当请求的任务是批评该立场或稍后的协调轮比较已形成的观点时才公开它。
