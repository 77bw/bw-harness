# 批量迁移流程

首先获取只读清单。对于每个段落、表格、代码片段或证据参考记录其来源path/anchor、传入链接、已知修订或受保护副本、候选所有者和范围。查找现有的成功检查（如果有）。对于未追踪的原材料Git不是回收源。不要将私有产物复制到跟踪的文档中或假设已备份被忽略的目录。

建议以可审查单元进行操作：**保留为历史/交叉链接/合并/按责任拆分/推迟冲突**。对于混合的CONTEXT/CONCEPTS页面，稳定的术语可能会进入领域术语表，对ADR的决定，研究的测量反例以及当前状态的开放单元。不要只是将文件重命名为 GLOSSARY。对于已解决的课程，请先检查原生 CE 的当前形式并复制，然后再推荐耐用的支架；旧的会话摘要并不能证明问题已得到解决。保留业务代码及其目录布局。

在编写批准的批次之前，再次找到相关的段落和当前的差异。如果来源自批准后发生更改，请协调或暂停受影响的项目。 Create/merge 更改旧入境点之前的目的地；保留引用的证据条件和来源指针。更新传入链接（包括锚点和地图）；在历史引用文档无法移动的地方，保留一个小的历史重定向及其范围。永远不要删除唯一的副本或默默地解决语义矛盾。未批准的项目保持不变。

为了进行验证，请追踪每个起始部分的保留来源、合并的权威或明确的开放问题；打开来自新老消费者的链接。比较 before/after 文件名、批准的范围和 Git 差异（包括未跟踪的资产）。记录每个项目的恢复（原始 revision/retained 路径或经过验证的受保护备份），而不是对其他人的树进行破坏性的全面重置。
